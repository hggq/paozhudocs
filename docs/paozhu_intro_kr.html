Paozhu（폭죽）웹 프레임워크

Paozhu는 C++로 작성된 웹 프레임워크입니다. 소스 코드: https://github.com/hggq/paozhu. 가장 두드러진 특징은 하나의 실행 파일에 모든 것이 들어 있다는 점입니다. HTTP/1.1, HTTP/2, WebSocket, 원시 TCP, MQTT 클라이언트, Redis 클라이언트, ORM, 템플릿 뷰, 정적 파일 서비스가 모두 같은 프로세스에 존재하며, 컴파일 시 스위치로 필요 없는 부분을 잘라낼 수 있습니다.

가장 짧은 예제부터 보겠습니다. 핸들러는 코루틴 작업을 반환하고, peer->output에 대입한 값이 응답 본문이 되며, 라우트는 함수 위의 주석으로 선언합니다:

서버를 실행한 뒤 브라우저에서 http://localhost/hello 로 접속하면 됩니다.

#include "httppeer.h"
#include "testhello.h"
namespace http
{
//@urlpath(null,hello)
asio::awaitable<std::string> testhello(std::shared_ptr<httppeer> peer)
{
    peer->output = "Hello, world!";
    co_return "";
}
 
}// namespace http

hello는 주석 함수입니다. testhello.h는 직접 만들 필요가 없으며 cmake make 시 자동으로 생성됩니다. co_return "";은 고급 사용 방식으로, 값을 반환하면 다음 주석 함수로 계속 진행하고 빈 값을 반환하면 완료를 뜻합니다.

1. 무엇인가

소스 구조만 보아도 분명한 설계 방향이 드러납니다.

네트워크 계층은 standalone Asio 위에 구축되어 있습니다. 서버는 자체 이벤트 루프 대신 asio::io_context를 보유하며, 따라서 Asio 생태계의 대부분의 용법을 그대로 연결할 수 있습니다.

I/O와 비즈니스 로직은 분리되어 있습니다. I/O 스레드는 accept, read, write만 수행하고, 동기 핸들러는 전용 비즈니스 스레드 풀 clientrunpool로 디스패치됩니다. 그러므로 핸들러 안의 블로킹 코드는 네트워크 스레드가 아니라 비즈니스 풀을 점유합니다.

I/O 루프는 하나로 합치지 않고 코어 수에 따라 그룹화됩니다. 프로세스는 여러 io_context 인스턴스를 가지며, 각 연결은 라운드 로빈으로 그중 하나에 배정되고, 각 ioc는 여러 스레드를 실행합니다. 자세한 내용은 3절에서 다룹니다.

코루틴이 라우팅 계층의 진입점입니다. 라우트 매칭과 디스패치는 router::co_resolve에서 시작되며, pre 핸들러와 핸들러 모두 동기 슬롯과 코루틴 슬롯을 가지고 있어 비즈니스 코드가 원하는 방식을 선택할 수 있습니다.

HTTP/2는 자체 구현입니다. 프레임 파싱, HPACK에 사용되는 Huffman 코딩, 연결별 송신 링, 전역 송신 큐, 흐름 제어가 모두 서드파티 래퍼 뒤가 아니라 이 저장소 안에 있습니다.

라우트는 주석으로 선언하고 컴파일 시 레지스트리로 만듭니다. 비즈니스 함수에 //@urlpath(...) 주석을 달면, 빌드 시 paozhu_pre가 이를 스캔하여 레지스트리와 함수 선언 스텁을 생성합니다.

기능은 하나의 묶음으로 제공됩니다. ORM, 커넥션 풀, RBAC, OAuth, 결제, Excel/Word/PDF, 이미지, 압축, 차트, SMS, Redis 클라이언트가 모두 같은 저장소의 vendor/와 libs/ 아래에 있습니다. 기본값은 꺼져 있으며, CMakeLists.txt에서 해당 CMake 옵션의 기본값은 OFF입니다.

저장소는 대략 네 계층으로 나뉩니다. vendor/httpserver가 프레임워크 본체입니다. 그 밖의 vendor/ 하위 디렉터리와 libs/는 재사용 가능한 기능입니다. common/, orm/, models/, viewsrc/는 프레임워크와 비즈니스 코드 사이의 접착 계층입니다. controller/, view/, www/, module/는 통째로 삭제 가능한 예제 비즈니스 코드입니다. mini_project.sh가 이 구분을 실제로 보여 줍니다. 이 스크립트는 controller/src/admin, github, oauth 같은 데모 디렉터리를 제거하고 프레임워크 코어만 남깁니다.

2. 실행하기

의존성과 빌드

의존성은 vcpkg.json에 나열되어 있습니다: openssl, brotli, asio, zlib, sqlite3와, pkgconf, libgd, freetype, libpng, libqrencode를 끌어오는 gd 기능입니다. vcpkg를 쓴다면 -DENABLE_VCPKG=ON을 켜고 CMAKE_TOOLCHAIN_FILE을 전달하십시오. 자세한 내용은 README_CN.md에 있습니다. xmake를 선호하는 사람을 위해 xmake.lua도 함께 제공됩니다.

일반적인 빌드는 세 단계입니다:

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./bin/paozhu                 # you can also pass ./bin/paozhu /path/to/server.conf

bin/에는 현재 세 개의 산출물이 있습니다: paozhu, paozhu_cli, paozhu_pre. 벤치마크 관련 코드는 -DENABLE_BENCHMARK=ON을 명시해야 포함됩니다.

빌드는 네 개의 CMake 타깃을 만듭니다: 메인 프로그램 paozhu, 데이터베이스/모델 도구 paozhu_cli, 주석 라우트 생성기 paozhu_pre, 그리고 빌드마다 실행되는 paozhu_codegen입니다.

메인 프로그램의 소스 집합은 여러 glob으로 조립됩니다:

set(paozhu_srcs
  ${common_list} ${viewsrc_list} ${framework_cpps} ${orm_list}
  ${reflect_list} ${src_list} ${source_list} ${controller_list})

reflect_list는 libs/*.cpp를 재귀적으로 포함합니다.

진입점

Release 빌드는 startup/main_daemon.cpp를 사용하고, 다른 빌드 구성은 자동으로 startup/main_dev.cpp로 전환됩니다. 데몬 버전은 먼저 argv[1]을 server.conf의 경로 또는 그것을 포함하는 디렉터리로 취급한 뒤, init_daemon() 안에서 fork합니다. 자식은 get_server_app(), http::rbac::install_route_guard(), httpmy.run(argv_str)를 실행하고, 부모는 wait를 반복하며 SIGCHLD가 오면 자식을 다시 생성합니다. 포그라운드 버전은 fork 없이 같은 run() 경로를 따릅니다.

run() 내부의 순서는 다음과 같습니다: 설정 읽기, ioc와 스레드 생성, accept 시작, 라우트 등록, 이벤트 루프 진입.

3. 요청은 어떻게 흘러가는가

스레드 분할 방식

프로세스에는 네 종류의 스레드가 있습니다. 개요는 다음과 같습니다.

스레드 종류 개수 담당 업무
accept 스레드 2개 (HTTP용 1, SSL용 1) 블로킹 accept; 새 연결을 ioc에 넘김
I/O 스레드 ioc 개수 × ioc당 run() 스레드 수 io_context::run() 실행; 연결 I/O와 프로토콜 파싱
보조 스레드 httpwatch 1개, HTTP/2 송신 http2_send_loop_num개(최소 2), websocket_loop 1개, ratelimiter 1개 주기적 검사, HTTP/2 송신 큐 배출, 연결 단위 속도 제한
비즈니스 풀 hardware_concurrency() + 2 동기 핸들러 실행

I/O 스레드 수는 두 단계로 계산됩니다. ioc 개수는 min(cothreadnum, hardware_concurrency())이고, 그 값이 4보다 작으면 4로 올립니다. 그다음 각 ioc가 per_ioc_thread_num개의 run() 스레드를 시작합니다. conf/server.conf의 주석이 공식을 직접적으로 적어 둡니다: cothreadnum * per_ioc_thread_num = threads.

io_contexts[0]에는 두 번째 역할이 있습니다. 호환용 멤버 io_context이기도 하며, 프레임워크 자체의 타이머 루프, 동기 커넥션 획득, client_context가 모두 이 위에 머뭅니다.

직렬화는 연결 내부에서만 일어납니다. 새 연결은 session_ioc_cursor++ % io_contexts.size()로 ioc에 배정되고, 연결은 자체 asio::strand를 바인딩하여 해당 연결의 프로토콜 처리가 순서를 유지하도록 합니다. 서로 다른 연결 사이에는 그런 순서 보장이 없습니다.

httppeer 풀은 스레드가 아니지만, 스레드와 혼동하기 쉬워 여기에 등장합니다. acquire_peer()가 재사용 가능한 객체를 가져가고, 마지막 참조가 해제되면 reset_for_reuse()를 거쳐 돌아옵니다. 상한은 PEER_POOL_MAX = 512이며, BENCHMARK 빌드에서는 4096입니다.

연결은 처음 들어온 뒤 나갈 때까지 다음 스레드를 거칩니다:

  1. accept 스레드가 연결을 받아 ioc에 넘깁니다.
  2. 그 이후 읽기, 쓰기, 프로토콜 파싱은 해당 ioc의 run() 스레드에서 실행되며, strand가 연결의 처리를 직렬화합니다.
  3. 동기 핸들러에 도달하면 작업이 비즈니스 풀로 디스패치되고, 코루틴 핸들러는 그 자리에서 await하며 ioc 스레드에서 계속 진행됩니다.
  4. 출력에서 HTTP/1.1은 I/O 스레드가 직접 되돌려 쓰고, HTTP/2는 송신 큐를 배출하는 고정 http2_send_queue_loop 스레드로 들어갑니다.
  5. 보조 스레드는 주기적 검사, 속도 제한, 큐 배출만 수행하며 비즈니스 로직은 처리하지 않습니다.

라우트 매칭과 디스패치

accept부터 응답까지 주요 경로는 다음과 같습니다:

accept (side thread)
  → pick an ioc by round-robin, bind the connection to a strand
  → parse: HTTP/1.1 via http_parse.cpp, HTTP/2 via http2_parse.cpp
  → take an httppeer (acquire_peer)
  → router::co_resolve
        ├─ exact lookup, then prefix fallback (up to 6 segments)
        ├─ write the matched mask_code into the peer
        ├─ annotation-level rate limiting
        ├─ RBAC hook, only when mask_code is non-zero
        └─ pre → handler (the synchronous path goes to the business pool; coroutines await in place)
  → write the response: HTTP/1.1 directly, HTTP/2 through the send queue

router.cpp에는 두 개의 병렬 구현이 있습니다. 하나는 동기 체인, 다른 하나는 co_resolve 안의 코루틴 체인입니다. router.h의 주석은 두 체인의 pre/handler 분기가 동일하게 동작해야 함을 명시합니다. 한쪽을 바꾸면 다른 쪽도 바꿔야 합니다.

HTTP/1.1 및 HTTP/2 출력

HTTP/1.1 파싱은 자체 구현이며, vendor/httpserver/src/http_parse.cpp를 중심으로 request.cpp와 httppeer.cpp가 이를 보조합니다. 요청과 응답은 직렬이며 파이프라이닝은 없습니다.

HTTP/2는 완전한 구현이며, 관련 파일은 모두 vendor/httpserver/src/에 있습니다. http2_parse.cpp는 프레임 파싱과 연결 상태 머신, http2_frame.cpp/http2_define.cpp는 프레임 구조와 상수, http2_huffman.cpp는 HPACK가 사용하는 Huffman 코덱, http2_ring_queue.cpp는 연결별 고정 크기 송신 링, http2_send_queue.cpp는 전역 송신 큐, http2_flow.h는 흐름 제어 윈도우 정의를 담습니다.

몇 가지 설계 포인트가 중요합니다:

  • 연결마다 32슬롯 고정 링이 있습니다. CONST_HTTP2_RING_QUEUE_CAPACITY = 32이며, 컴파일 시 2의 거듭제곱이고 unsigned char에 들어가야 함을 검사합니다. head_와 tail_은 원자적 인덱스이고, 별도의 bytes 적재 카운터가 있습니다.
  • 송신 객체는 명시적인 상태 머신을 가집니다. own_state가 객체가 풀, 전역 큐, 스레드 전용 저장소, 주차 상태 중 어디에 있는지 나타내고, block_reason이 차단된 이유를 기록합니다.
  • 차단된 객체를 반복적으로 폴링하지 않습니다. parked_list에 주차해 두고, 윈도우 변경, SETTINGS 프레임, 링 슬롯 해제라는 세 종류의 이벤트가 발생할 때 park() / detach_parked() / reattach_parked()로 다시 붙입니다.
  • 스트림은 일반 유휴 타임아웃이 아니라 "120초간 진행 없음"을 기준으로 리셋됩니다. 상수는 CONST_HTTP2_SEND_NO_PROGRESS_TIMEOUT = 120이고, 검사는 server.cpp에 있습니다.
  • 스위치는 conf/server.conf의 http2_enable = 1입니다.

4. 각 모듈의 역할

프레임워크 코어: vendor/httpserver

이 디렉터리는 include/와 src/로 나뉘며, src/ 아래에 85개의 .cpp 파일이 있습니다. 역할은 다음과 같이 묶입니다:

  • 서버와 수명 주기: server.cpp, serverconfig.cpp, client_context.cpp, resident_stop.cpp — 시작, 설정, 스레드 조율, 정상 종료.
  • 연결과 프로토콜: http_parse.cpp, http_header.cpp, http_domain.cpp, rpc_parse.cpp, client_session.cpp — HTTP/1.1 파싱, 호스트 라우팅, RPC 파싱.
  • HTTP/2: 3절에 나열한 파일 그룹.
  • 요청 모델: httppeer.cpp, request.cpp, cookie.cpp, session_id.cpp.
  • 라우팅: router.cpp, viewmethold_reg.cpp.
  • ORM과 연결: orm_common.cpp, orm_conn_pool.cpp, orm_connect_mar.cpp, orm_query.cpp, mysql_conn.cpp, pg_conn.cpp, sqlite_conn.cpp.
  • 스레드 기초: threadpool.cpp, atomic_count.cpp, atomic_guard.cpp.
  • 정적 파일: file_get_content.cpp, gzip.cpp, https_brotli.cpp, mime.cpp, directory_fun.cpp.
  • 장기 연결: ws_*.cpp, http_websocket_client.cpp, http_socket*.cpp, mqtt_*.cpp, sock_subpub_reg.cpp.
  • 보안과 인증: jwt.cpp, acme_*.cpp, ocsp_check.cpp, base64.cpp, md5.cpp.
  • 유틸리티: parse_ini.cpp, str_fun.cpp, urlcode.cpp, unicode.cpp, datetime.cpp, qrcode.cpp, send_email.cpp, fastcgi.cpp, loadmodule.cpp, loadviewso.cpp.

include/의 두 헤더는 오해하기 쉽습니다. request.h는 사실 HTTP 요청 클래스가 아니라 내장 JSON 마이크로 객체 obj_val이며, 실제 요청/응답 운반체는 httppeer.h입니다. httphook.h는 common/httphook.cpp와 함께 라우팅, 인증, 속도 제한이 붙는 훅 계층을 이룹니다. 또한 orm_cache.hpp, mysqlorm.hpp, postgresqlorm.hpp, sqliteorm.hpp는 ORM의 템플릿 파사드입니다.

두 개의 생성기: vendor/httpcli

이 디렉터리는 역할이 완전히 다른 두 실행 파일을 만듭니다.

paozhu_pre는 주석 라우트 생성기입니다. 소스는 vendor/httpcli/autopickmethod.cpp와 vendor/httpserver/src/md5.cpp입니다. controller/src 아래의 주석을 스캔하여 common/autocontrolmethod.hpp와 controller/include/*.h를 기록합니다.

paozhu_cli는 데이터베이스/모델 도구입니다. 소스는 vendor/httpcli/http_cli.cpp와 ORM 연결 및 모델 소스입니다. dbcreate, dbconvert, dbschema_check, dbdump_*, templateparse*, struct_reflectfile 같은 기능을 제공하며, vendor/httpcli/*.hpp에 선언되어 있습니다.

vendor/httpcli/ 아래의 .hpp 파일은 생성기의 템플릿이자 파싱 구현입니다: controllerparse.hpp, ccontrollfun.hpp, dbtypes.hpp, modelfun.hpp, templateparse.hpp, typestatement.hpp, utility.hpp.

생성 체인은 빌드에 연결되어 있습니다:

add_custom_target(paozhu_codegen ALL)
    COMMAND paozhu_pre <source root>
add_dependencies(paozhu paozhu_codegen)

따라서 빌드마다 paozhu_pre가 실행되지만, 파일 해시와 mtime을 비교하여 변화가 없으면 아무것도 기록하지 않습니다.

레지스트리와 비즈니스 계층: common, controller

common/에는 14개 파일이 있으며, 대부분 손으로 작성한 전역 정의와 레지스트리이고 생성 파일은 하나뿐입니다. autocontrolmethod.hpp는 paozhu_pre가 기록하는 주석 라우트 레지스트리이며, 출력 경로는 vendor/httpcli/autopickmethod.cpp에 하드코딩되어 있습니다. autorestfulpaths.hpp는 RESTful 경로의 파라미터 이름을 기록합니다. server.cpp가 이를 include하고, mini_project.sh가 새 프로젝트를 만들 때 이를 다시 씁니다. cost_define.h는 전역 상수, httphook.cpp는 훅 계층 구현, json_reflect_headers.h는 JSON 리플렉션 헤더를 모읍니다. reghttpmethod.hpp와 reghttpmethod_pre.hpp는 초기의 수동 레지스트리입니다(REG_SYNC_SYNC 매크로 목록이며 server.cpp가 include). 나머지 파일 — mqtt_client_regmethod.hpp, mqtt_method_reg.hpp, redis_regmethod.hpp, sock_client_regmethod.hpp, sockets_method_reg.hpp, websockets_method_reg.hpp, ws_client_regmethod.hpp — 는 여러 장기 연결 백엔드용 레지스트리입니다.

등록 순기를 기억할 필요가 있습니다. server.cpp는 _initauto_all_httputils(), _inithttpmethodregto(), _inithttpmethodregto_pre()를 이 순서로 호출합니다. 생성 테이블, 수동 테이블, 수동 pre 테이블 순입니다. reg_add는 첫 등록을 유지하므로, 같은 경로의 수동 항목은 생성 테이블에 가려집니다. paozhu_pre는 이를 알고 생성 중에 그러한 충돌을 ROUTE-WARN으로 보고합니다.

controller/include/ 아래의 100개 헤더는 손으로 쓴 코드가 아니라 생성된 함수 선언 스텁입니다. paozhu_pre는 주석 시그니처가 바뀔 때만 md5와 mtime으로 판단해 다시 씁니다. configure 단계에서 CMake는 빠진 헤더를 file(TOUCH)로 자리 표시자만 만듭니다. 실제 구현은 controller/src/에 있으며 비즈니스 도메인별로 나뉩니다: 백오피스와 권한용 admin/, superadmin/(superadmin/rbac/ 포함), rbac/; 인가와 로그인용 oauth/, oauth_client/, github/; 다중 테넌트 데모 사이트 saas.com/; 모니터링 엔드포인트용 serverwatch.cpp; 기능 데모와 회귀 사례용 test_*.cpp, test*.cpp(예: test_maskcode.cpp는 주석 속도 제한을 보여 줍니다).

데이터 계층: orm, models, schema

orm/orm.h가 진입점입니다. 그 아래에 MySQL, PostgreSQL, SQLite에 대응하는 세 모델 도메인 cms/, pg/, lite/가 있습니다. orm/cms/include/ 아래의 64개 *_base.h는 paozhu_cli가 생성하며, 헤더에 This file is auto create from paozhu_cli라고 적혀 있습니다. fk_child_opsql.cpp와 fk_parent_opsql.cpp는 손으로 작성한 조인 쿼리입니다. models/는 모델 동작을 담습니다. 이 .cpp 파일은 paozhu_cli가 한 번만 생성하고 이후 덮어쓰지 않습니다. 파일 헤더에 기존 파일은 유지하고 없는 파일을 생성한다고 적혀 있으므로, 여기에 비즈니스 로직을 안전하게 작성할 수 있습니다. schema/에는 테이블 생성 SQL이 있습니다.

커넥션 풀은 vendor/httpserver/src/orm_conn_pool.cpp와 include/orm_conn_pool.h에 있습니다. 풀은 ioc별로 샤딩됩니다. 전역 max_pool을 샤드 수로 나누고 나머지는 작은 샤드에 차례대로 더하며, 각 샤드는 최소 한 슬롯을 가집니다(slot_max_of / slot_min_of). 샤드마다 자체 락이 있어 서로 다른 ioc의 스레드는 같은 락을 두고 경쟁하지 않습니다. 설정 키는 orm_ioc_num과 orm_thread_pool_num이고, 연결 파라미터는 conf/orm.conf에 있습니다. ORM은 코루틴 인터페이스도 노출합니다. orm_connect_mar.cpp와 orm_query.cpp의 쿼리는 직접 await할 수 있습니다.

재사용 가능 기능 라이브러리: libs

libs/에는 11개 하위 디렉터리가 모두 수동으로 작성되어 있습니다. 빌드 시 CMakeLists.txt의 재귀 glob으로 메인 타깃에 포함되고, 헤더 디렉터리도 재귀적으로 include 경로에 추가됩니다.

libs/rbac는 권한 판정의 핵심입니다. rbac.h는 load_user_roles, load_role_perms, load_user_grants(한 번에 여섯 쿼리로 역할, 권한, 할당 계층, 디렉터리를 가져옵니다), user_has_url, user_has_permscode를 제공합니다. route_guard.cpp는 라우트 훅입니다. adminid가 없으면 401, companyid가 없으면 403을 반환하고, 그 외에는 캐시에 맡깁니다. route_cache.cpp의 allow()는 (adminid, companyid)를 키로 16 샤드, 4096 항목, 60초 TTL로 캐시합니다. 로딩 시 샤드 락을 잡아 single-flight를 구현하고, 로드 실패는 fail-closed로 처리합니다. route_cache.cpp에는 호출자가 없는 stats() 함수도 있습니다.

libs/oauth는 OAuth 서버 측으로, conf/oauth.conf를 읽는 oauth_config, 토큰 해싱·PKCE 검증·Basic 클라이언트 인증을 담는 oauth_store, 감사 로그를 담는 oauth_audit로 나뉩니다. oauth_audit의 audit_log()는 프레임워크 오류 로그 큐에 한 줄을 넣고, httpwatch가 이를 log/error.log에 덧붙입니다. 엔드포인트 자체는 controller/src/oauth/에 있습니다: oauth_authorize.cpp, oauth_token.cpp, oauth_introspect.cpp, oauth_revoke.cpp, oauth_jwks.cpp, oauth_metadata.cpp, oauth_userinfo.cpp, oauth_bearerauth.cpp, oauth_client_add.cpp, oauth_purge.cpp.

libs/oauth_client는 특정 인증 서버에 묶이지 않는 범용 OAuth 2.x/2.1 클라이언트입니다. 엔드포인트 URL 네 개를 채우면 GitHub, Google, 자체 호스팅 oauth 엔드포인트와 통신할 수 있습니다. PKCE, 세 가지 grant(authorization code, refresh, client_credentials), introspect와 revoke를 지원합니다. libs/github는 GitHub 전용 변형으로, state는 [adminid, client_id, rand32] 세 부분이고, revoke는 DELETE + Basic을 사용하며, scope에는 항상 read:user가 덧붙습니다. github_api, github_config, github_crypto, github_store도 포함합니다.

libs/webpay는 애플리케이션 측 결제 로직입니다. 주문 상태 머신(pending/paid/cancelled/refunded), 주문번호 생성, wxorder로 조회, 비동기 조회, WeChat V3 조회 응답에 대한 정산 판단과, 콜백, 인증서 게이트, Alipay/WeChat V2/V3, QR 코드, 토큰 관련 파일이 있습니다.

libs/markdown의 markdown2html은 인용, 굵게, 링크, 제목, 수평선, 표, 이미지, 한 줄 취소선, 코드 블록, 순서/비순서 목록을 처리하고 목차와 참조 목록도 관리합니다. libs/pinyin은 pinyin-data의 데이터와 이진 탐색으로 한자를 병음으로 변환합니다. libs/ipdata는 ip.data(ip2region 형식)를 읽어 IP를 국가/성/도시로 매핑합니다. libs/department는 parentid와 children을 가진 조직 트리 구조입니다. libs/img의 upload_images는 이미지, 동영상, base64, 폼 파일 업로드를 처리하고 업로드된 파일을 나열합니다. libs/types에는 중첩 객체와 배열을 포함한 JSON 리플렉션용 예제 타입이 있어 리플렉션 생성을 시연합니다.

선택적 기능 모듈: vendor/*

이 모듈들은 모두 include/ + src/ 구조를 따르고 기본값은 꺼져 있습니다. 소스는 CMakeLists.txt의 조건부 glob으로 paozhu_srcs에 추가되며, 스위치도 같은 곳에 모여 있습니다. 실제 애플리케이션에서 필요할 가능성이 높은 순서대로 정리했습니다.

문서와 스프레드시트. 백오피스 보고서 내보내기, Excel 가져오기, 계약서나 공지 생성, 페이지를 PDF로 저장하는 용도입니다. pzexcel은 xlsx 읽기/쓰기, 여러 시트, 셀 스타일을 담당합니다. pzword는 docx 읽기/쓰기, HTML↔docx 변환을 지원하고 메모리 바이트 스트림으로 바로 출력할 수 있습니다. webpdf는 PDF 렌더러이며, 공개 헤더가 HTMLRenderer를 노출하고 같은 디렉터리에 HTML, CSS, SVG, TTF용 파서 네 개가 있습니다. 애플리케이션이 Office 문서를 가져오거나 내보내면 ENABLE_OFFICE를 켜고, HTML→PDF에는 ENABLE_PDF를 따로 켜십시오.

압축, 이미지, 차트. 패키지 다운로드나 업로드 압축 해제에는 pzzip을 쓰십시오. 임시 파일 없이 메모리 버퍼에 zip을 바로 쓸 수 있습니다. 캡차와 일반 이미지 처리에는 pzimage를 쓰십시오. PNG/JPEG 코덱을 포함하고 TrueType/OpenType 외곽선으로 글리프를 그릴 수 있습니다. 보고서 페이지에 넣는 차트에는 pzcharts를 쓰십시오. SVG를 직접 생성하며 선형, 부드러운 선형, 막대, 산점수, 도넛, 레이더, 게이지, 퍼널 차트를 지원합니다. 스위치는 서로 독립적이므로 실제로 사용하는 기능만 켜십시오.

결제와 SMS. 거래 흐름이 필요하면 vendor/webpay를 쓰십시오. WeChat/Alipay SDK를 감싸고 V3 인증서, 플랫폼 인증서, 환불 멱등 키 같은 하위 수준의 세부 사항을 처리합니다. 애플리케이션 측 로직(주문 상태 머신, 콜백, 인증서 게이트)은 앞선 libs 절에서 설명한 대로 libs/webpay에 있습니다. 인증번호나 알림에는 sms를 쓰십시오. 알리바바 클라우드와 텐센트 클라우드 클라이언트가 들어 있습니다. 각각 ENABLE_WEBPAY와 ENABLE_SMS에 대응합니다.

캐시 등. pzredis는 Redis 클라이언트입니다. redis_client는 연결을 직접 들고 있지 않습니다. 각 명령이 설정 섹션에서 연결을 빌려 쓰고 끝나면 돌려주며, 동기 API와 코루틴 API를 모두 제공합니다. 캐시, 분산 락, pub/sub에는 ENABLE_REDIS를 켜십시오. 프레임워크 수준의 Redis 장기 연결 클라이언트는 별도 스위치 ENABLE_REDIS_CLIENT이며, ENABLE_REDIS도 켜져 있어야 합니다. 그렇지 않으면 configure가 즉시 실패합니다.

장기 연결

저장소에는 주로 데모 사이트와 예제인 네 개의 독립 디렉터리 — websockets/, sockets/, mqtt/, redis/ — 가 있습니다. 실제 프로토콜 구현은 vendor/httpserver/src/에 있습니다. WebSocket은 ws_conn.cpp, ws_handshake.cpp, ws_parser.cpp, ws_wire.cpp, websockets_callback.cpp; 원시 TCP는 http_socket.cpp, http_socket_client.cpp, sock_subpub_reg.cpp; MQTT는 mqtt_frame.cpp, mqtt_session.cpp, mqtt_reg.cpp, mqtt_subpub_reg.cpp, http_mqtt_client.cpp; Redis 장기 연결은 http_rpcclient.cpp와 vendor/pzredis의 클라이언트입니다. 스위치는 ENABLE_WEBSOCKETS_CLIENT, ENABLE_SOCKETS_CLIENT, ENABLE_MQTT_CLIENT(기본 켜짐), ENABLE_REDIS_CLIENT(기본 꺼짐이며 ENABLE_REDIS 필요)입니다. 비즈니스 측 레지스트리는 common/의 *_regmethod.hpp 그룹입니다.

뷰, 정적 파일, .so 핫 로딩

view/에는 손으로 작성한 HTML 템플릿이 비즈니스 도메인별로 home/, admin/, cms/, login/, oauth/, superadmin/ 등으로 나뉘어 있습니다. viewsrc/include/viewsrc.h와 viewsrc/include/regviewmethod.hpp는 수동 등록 진입점입니다. viewsrc/view/**.cpp는 템플릿 파서가 생성한 C++이며, 파일 머리에 //This file create by paozhu가 붙습니다(viewsrc/view/home/header.cpp 참조). 현재 home/header.cpp, oauth/consent.cpp, oauth_client/page.cpp, superadmin/*.cpp 등이 포함됩니다. 파서는 vendor/httpcli/templateparse.hpp에 있습니다.

www/default/는 정적 사이트 루트이며, wwwpath = ./www/default로 설정합니다.

module/은 공유 라이브러리 디렉터리로, module/controller/testviewso.so와 module/view/{admin,cms,home,login}/*.so가 들어 있습니다. 스위치가 각쪽을 담당합니다. ENABLE_VIEWSO는 viewsopath로 module/view를 가리키고, ENABLE_MODELSO는 controlsopath로 module/controller를 가리킵니다. 로딩 로직은 loadmodule.cpp와 loadviewso.cpp에 있으며, pz::dll::library로 .so 파일을 열고 라이브러리 핸들을 캐시된 함수 포인터와 함께 보관하여 dlclose 이후 포인터가 무효화되지 않도록 합니다.

5. 설정과 확장

설정 파일 위치

conf/는 하위 시스템별로 나뉩니다: server.conf, orm.conf, redis.conf, mqtt.conf, sockets.conf, websockets.conf, oauth.conf, webpay.conf, acme.conf, github.conf, test.conf와 인증서 및 키 파일입니다. 가장 자주 다루게 될 세 파일은 프로세스와 사이트를 담당하는 server.conf, 데이터베이스 연결의 orm.conf, 자동 인증서 발급의 acme.conf입니다. 나머지는 해당 하위 시스템을 켤 때만 중요합니다.

server.conf

주 설정 파일이며, 시작 시 한 번 읽습니다. 주석 라우트 작성하기

라우트는 비즈니스 함수 위의 주석으로 선언하며, 형식은 //@urlpath(pre, urlpath)입니다. HTTP 메서드를 구분하려면 :mask 접미사를 붙일 수 있습니다:

//@urlpath(superadmin_islogin,superadmin/rbac/perm)
std::string superadmin_rbac_perm_list(std::shared_ptr<httppeer> peer)

이 예제는 controller/src/superadmin/rbac/rbacperm.cpp에서 가져왔습니다.

스캔 후 paozhu_pre는 reg_raw(site, path, pre_sync, co_pre, reg_sync, co_reg, mask_code) 형식의 항목을 생성하여 common/autocontrolmethod.hpp에 넣습니다. :param이 포함된 경로는 파라미터 이름도 common/autorestfulpaths.hpp에 등록합니다. 주석에는 //@urlpath(...):ratelimit(time,num) 형태로 속도 제한 파라미터를 실을 수도 있습니다. 예제는 controller/src/test_maskcode.cpp에 있고, 파싱된 값은 라우트 항목의 rate_time과 rate_num에 들어갑니다.

주석을 원하지 않는다면 common/reghttpmethod.hpp에 순수 수동 등록 방식 REG_SYNC_SYNC가 있으며, /helloworld용 인라인 람다도 들어 있습니다. 다만 이 등록은 생성 테이블 뒤에 오므로 같은 이름의 경로는 생성 항목에 가려집니다. 임시 실험에는 적합하지만 운영 엔드포인트에는 적합하지 않습니다.

엔드포인트 추가하기

일반적인 경로는 짧습니다. controller/src/ 아래에서 적당한 파일을 골라 주석과 함께 함수를 작성하고 빌드하십시오. 빌드 중 paozhu_codegen이 paozhu_pre를 실행하여 controller/include/의 선언 스텁과 common/autocontrolmethod.hpp의 레지스트리 항목을 갱신합니다. 프로세스가 시작되면 생성 테이블을 등록하고 요청이 해당 라우트로 향합니다.

엔드포인트에 속도 제한이 필요하면 주석 뒤에 ratelimit(time,num)을 추가하십시오. RBAC가 필요하면 라우트에 0이 아닌 mask_code를 주고, 권한 테이블에 같은 urlpath와 maskcode를 가진권한 부여 행을 추가하십시오. libs/rbac/rbac.h의 주석은 판정 조건이 "라우트의 maskcode가 사용자의 유효 권한 중 하나와 정확히 같아야 한다"고 설명합니다.

런타임에 .so 로딩

컴파일 시 ENABLE_VIEWSO 또는 ENABLE_MODELSO가 켜져 있으면 module/view와 module/controller 아래의 .so 파일을 런타임에 로드할 수 있습니다. 뷰 측 진입점은 loadview / loadviewso이고, 컨트롤러 측 진입점은 loadmodule.cpp에 있습니다. 설정에서 viewsopath와 controlsopath를 해당 디렉터리로 가리키십시오. module/ 아래 파일은 빌드 산출물이거나 수동 배포된 공유 라이브러리이며 소스가 아닙니다.

6. 테스트와 자체 점검

테스트는 기본적으로 빌드되지 않고 -DENABLE_TESTS=ON일 때만 포함됩니다. tests/CMakeLists.txt의 규칙은 tests/*.cpp와 tests/orm/*.cpp 각각에 같은 이름의 실행 타깃을 만드는 것이며, pool_thread만 예외입니다. 기존 사례에는 test_framework_smoke.cpp(프레임워크 스모크), test_http2_ring_queue.cpp와 test_http2_headers_split.cpp(HTTP/2 송신 링과 헤더 분리), test_router_hooks.cpp(라우트 훅), test_jwt_smoke.cpp(JWT), test_filename_safety.cpp(파일명 안전), test_pzexcel_p2.cpp와 test_pzzip.cpp(선택적 하위 모듈)가 있습니다. 프로토콜 파싱용 하위 디렉터리로 http1_consume/, multipart_boundary/, multipart_part_headers/, postform/, raw_post_fastpath/, orm/도 있습니다.

자체 점검 엔드포인트는 모두 controller/src/serverwatch.cpp에 있습니다. /metrics는 Prometheus 텍스트 형식을 출력하고, /paozhu_status는 구버전 사용자 정의 대시보드이며, /frametasks_timeloop는 프레임워크 타이머 작업을 보여 줍니다. 백오피스 로그인 엔드포인트는 admin/login과 속도 제한이 걸린 admin/loginpost:ratelimit(60,5)이고, controller/src/admin/main.cpp에 구현되어 있습니다. 최고 관리자 진입점은 superadmin/login이며 controller/src/superadmin/supermain.cpp에 있습니다.

7. 검증 범위

이 문서의 결론은 대부분 소스와 디렉터리 내용을 읽어 얻었습니다. 빌드 설정, 스레드 토폴로지, 라우팅 경로, HTTP/2 송신 큐, RBAC 캐시, 속도 제한, 생성 산출물, server.conf 키, 자체 점검 엔드포인트는 모두 마지막에 나열한 파일로 추적할 수 있습니다. 이번에는 libs/와 vendor/ 아래 모듈의 공개 헤더도 다루었습니다. oauth, oauth_client, github, webpay, markdown, pinyin, ipdata, department, img, types, pzexcel, pzword, webpdf, pzimage, pzcharts, pzzip, pzredis, sms에 대한 설명은 해당 헤더의 함수 시그니처나 주석에 근거합니다.

여섯 영역은 구현을 하나씩 읽지 않았습니다. 이 목록 바깥의 설명을 한 줄 단위로 검증된 사실로 취급하지 마십시오:

  • ENABLE_MODELSO를 켰을 때 module/controller/testviewso.so 안의 함수 이름이 라우트에 어떻게 매핑되는지. 스위치와 디렉터리의 대응 관계만 확인했고, 로딩 이후의 전체 등록 체인은 확인하지 않았습니다.
  • 세 ORM 모델 도메인(cms/pg/lite)의 필드 범위와 생성 규칙. 생성 출처, 풀 샤딩, "기존 모델 파일 유지" 정책만 확인했습니다.
  • view/ 템플릿을 viewsrc/view/*.cpp로 만드는 생성 문법과 갱신 트리거. 파일 헤더 표식과 파서 위치만 확인했습니다.
  • 각 tests/*.cpp 사례의 구체적인 단언. 파일 이름과 tests/CMakeLists.txt의 규칙으로만 설명했습니다.
  • startup/main_dev.cpp와 startup/main_daemon.cpp가 fork 이외에 정확히 같은 체인을 따르는지. 두 파일을 한 줄씩 비교하지 않았습니다.
  • pzexcel, pzword, webpdf의 구현 깊이. 공개 헤더만 읽었고 각 읽기/쓰기 흐름을 따라가지 않았습니다.
