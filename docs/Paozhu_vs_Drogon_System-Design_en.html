Paozhu vs Drogon — C++ Web framework System Design Comparison

Based on source-code verification (paozhu(https://github.com/hggq/paozhu), drogon(https://github.com/drogonframework/drogon), both retrieved Oct 2026). Key finding: drogon-master (master branch checked out Oct 2026) has no HTTP/2 server implementation in lib/ or trantor/ (no Http2Server/Http2Connection; lib/src/HttpServer.cc only outputs HTTP/1.1, no h2/ALPN registration; trantor only has TLS-layer ALPN stubs). Paozhu ships HTTP/2 built-in (http2_parse.cpp and related). All Drogon HTTP/2 references below are scoped to the actual code present in this checkout — Drogon's mainline had not yet landed an HTTP/2 server at time of writing, making Paozhu's HTTP/2 a genuine differentiator.

0. One-Line Positioning

  • Drogon: Classic muduo-style reactor + reflection-macro registration + compile-time code generation. Industrial-grade, complete ecosystem, friendly high-level API.
  • Paozhu (炮竹): Single io_context + Asio C++20 coroutines throughout the stack (even ORM queries are coroutines). HTTP/1.1 and HTTP/2 both custom-built. "Full async coroutine + multi-tenant" orientation.

Philosophical divergence:

  • Drogon's "multiple independent loops" fits the classic Reactor model more cleanly — a single connection binds to one thread for its full lifetime, lock-free, good cache locality.

2.1 Static File Serving + Compression Cache (Both Have It, Opposite Strategies)

Neither does "real-time compression on every request" — both use a cache after the first access. But the caching strategies are diametrically opposed: Paozhu lazily compresses and auto-writes to disk; Drogon expects pre-compressed files to already exist.

Paozhu — Lazy cache + auto-reclaim (server.cpp:395-518):

  • Compress on first request: Detect Accept-Encoding → brotli / gzip → temp file → rename atomic write (safe for concurrent first hits).
  • Cache filename: {original_path}.{hash(host+"\n"+urlpath)}.br or .gzip. Subsequent hits just fopen and serve — zero CPU cost.
  • Large file protection: Skip compression for content_length > 16MB (saves memory).
  • Bad-cache protection: Fall back to original content on compression failure, don't write cache; auto-detects 0-byte cache files, deletes and regenerates.
  • Cache reclaim: Pushes mtime back on large-file hits; background daemon reclaims cold entries based on CONST_HTTP_STATIC_CACHE_REFRESH_AGE.

Drogon — Pre-compressed file lookup (config.example.json:296-301 + StaticFileRouter.cc):

  • Framework reads but never writes: gzip_static: true (default), brotli_static: false. On request, framework directly looks for pre-compressed .gz / .br files in the same directory. If not found, serves original.
  • Requires pre-compression via gzip -k / brotli in CI/CD deploy pipelines. Framework itself never computes compression.
  • Plus: IOThreadStorage-isolated static file content cache (StaticFileRouter.h:150-153, per-EventLoop isolation, lock-free).

Essential difference: Paozhu makes compression caching an auto-managed framework concern (lazy compression + atomic write + bad-cache guard + reclaim) — zero developer cost. Drogon pushes compression caching to the deployment phase — framework only reads, never writes, keeping itself lighter. Both have equivalent runtime performance (zero CPU after cache hit), but the first-access path and operational model are different.

3. Routing System (Deep Dive)

Both use "declarative route registration", but the mechanisms fork: Drogon uses compile-time reflection + macros + static self-registration; Paozhu uses source annotations + build-time codegen generating reg_raw tables. Additionally, Paozhu extra-provides simple task orchestration based on httppeer::flow_method (see §3.4). Drogon has no equivalent.

3.1 Registration & Code Generation

Paozhu (controller/src/*.cpp with //@urlpath(pre,urlpath):mask, scanned by paozhu_pre at build time):

  • The generated common/autocontrolmethod.hpp contains a reg_raw call table (autocontrolmethod.hpp:127-141): reg_raw(site, path, pre_sync, co_pre, reg_sync, co_reg, mask_code). Each route registers 5 slots: synchronous pre, co_await-pre, synchronous handler, coroutine handler, and mask_code (numeric in the //@urlpath annotation distinguishing HTTP methods).
  • Paths with a :param segment get a separate reg_urlpath(site, path, {param_names...}) table right after (autocontrolmethod.hpp:139-140).
  • Build also generates helper tables: common/autorestfulpaths.hpp, common/reghttpmethod.hpp, etc.

Drogon (via HttpController.h macros, compile-time):

  • METHOD_ADD(method, pattern, ...) / ADD_METHOD_TO(method, path, ...) (HttpController.h:31-34) → registerMethod(&method, pattern, {...}, ...). Also supports ADD_METHOD_VIA_REGEX (:35) for regex patterns.
  • Static self-registration: Each controller includes class methodRegistrator + static methodRegistrator registrator_ (HttpController.h:127-139). The constructor registers the method name + parameter pack into the framework — completed by CRT static init before main(), zero runtime scanning. Class-name-to-path mapping is auto-derived by DrClassMap::demangle(typeid(T).name()) (HttpBinder.h:235), :: becomes /.

3.2 Matching Structures

Paozhu: Core router class (router.h:32). At runtime, reg_raw populates _handlers / _urlpath_map / _site_to_slot (global slot 0; multi-tenant see §3.5). co_resolve(peer, known_idx) (router.h:79) coroutine-drives the entire match + pre + handler chain, with route_exact_checked optimization (httppeer.h:298-299, RPC/sync chains skip redundant exact lookup).

  • If exact match fails, prefix fallback up to 6 segments (router.cpp two-level lookup: lookup_exact → lookup_registered → lookup_key_in_slots, router.cpp:180-185). Unregistered hop names are skipped during chain draining (router.cpp:350-363).

Drogon: HttpControllersRouter + StaticFileRouter. Three structures (HttpControllersRouter.cc):

  • simpleCtrlMap_: no-parameter exact match (lowercase-keyed std::unordered_map).
  • ctrlMap_: parameterized but structurally fixed exact routes. ctrlMap_.find(loweredPath) directly hash-hits (HttpControllersRouter.cc:626).
  • ctrlVector_: routes with :param / regex. At compile time {param} placeholders are replaced with ([^/]*) via regex_replace (:564). At runtime, std::regex_match does linear matching (:635-640).
  • Each route has binders_[req->method()] buckets by HttpMethod; initMiddlewaresAndCorsMethods auto-injects middlewares and opens OPTIONS/CORS (:58/63/75).

3.3 Pre-handler Chain & Sync/Coroutine Mixing

Paozhu — Each route splits into 4 independent slots; sync and coroutine are "first-class routing citizens": reg_raw(site, path, pre_sync, co_pre, reg_sync, co_reg, mask_code) (common/autocontrolmethod.hpp) registers a route as sync-pre / coro-pre / sync-handler / coro-handler four separate entry points. The main driver co_resolve (router.cpp:694) transparently interleaves them: coroutine steps co_await in place (pre co_await h.co_pre(peer); handler co_await h.co_regfun(peer)); synchronous steps go to the business thread pool.

  • Sync/coroutine mixing is a built-in capability: Within one request, "sync-pre auth → coro-handler DB lookup" and "coro-pre → sync-handler" can be declared directly. The framework auto-dispatches based on each entry's pre_kind/reg_kind. Developers never need to manually switch threads or wrap in std::async. This is a different design philosophy from Drogon's "handler picks one form, CoroMapper is a separate type" — Paozhu treats "is this a coroutine" as a property of each registration slot, not the handler as a whole.
  • Built-in urlpath pre interception: Each route's pre_sync/co_pre chain up in declaration order into a serial pre chain; classify_step() decides direction based on return value — @ok (pass), same-name (continue), @exit (explicit stop), jump name (router.cpp:76-87). First non-empty return short-circuits; empty string is the only "pass" signal (router.cpp:458-461). Additionally, site-level pre/after hooks: run_site_hooks (sync :462) and co_run_site_hooks (coro :478) batch-run action_pre_lists/action_after_lists. When the list exceeds the limit, it truncates to the first site_hook_limit entries rather than dropping the whole thing (avoids silent auth failures).
  • Flow stack draining: When the orchestration stack drains (pop_flow_index), if the driver is a sync chain but the popped entry is a coroutine, draining stops (:364-368); if coroutine-driven, it co_awaits inline (:865-873).

Drogon: Pre-handler logic lives in Filters (HttpFilter + ADD_FILTER_TO / GlobalFilters.cc) and Middlewares (HttpMiddleware, MiddlewaresFunction.cc + HttpAppFramework.h:718). The framework executes them before handlers, ordered by path / global ordering, decoupled from the routing table, reusable, sortable. The sync/async choice lives on the individual method form (binder's Blocking/Callback/future triad, or coroutines via separate CoroMapper). There is no slot-based mixed declaration like "one route declares a sync-pre + coro-handler together".

3.4 Simple Task Orchestration (Paozhu flow_method)

Conclusion: Yes, Paozhu has built-in simple task orchestration on httppeer, implemented via httppeer::flow_method for "sequential multi-handler orchestration within a single request".

  • Structure: httppeer holds a lazily-allocated stack std::unique_ptr<std::list<std::string>> flow_method (httppeer.h:300-301) — stores names of subsequent handlers to execute.
  • Push API (httppeer.cpp:2135-2155):
    • push_next(name): push_back (stack top, LIFO — last pushed runs first).
    • push_last(name): push_front (stack bottom, FIFO — first pushed runs first, the default recommended for sequential breakdowns).
    • push_steps({...}): batch-push.
  • Pop/Consume (httppeer.cpp:2156-2169 pop_flow() pops back; router.cpp:340-368 pop_flow_index): After a handler completes normally (returns empty string), the router pops the next registered handler name from the stack and executes it. One handler pops exactly one; the rest wait for that handler to return empty before popping, until the stack empties or the chain hits the top (router.cpp:651-657 sync chain, 834-839 coro chain).
  • Flow control directives: kFlowOk / kFlowExit (explicit stop, no pop) / kFlowTimeloop (transfer to event loop), interpreted by classify_step (router.cpp:76-87).
  • Robustness: When popping an unregistered name, skip and continue to the next (don't swallow the whole chain, :350-363); a coroutine entry pushed onto a sync chain stops by design (:364-368).

This means one request can do "handler A → push B, C, D → after A returns empty, run B→C→D in order", forming a lightweight sequential workflow / pipeline. Drogon has no equivalent built-in mechanism: its composition primitives are Filters/Middlewares (cross-cutting concerns, not sequential step orchestration) and handler-internal logic. To chain multiple handlers in Drogon, you'd manually call or redirect inside the handler — the framework layer provides no orchestration stack.

3.5 Multi-Tenant / Site Slot

Paozhu: Routes naturally attach to site slots — host_index → slot, _site_to_slot maintains one slot per site. Route tables are isolated by slot (router.cpp:337 find_name_in_slots(peer_slot(peer), ...)); the first argument of reg_raw is site (domain, empty string = global slot 0). Combined with theme views (§9), this is framework-level multi-tenancy. Drogon: Routes themselves carry no tenant concept. Multi-tenancy is achieved at the business layer via "multiple apps / multiple controller groups + DrObject naming" — no one-stop slot isolation.

4. ORM Deep Dive

Both support MySQL / PostgreSQL / SQLite and their ORM queries support C++20 coroutine async. But they differ significantly in generation timing, code organization, query style, caching, transactions, and relationship expression.

4.1 Generated Code Structure

Paozhu (paozhu_cli orm <dbtag>, generator vendor/httpcli/modelfun.hpp) produces three layers per table:

  • <table>_base.h: pure data/reflection layer — namespace <table>_info contains col_count, enum cols, struct meta (field definitions), type:: type aliases, col_names, null_col bitmap, assign_field_value (world_base.h:41-45, L76-80), plus dirty-field bitmap __dirty_bits + get_dirty_indices()/clear_dirty()/make_update_dirty_sql().
  • <table>_opsql.h: template<M_MODEL,B_BASE> class <table>_opsql : public B_BASE containing all query/cache/dirty-update methods. Constructor fetches orm_conn_pool from get_orm_conn_pool_obj() per dbtag.
    • Dirty-update mechanism: setXxx() marks the corresponding dirty bit when writing a field. update_dirty() (text protocol) / exec_update_dirty() (prepared) / async_update_dirty() / async_exec_update_dirty() / commit_update_dirty() only build UPDATE for dirty-bit fields. On success clear_dirty(). Short-circuits when the dirty set is empty (prevents accidental all-field updates) and refuses execution without WHERE (article_opsql.h:9866/15248/10319/15323/13120). Mechanistically equivalent to Drogon's dirtyFlag_[] — both are "incremental writes of changed columns only".
  • models/include/<Model>.h: thin shell class <Model> : public <table>_opsql<<Model>,<table>_base> (models/include/World.h:11).
  • FK relationships live in external .cpp: orm/fk_child_opsql.cpp, orm/fk_parent_opsql.cpp (see §4.6).

Drogon (drogon_ctl create_model, reuses CSP templates model_h.csp/model_cc.csp) generates one model class per table (example orm_lib/tests/mysql/Users.h):

  • struct Cols (column-name constants), table metadata (tableName/primaryKeyName/PrimaryKeyType: single PK = concrete type, composite = std::tuple, no PK = void).
  • Three pieces per field: getValueOfXxx() / getXxx() / setXxx() + setXxxToNull() (nullable).
  • JSON interop & validation: toJson() / updateByJson() / validateJsonForCreation/Update.
  • Private persistence friend methods: outputArgs / updateColumns / updateArgs / insertColumns, called internally by Mapper.
  • Dirty flag dirtyFlag_[]: determines insert/update writes only changed columns (Users.h:252-274).
  • Static SQL strings: sqlForFindingByPrimaryKey() / sqlForDeletingByPrimaryKey() / sqlForInserting(bool& needSelection) (dynamically builds column list from dirtyFlag_[]; PG appends returning *, MySQL/SQLite relies on LAST_INSERT_ID/insertId()).

Key difference: Paozhu separates "data definition (base)" from "SQL operations (opsql)" into two files and supports external FK .cpp; Drogon puts everything into one model class with private+friend persistence internals — more OOP.

4.2 Query API Style

Paozhu — Chained builder (returns M_MODEL&), method names lean toward "direct SQL verbs":

  • Read: count() / page() / fetch() / fetch_one() / fetch_to<T>() / fetch_one_to().
  • Write: update_col / exec_update_col / replace_col.
  • Conditions: where() / whereIn / whereNull / whereEQ / per-column shortcuts eqId(); condition operators orm::wq::eq/nq/bt/be/lt/le.
  • JOIN: leftJoin().
  • Async: async_fetch / async_count / async_page, plus exec_* variants with _prepared.
  • Pagination auto-reuses existing conditions: page() internally calls count() first. count() reads the already-set .where() filters from the model; subsequent fetch() also goes through the same build_text_where — COUNT and data queries share the same where, set conditions once. page() also directly returns the navigation 4-tuple (nav_min, nav_max, cur_page, total_page) — no manual pagination math.

Drogon — Streaming Mapper<T> + Criteria (template Mapper in orm/Mapper.h:115, constructor takes DbClientPtr):

  • Read: findByPrimaryKey / findAll / count / findOne / findBy, each in three forms (sync/callback/future).
  • Write: insert / update / updateBy / increment / deleteOne / deleteBy / deleteByPrimaryKey.
  • Condition Criteria (Criteria.h:73): CompareOperator has EQ/NE/GT/GE/LT/LE/Like/In/IsNull/IsNotNull; supports operator&&/|| composition, CustomSql + _sql literals, Criteria(Json::Value).
  • Streaming builder: limit / offset / orderBy / paginate / forUpdate / innerJoin / leftJoin / rightJoin; placeholder $? is DB-aware and replaced with $1,.. (PG) or ? (MySQL/SQLite).

Style divergence: Paozhu leans toward "familiar chained verbs + per-column shortcuts" — low learning curve. Drogon uses Criteria expression objects + Mapper streaming — more type-safe, but needs understanding the Criteria/SqlBinder system. Pagination comparison: Paozhu's page() auto-reuses already-set where, completes "count + fetch + return navigation 4-tuple" in one call. Drogon's paginate(page,perPage) (Mapper.h:173/2013) only sets offset/limit; count() defaults to empty Criteria() (Mapper.h:459), so you need to pass the same Criteria to both count(criteria) and the query. Pagination navigation (total pages / window) you compute yourself.

4.3 Query-Result Caching (Largest Functional Gap)

4.4 Async & Coroutine Model

Paozhu — Sync + coroutine dual form; coroutine is the primary paradigm:

  • Every query method has both sync and coroutine forms: sync fetch() / count() / page() / exec_fetch() / exec_count(); coro async_fetch() / async_count() / async_page() / async_exec_fetch().
  • Coro versions internally co_await select_conn->async_fetch_directly(...); DML does co_await edit_conn->async_exec_dml.
  • Connection pool orm_conn_pool.cpp: coroutine async_get_mysql_select_conn / async_get_mysql_edit_conn uses co_await async_add_*_connect to fetch/build connections; sync get_mysql_*_conn.
  • Backends: pg_conn.cpp async_read_loop co_await; sqlite_conn.cpp goes through run_on_worker queue.
  • Business handler layer: reg_raw provides sync slots (reg_sync / pre_sync) and coro slots (co_reg / co_pre) simultaneously; co_resolve interleaves transparently — developers choose the form by function signature (see §3.3).

Drogon — Three forms (sync / callback / future) + coroutine overlay:

  • Every Mapper method provides three sets: binder << Mode::Blocking (sync, throws exception) / binder >> rcb >> ecb (callback) / std::promise + get_future (future).
  • Bottom layer DbClient::operator<<(sql) returns SqlBinder (DbClient.h:256) — << binds params, >> registers callbacks, exec() executes.
  • Coroutines: CoroMapper (CoroMapper.h:67, inherits Mapper<T>) returns MapperAwaiter, whose await_suspend plugs the callback into CallbackAwaiter and resume()s. Also has execSqlCoro, newTransactionCoro.
  • Result abstraction: Result (Result.h:57, reference-counted, polymorphic size()/affectedRows()/insertId() etc.) / Row (Row.h:46, operator[] returns Field).

4.4.1 Dual-Pool Concurrency Architecture (io_context Coroutine Pool + Dedicated ThreadPool)

Paozhu's execution layer runs two thread pools side by side, with concurrency split into three layers via "strand serialization + business-pool dispatch-back-to-strand + peer chained shared ownership". No GC needed, still safe:

  • Pool 1: Asio io_context coroutine pool (server.h:381, single io_context + runthreads). Runs all co_spawn coroutines — HTTP/1.1 · HTTP/2 · WS · MQTT · RPC.
  • Pool 2: Dedicated ThreadPool clientrunpool (server.h:487, initial size hardware_concurrency()*2+2, threadpool.h). Picks up sync/blocking tasks offloaded from the coroutine loop (router sync pre/regfun, timers, WS data messages). Supports dynamic resize (addthread/fixthread, cap 32) and 503 backpressure (force_reject_* → add_sync_task/add_conn_task returns false).
  • I/O layer: Each client_session (client_session.h:76, enable_shared_from_this) binds an asio::strand. Per-connection send/receive serialized, lock-free. Sends go through post_write (:81-91) into the per-connection send ring, written out serially by a consumer coroutine.
  • Business layer: Blocking code (router sync handlers, MQTT/socket sync hooks) is dispatched to clientrunpool via co_pool_run_step (pool_step.h:41). After fn() completes in the pool thread, finish uses asio::dispatch to put the continuation back onto the session strand — business threads only run fn(), response sending always lands on the strand (pool_step.cpp:18-20).
  • Lifecycle / deadlock prevention: peer is a first-class parameter throughout "task closure → finish → wake-up op → strand resume", each carrying one strong reference sequentially (pool_step.cpp:91-117). Release point is fixed on the strand thread, send threads never get freed objects. When the pool can't accept work, it doesn't drop tasks but completes the awaitable in-place with rejected=true (pool_step.cpp:79-86), eliminating permanent coroutine hangs.

Drogon comparison: Drogon uses "multiple independent EventLoop" (one EventLoop per worker, MPSC cross-thread, epoll/kqueue). Handlers run on the owning ioLoop; heavy blocking needs manual offload. It doesn't have Paozhu's "shared io_context + independent generic ThreadPool + strand closed loop" cross-pool model, so it also avoids the cross-pool object ownership question.

4.5 Transactions

Paozhu transactions have two layers of API, both with real examples in business code (controller/src/test_sql_commit.cpp):

① Native SQL layer (orm::db_conn directly holds the transaction connection):

auto ulink = std::make_unique<orm::db_conn>("cms");
ulink->begin_commit();                 // BEGIN / BEGIN IMMEDIATE
ulink->edit_query("UPDATE sysuser set ...");
ulink->edit_query("INSERT INTO sysuser ...");
// Queries also go through the same write connection (reads what we just wrote, no master-replica replication lag)
orm::cms::LocalusersqlStruct row;
ulink->edit_query("SELECT * FROM sysuser WHERE ...", row);
if (ulink->iserror) ulink->rollback();
else                ulink->commit();
  • A single db_conn instance holds one mysql_edit_conn. Inside a transaction, both reads and writes go through this one write connection — edit_query(sql) writes, edit_query(sql, struct&) reads (second param is the output). This guarantees intra-transaction read consistency, no master-replica replication lag.
  • Coroutine form: async_begin_commit() / async_commit() / async_rollback() / async_edit_query().
  • Cross-object: Native SQL has no model concept — naturally cross-table / cross-object.

② ORM layer (lock_conn binds the transaction connection to the model):

auto txnlink = std::make_unique<orm::db_conn>("cms");
txnlink->begin_commit();

// Multiple different model objects all lock onto the same transaction connection — cross-object transaction
orm::cms::Sysuser user_m;
user_m.lock_conn(txnlink->mysql_edit_conn);
user_m.where("adminid", 10000);
user_m.update("nickname");

orm::cms::Sysroles role_m;              // Different table, different model class
role_m.lock_conn(txnlink->mysql_edit_conn);  // Also locks onto the same one
role_m.where("roleid", 50);
role_m.update("remark");

user_m.unlock_conn();
role_m.unlock_conn();
txnlink->commit();                      // Unified commit or rollback
  • Models fetch their own connections from the pool (read-write separated). Running ORM operations directly inside a db_conn transaction would land on another auto-committed session — lock_conn() binds the model onto the write connection opened by db_conn, so all models' reads and writes inside the transaction go through the same one.
  • Cross-object: Multiple different model objects (different tables, different generated opsql classes) can all lock_conn onto the same db_conn's write connection, forming a cross-table transaction.
  • unlock_conn() only unbinds, does not return to pool (prevents uncommitted session leaks). The final commit()/rollback() on db_conn unifies the return.

Drogon — First-class Transaction object:

  • Transaction inherits DbClient; Mapper<T>(transactionPtr) makes subsequent reads and writes happen on the same transaction connection.
  • newTransaction / newTransactionAsync / newTransactionCoro. TransactionImpl borrows a single connection from readyConnections_ and moves it to busyConnections_, auto-sends BEGIN / BEGIN IMMEDIATE / BEGIN EXCLUSIVE; after commit/rollback, returns via usedUpCallback.
  • Supports isolation level selection: TransactionType::{Deferred, Immediate, Exclusive}.

Comparison: Drogon uses a first-class Transaction object passed to Mapper — API is clean, models don't know they're inside a transaction. Paozhu is explicit and manual — either use db_conn for native SQL, or lock_conn to bind ORM models to the transaction connection (models need to be aware of transaction state). Both work, but Drogon is more elegant.

4.6 Relationships / Foreign Keys

Paozhu: oneXXX/manyXXX live in external .cpp (orm/fk_child_opsql.cpp / orm/fk_parent_opsql.cpp), implemented by applying where()/whereIn() to the related model using this table's FK values. Also provides generic leftJoin() for explicit JOINs.

Drogon: Relationships are "generation-time config + per-model methods at runtime", no generic Mapper API for hasMany/hasOne style.

  • Config structure Relationship (create_model.h:211, Type{HasOne,HasMany,ManyToMany} + PivotTable for many-to-many join tables).
  • Auto FK detection: tryAddAutoRelationship (create_model.cc:181); PG queries information_schema FK views, MySQL queries KEY_COLUMN_USAGE, SQLite queries PRAGMA foreign_key_list.
  • Generates method bodies (model_cc.csp:1580-1789): per-type generates getXxx(clientPtr) sync/async pairs — HasOne builds select * from <target> where <key> = ?, HasMany returns vector<Target>, ManyToMany does join + pivot returning vector<pair<Target,Pivot>>. Relationship queries go through DbClient/SqlBinder, can take a transaction client.

4.7 Type Mapping & Parameter Binding

Paozhu: At generation time, modelfun.hpp uses pg_type_to_mysql_type() + SQLite affinity mapping to convert SQL types to MySQL binary type codes, then get_field_type() maps codes to C++ (integers/dates/strings etc.), landing in the struct meta + type:: of _base.h.

Drogon: At generation time, create_model.cc writes per-DB hardcoded mappings (PG / MySQL / SQLite branches). Parameter binding SqlBinder::operator<< branches on ClientType:

  • PG: 2/4/8-byte integers go through htons/htonl/htonll for network order, format=1 (binary);
  • MySQL: uses getMysqlType<ParaType>() mapping (with static_assert rejecting unsupported types);
  • SQLite: picks type based on sizeof(T); also supports trantor::Date / vector<char> / optional<T> / Json::Value.
  • DB row → C++ field: Field::as<T>() (Field.h:70-107, extensive specializations) + model constructor T(const Row&, indexOffset), does special parsing for date/bytea, and controls incremental column writes based on dirtyFlag_[].

4.8 Connection Pools

Paozhu: orm_conn_pool.cpp maintains a read-write separated pool per dbtag (async_get_mysql_select_conn for reads / async_get_mysql_edit_conn for writes); coroutine connection fetch/build via co_await async_add_*_connect; backends pg_conn/mysql_conn/sqlite_conn each implement async_* non-blocking I/O; started by init_orm_conn_pool(io_context,...) (server.cpp:9269).

  • Framework-level connection health check orm_connect_mar_t (orm_connect_mar.h/cpp): When borrowing, watch_mysql_connect(conn) registers a weak_ptr + time_begin. The server main loop calls clear_connect() every 320 ticks — automatically prunes weak_ptr that have expired, skips async connections, and hard-closes (hard_close()) sync connections exceeding CONST_ORM_QUERY_CONNECT_TIMEOUT. Rate-limit: max 10 connections per scan round, scan over multiple rounds, sleeps 200ns between rounds to yield CPU.
  • ORM query logging: In debug mode, push_log(sql_string, duration_ms) records slow queries; save_log() flushes to disk every CONST_ORM_QUERY_LOG_TIME ticks.

Drogon: DbClientLockFree (orm_lib/src/DbClientLockFree.cc) with three-state collections connections_/readyConnections_/busyConnections_ (mutex-protected). execSql reuses an idle one if available, otherwise pushes into sqlCmdBuffer_ (max 20000; exceeding it reports "Too many queries in buffer", DbClientLockFree.cc:203). Number of event loops decided by connNum (SQLite fixed at 1, PG/MySQL take min(hardware_concurrency(), connNum)). Per-library connection classes PgConnection/MysqlConnection/Sqlite3Connection only handle single-connection non-blocking I/O; supports execSqlWithTimeout which throws TimeoutError on timeout.

Underlying protocol implementation divergence (architecture-level):

  • Paozhu self-implements MySQL / PostgreSQL wire protocols; SQLite uses the official library:
    • MySQL: mysql_conn.cpp hand-written read_server_hello (parses capability_flags, auth_plugin_salt_data), caching_sha2_password auth handshake, mysqlnd_xor_string encryption, seq_next_id packet sequence number.
    • PostgreSQL: pg_conn.cpp hand-written build_startup_message, SCRAM-SHA-256 handshake (sasl_scram_sha256, int32_to_buf message frames).
    • SQLite: sqlite_conn.cpp / sqlite_conn.h (L45) directly uses the official sqlite3 C API (sqlite3_open/sqlite3_prepare_v2/sqlite3_step/sqlite3_stmt*), guarded by #ifdef ENABLE_SQLITE, CMake find_package(SQLite3 REQUIRED) linking. SQLite is an embedded database with no wire protocol of its own to self-implement.
    • The entire project CMakeLists.txt does not link libmysqlclient / libpq (the cost of self-implementing MySQL/PG wire protocols), but SQLite needs SQLite::SQLite3.
  • Drogon wraps all official client libraries: MysqlConnection directly #include <mysql.h> (links unofficial::libmariadb); PgConnection uses libpq (find_package(pg)); SQLite uses SQLite3_lib. Wire protocols are delegated entirely to third-party libraries; Drogon only provides async wrappers (based on non-blocking APIs like mysql_real_connect_start/cont).

4.9 Business Code Style (Actual Usage)

§4.2 covered API shapes. Here's what real business code looks like (examples taken from both sides' source).

Paozhu — The model object IS the query builder; chained verbs + coro/sync dual form (example controller/src/testormcache.cpp / testcrud.cpp):

// The model object itself is the builder; conditions, caching, and query all chained in one go

co_await art.fetch_one();                          // Coroutine query, result backfills art

if (art.is_hit_cache()) { /* cache hit branch */ }

// Pagination: directly returns (nav_min, nav_max, cur_page, total_page)

Style takeaway: get a model instance → chain .where()/.whereEQ()/.use_cache()/.fetch_one()/.page() on it → co_await or sync fetch_one(). No separate Mapper layer — the model IS the DAO.

Drogon — Generic Mapper<T> + Criteria expression; CRUD by model type (example orm_lib/tests/db_test.cc):

using namespace drogon_model::postgres;
Mapper<Users> mapper(clientPtr);          // clientPtr = app().getDbClient()
Users user;
user.setUserId("pg"); user.setUserName("alice");
mapper.insert(user);                      // Sync write

// Coroutine form
CoroMapper<Users> cmapper(clientPtr);
auto cu  = co_await cmapper.findByPrimaryKey(2);
auto us  = co_await cmapper.orderBy(Users::Cols::_user_id).limit(2).findAll();
auto one = co_await cmapper.findOne(
    Criteria(Users::Cols::_id, CompareOperator::EQ, 1));

Style takeaway: Mapper<Model> is a generic CRUD facade independent of the model object. Conditions use Criteria(col, op, val) expression construction. The model object only carries data + setter/getter; all persistence goes through Mapper.

One-liner: Paozhu is "the model queries itself" (builder attached to the model, verb-style, quick to pick up). Drogon is "Mapper proxies model CRUD" (generic facade + Criteria expressions, type-safe, cleaner separation of concerns).

5. Rate Limiting Comparison

Both have rate limiting at different layers, with some overlap: Drogon has both hard connection caps (HttpConnectionLimit, global + per-IP hard caps) and request-level (per-IP / per-user / per-route, token bucket/sliding window/fixed window, plugin-ready out of the box). Paozhu has connection-admission-level overload protection (60-second connection window + load-adaptive admission rate + queued slow admission) + site upload limits + IP blocking. They approach connection-level protection differently (hard reject vs. queued admission); request-level quotas are Drogon's unique business capability.

5.1 Drogon — Request-Level RateLimiter + Hodor Plugin

Core class (lib/inc/drogon/RateLimiter.h):

  • RateLimiterType three algorithms: kFixedWindow / kSlidingWindow / kTokenBucket (RateLimiter.h:10-15).
  • Factory RateLimiter::newRateLimiter(type, capacity, timeUnit=60s) (RateLimiter.h:42-45), interface isAllowed()→bool (:52); SafeRateLimiter wraps with mutex for thread safety (:56-74).
  • Three implementations: TokenBucketRateLimiter / SlidingWindowRateLimiter / FixedWindowRateLimiter (lib/src/ .cc/.h files).

Hodor plugin (lib/inc/drogon/plugins/Hodor.h, official Drogon rate-limiting plugin):

  • JSON config to enable. Intercepts via AOP onHttpRequest (Hodor.h:144) AdviceCallback pre-advice. On limit hit returns rejection_message (default "Too many requests").
  • Complete dimension support (Hodor.h:36-77): algorithm (default token_bucket), urls regex (empty = all), time_unit, capacity (global), ip_capacity (per-IP), user_capacity (per-user, configurable setUserIdGetter), sub_limits (per-URL group sub-policies), trust_ips / use_real_ip_resolver (XFF / real IP), limiter_expire_time (default 600s, uses CacheMap storing limiter per IP/user).

Drogon's request-level rate limiting is production-grade, fine-grained, and declarative: configure one JSON block to get "global 1000/s + per-IP 100/s + per-user 50/s" combo policies matching URLs like /api/.*, with swappable algorithms.

Hard connection cap (lib/src/HttpConnectionLimit.h:26, atomic counting at accept stage):

  • HttpConnectionLimit::setMaxConnectionNum(num) — global hard connection cap; setMaxConnectionNumPerIP(num) — per-IP hard connection cap.
  • HttpServer.cc:L121 calls tryAddConnection() at accept time; over-limit rejects immediately; releaseConnection() atomically decrements on connection close.
  • Property: hard-reject — over-limit immediately closes new connections, no queue, no wait. Different approach from Paozhu §5.2's "queued slow admission" for the same problem.

5.2 Paozhu — Connection-Admission Overload Protection + Upload Limits + IP Blocking

Connection admission throttling (built into httpserver core, server.h:247 ratelimiter() thread-driven):

  • 60-second traffic window: update_minute_count() (server.cpp:8583-8632) — each accept thread holds one 60-bucket thread-local ring, snapshots global total_count (connection counter), computes "connections entering in the last ~60 seconds".
  • Load-adaptive admission rate: compute_rate_from_load(has_save_link_count) (server.cpp:8636-8647) — maps active connection count to [lo,hi] interval as percentage, then linearly converts to admission rate [num1,num2]; thresholds controlled by rate_limit_new_wait_num / rate_limit_accept_wait_num / rate_limit_second_num1 / rate_limit_second_num2.
  • Queued slow admission: When thresholds exceeded (has_save_link_count > rate_limit_new_wait_num && live_link_count > rate_limit_new_wait_num, server.cpp:9014-9022 / 9197-9204), calls enqueue_rate_limited() (:8650) to push connections into socket_session_wait_rate. The throttling thread wakes up on rate_limit_condition and admits them gradually at rate_limit_second_time_num per second (:8749-8758 slot loop).
  • Property: per-connection (not per-request) total-cap gate — overload-smoothing admission of new connections, not "N requests per IP/user per second" quota.

Upload limits: httppeer::check_upload_limit() (httppeer.cpp:789, guarded by site-level host_index) — limits upload body size per site.

IP blocking: check_blockip(peer_session) (server.cpp:5757, TLS handshake failed connections excluded from traffic counts), blacklist/whitelist access-layer interception.

Paozhu has no built-in "per-IP / per-user / per-route request quota" layer, but can be implemented with framework capabilities: add an IP sliding-window counter (maintaining std::unordered_map<ip, deque<timestamp>>) inside router's site pre hooks (action_pre_lists, router.cpp:462), and on limit hit return httppeer::kFlowExit (@exit) to reject the request — the pre chain short-circuits on the first non-empty return. The whole implementation closes within the framework, no core extension needed.

6. Protocol & Middleware Support (WebSocket / MQTT / Redis / RPC / Socket)

This dimension diverges sharply: Paozhu builds all five protocol types natively into httpserver core (and uses a unified subpub registration model across ws/mqtt/socket); Drogon only builds WebSocket and Redis natively, with no framework-level support for MQTT / RPC / raw Socket servers.

6.1 WebSocket

  • Paozhu (built-in server + client): websockets.h + ws_conn.cpp (connection) / ws_handshake.cpp (handshake) / ws_parser.cpp + ws_wire.h (frame codec) / http_websocket_client.cpp (65KB client); websockets_callback.cpp + websockets.conf config; controller layer also provides websockets/loopwebsockets.hpp / loopwebsockets_co.hpp (coroutine loop) / wssleepwebsockets.hpp and other loop abstractions.
  • Drogon (built-in server + client): WebSocketController.h (server controller) / WebSocketConnection.h (connection) / WebSocketClient.h (client), with matching *Impl.cc files; tests/ has complete coro/keepalive/upgrade tests. Capabilities are equivalent.

6.2 Redis

  • Paozhu (built-in, vendor/pzredis/): Complete client redis_client.h + redis_conn.h (connection) + redis_pool.h (per-section multi-instance connection pool) + redis_pubsub.h/redis_subpub.h (publish-subscribe) + redis_reply.h (reply parsing) + redis_types.h; synchronous bare names / coroutine async_ prefix (redis_client.h:294-296 asio::awaitable), configured via redis.conf. Does not depend on hiredis — self-implemented RESP parsing.
  • Drogon (built-in, nosql_lib/redis/): RedisClient + RedisConnection + RedisSubscriber + RedisTransaction + RedisClientManager; uses hiredis underneath (cmake_modules/FindHiredis.cmake). Capability matches Paozhu, but leans on a third-party library.

6.3 MQTT

  • Paozhu (built-in broker + client, complete implementation): mqtt_broker.h is a singleton broker (mqtt_broker::instance()), containing subscription tables subscribe()/unsubscribe()/unsubscribe_all, retained messages, topic filter matching, publish() delivery, prune_expired() expiry cleanup, plus a global cap kMaxSubscriptionsTotal=100000 (:84-198); mqtt_session.cpp + mqtt_frame.cpp (35KB, MQTT frame codec including MQTT5's No Local / Retain As Published / Retain Handling / shared subscriptions group+device); http_mqtt_client.cpp client + mqtt.conf, controllers mqtt/echo_mqtt_client.hpp / my_test_mqtt.hpp. Ready-to-use MQTT service.
  • Drogon (absent): The entire drogon-master repository contains zero MQTT source files. The framework ships neither a broker nor a client; you'll need a third-party plugin (e.g. the community drogon-mqtt) or build one on top of WebSocket/TCP yourself.

6.4 RPC

  • Paozhu (built-in custom RPC protocol): rpc_parse.h / rpc_parse.cpp parses a custom rpc wire format (request line + KV headers + binary body, with CONST_RPC_* size limits). http_rpcclient.cpp (73KB) handles client-side and connection logic, dispatches by its own routing. Controller test_rpc_handle.cpp demonstrates handlers. Provides RPC semantics on the same connection layer.
  • Drogon (not built-in): The only match for rpc in lib/ is a Windows-specific #include <rpc.h> (Utilities.cc:24, unrelated to any RPC framework). No protobuf / thrift / gRPC wrappers exist. RPC has to be built on top yourself — for instance JSON-over-custom-controllers, or an external gRPC process.

6.5 Raw Socket / TCP Server

  • Paozhu (built-in): http_socket.h + http_socket_client.cpp provides raw TCP connection support; sock_subpub_reg.h/.cpp + sock_subpub_client.h plugs sockets into the unified subpub registration/subscription model, configured via sockets_config.cpp. The framework can act as HTTP/WS/MQTT/Socket multi-protocol server simultaneously.
  • Drogon (absent): HttpAppFramework only exposes addListener() for HTTP listeners (:864). There is no createTcpServer, UdpServer, or any raw socket server API. If you need raw TCP, you'd build directly on trantor's TcpServer or self-managed Asio — the framework won't do protocol dispatch for you.

6.6 Architecture Theme: Unified subpub Registration Model

Paozhu uses *_subpub_reg across ws/mqtt/socket (ws_subpub_reg / mqtt_subpub_reg / sock_subpub_reg) — the same "subscription registration + publish dispatch" kernel spans multiple protocols. Redis also goes through redis_subpub. This is the unified abstraction behind Paozhu's "protocol big family". Drogon's capabilities are independent of each other (WebSocket controller, Redis nosql lib, no MQTT/socket), with no framework-level cross-protocol unified pub/sub kernel. However, the business layer has a PubSubService<MessageType> template class (lib/inc/drogon/PubSubService.h) — it provides named topics + subscribe/publish/unsubscribe, uses shared_mutex + copy-on-write, and is an in-process tool for business code, not a protocol dispatch mechanism inside the framework.

6.7 JWT & OAuth 2.0 / OIDC

  • Paozhu (built-in JWT + complete OAuth 2.0 / OIDC server + client):
    • JWT: jwt.cpp / jwt.h is a complete self-implementation depending on OpenSSL 3; supports HS256, RS256/RS384/RS512 (PKCS1 + PSS), ES256 (:523 es256_verify), includes alg:none protection (signature segment can be empty but has a clear error state), strict scan of exp/iat/nbf claims, full token length bound CONST_JWT_TOKEN_MAX_LEN, separates decode_without_verify and verify (unverified tokens are never treated as valid) — security-oriented self-implementation.
    • OAuth 2.0 / OIDC authorization server: libs/oauth/oauth_store.cpp (35KB, auth code / token / refresh storage) + full endpoints in controller/src/oauth/: oauth_authorize / oauth_token / oauth_introspect / oauth_jwks / oauth_userinfo / oauth_revoke / oauth_metadata / oauth_purge; paired with conf/oauth.conf + RSA key pairs; schema/cms/tables/oauth_*.sql generates OauthClient / OauthCode / OauthRefresh ORM models. Ready-to-use authorization server.
    • OAuth client + third-party integration: libs/oauth_client/oauth_client.cpp + controller/src/oauth_client/oauth_client_demo.cpp; libs/github/github_oauth.cpp has GitHub OAuth login built in.
  • Drogon (not built-in): The entire drogon-master repository contains no JWT or OAuth implementation files (lib/ only has incidental Bearer header mentions in HttpResponse.h and HttpHeaderTest.cc, not a real implementation). For JWT you'll need a third-party library (e.g. jwt-cpp) or a community plugin; an OAuth 2.0 server/client has to be built yourself or wired to an external service (there is a community drogon-oauth among others).

6.8 Session Management

  • Paozhu (built-in, weak-typed): httppeer directly holds http::obj_val session (httppeer.h:228) — the same JSON micro-object, naturally nested, weak-typed. Lifecycle methods parse_session()/save_session()/clear_session()/get_session_id(). Two persistence modes — file storage save_session_file/parse_session_file + memory storage save_session_memory/parse_session_memory. Automatic SameSite handling — session_samesite(): when the site has cors_credentials configured and the current request is HTTPS, auto-sets "None"; otherwise empty string (attribute omitted).
  • Drogon (built-in, strong-typed): Session class (lib/inc/drogon/Session.h, map<string, std::any> + mutex) with lifecycle managed by framework-level SessionManager, configurable timeouts. any + any_cast<T> strong-typed access — safer than Paozhu's obj_val but heavier. 6.9 HTTP Client

  • Paozhu (built-in, full-coroutine style): httpclient + http_websocket_client.h client, sync and coroutine (asio::awaitable) dual form — co_await httpclient(peer, "GET https://...") directly returns the response. Supports add_client_task_loop for client_context to manage lifecycle. Example controller/src/testcowaitclient.cpp demonstrates coroutine HTTP client. No HTTP/1.1 pipeline client — but HTTP/2 multiplexing interlaces requests and responses on a single connection, equivalent and more thorough (head-of-line blocking solved natively). Paozhu also supports h2c (plaintext HTTP/2), so internal microservice calls and proxy forwarding get the same multiplexing benefit without any TLS negotiation overhead. Most modern scenarios negotiate HTTP/2 and don't need pipeline.
  • Drogon (built-in, four forms + HTTP/1.1 pipeline client): HttpClient.h + HttpClientImpl.cc, sync/callback/future three forms + coroutine Task overlay. Exclusive HTTP/1.1 pipeline client — setPipeliningDepth() batch sends on a single HTTP/1.1 connection, pipeliningCallbacks_ queue calls back in order (HttpClientImpl.h:62/185). Complete tests in examples/client_example/ and tests/integration_test/client/. This capability only works on HTTP/1.1 connections; TCP head-of-line blocking remains.

  • Paozhu (base built-in + business-layer extensibility): Core framework provides basic self-check capability: controller/src/serverwatch.cpp registers a paozhu_status route (returns version, current online connection count total_count, coroutine pool clientrunpool thread status); frametasks_timeloop is the framework-level interval task registration point (router triggers it periodically by run_timeloop chain name). 10.1 Wrap-Up: Zero-Third-Party Built-in "Big Family" (Paozhu Engineering Mainline)

Consolidating all self-built points from previous sections into one statement: Paozhu has extremely thin mandatory external dependencies (only Asio + OpenSSL 3). On top of that, almost the entire stack is self-built — the only exception is SQLite (embedded DB, no independent wire protocol to self-implement, uses official sqlite3 C API, linked when ENABLE_SQLITE=ON). Drogon's core is also thin (trantor + OpenSSL/Botan), but capabilities are assembled from an ecosystem.

Paozhu self-built coverage (no corresponding third-party lib pulled in)

  • Transport/app protocols: HTTP/1.1, HTTP/2 (HPACK/ALPN/h2c), WebSocket, MQTT (incl. broker), Redis client, RPC, raw Socket — wire protocol/frame codecs all hand-written; no libwebsockets / mosquitto / hiredis / self-built RPC frameworks.
  • DB wire protocols: MySQL (caching_sha2_password handshake) + PostgreSQL (SCRAM-SHA-256 handshake) fully self-implemented, do not link libmysqlclient/libpq (SQLite using official sqlite3 C API is the natural choice for an embedded DB with no wire protocol to self-implement).
  • Identity/security: JWT (jwt.cpp, HS256/RS256/ES256, OpenSSL3, security-oriented self-implementation) + OAuth 2.0/OIDC authorization server (libs/oauth + full endpoints in controller/src/oauth + GitHub integration) built-in and self-implemented — self-host SSO without Keycloak/Auth0 external IdP (§6.7).
  • ORM generation dual mode: live DB introspection (vendor/httpcli/modelfun.hpp runs SHOW CREATE TABLE / PG table list, database-first) + offline read schema/*.sql, the latter decoupled from runtime DB, CI-friendly (§4.1/§7.2).
  • Certificate automation: built-in ACME client + OCSP stapling (acme_client.cpp/acme_run.cpp/ocsp_check.cpp), no certbot etc. external tools needed.
  • Rate limiting: connection-admission overload protection self-implemented (§5), not a plugin.
  • Unified abstraction: ws/mqtt/socket/redis share subpub registration kernel (§6.6), the thread connecting this big family together.

Drogon comparison (thin core + ecosystem assembly)

  • Redis uses hiredis, DB drivers wrap libmysqlclient/libpq/sqlite3, rate limiting is the Hodor plugin, ACME depends on external tooling — and MQTT broker, RPC framework, raw Socket server are all absent.
  • Tradeoff: focus on HTTP web framework, push "protocol big family" to ecosystem / external libraries, in exchange for maturity, documentation completeness, and pluggable TLS (Botan/OpenSSL).

Costs and benefits come from the same source: Paozhu's "self-built big family" brings simpler deployment (fewer external libs to install), capability consistency, zero protocol authorization/version entanglement — but enormous code size, self-implemented correctness risk, and a small ecosystem/community (see §11). Drogon takes "HTTP depth + easy assembly" as its engineering mainline.

11. Design Tradeoffs Summary

Paozhu strengths

  • Exclusive Asio third-party ecosystem: bottom layer uses standalone Asio with asio::io_context exposed at the bottom. Any Asio library (asio-grpc, boost::beast, async_mqtt, boost::redis, quiche/nghttp2_asio, etc.) can be dropped in directly, with co_spawn/co_await ready to use immediately. Drogon is completely unusable (trantor EventLoop is a muduo-branch self-build, not asio::io_context).
  • Zero-third-party built-in big family: HTTP/2 + MySQL/PG/SQLite wire protocols + MQTT(broker) + WebSocket + Redis(self-implemented RESP) + RPC + raw Socket + JWT + OAuth 2.0/OIDC authorization server + ACME/OCSP + webpay(payments) + webpdf/pzexcel/pzword/pzimage/pzcharts(document processing) — all self-built, only mandatory deps are Asio + OpenSSL; unified subpub kernel spanning multiple protocols. Simple deployment, no protocol library version entanglement.
  • Four resident outbound clients (Redis subscription / WS / raw TCP / MQTT), spun up on framework boot, lifecycle managed by client_context, naturally enabling cross-process reporting / subscription.
  • Framework-level self-protection: accept independent thread + handler-layer naturally isolated deadlock detection (two-counter equilibrium, within 15 seconds finds and actively exits, covers all deadlock scenarios — faster than systemd WatchdogSec=30s) + watchdog thread exit std::terminate + ORM connection health check (orm_connect_mar_t).
  • Full-stack C++20 coroutine unified mental model + HTTP/2 built-in + multi-tenant/theme views + ORM dual-mode generation (live DB introspection / offline SQL) + build-time auto codegen force-refreshing routes.

Paozhu costs

  • Dual thread-pool architecture (io_context coroutine pool + clientrunpool business thread pool), massive dialect ORM headers (~450KB/dialect), enormous code size and maintenance surface.
  • Framework's own community scale, documentation completeness, and framework-exclusive plugin count are far smaller than Drogon (but Asio third-party library ecosystem is exclusive, not constrained by this).
  • Everything self-built (HTTP/1.1/HTTP/2/HPACK/routing/DB wire protocols), correctness must be borne alone.

Drogon strengths

  • Mature industrial-grade reactor model (multiple independent EventLoops, MPSC cross-thread, epoll/kqueue).
  • Reflection macro registration + compile-time static self-registration, zero runtime scanning, auto-derived registration paths.
  • Exclusive HTTP enhancements: RequestStream streaming request body, reverse proxy forward(), PostgreSQL LISTEN/NOTIFY (DbListener), plugin system (AOP Advice + dependency topological sort), static-file pre-compression lookup, HTTP/1.1 pipeline and its client counterpart (HTTP/1.1 only; TCP head-of-line blocking remains — HTTP/2 multiplexing + h2c solves this completely).
  • Prometheus monitoring complete built-in (Collector/Counter/Histogram + PromExporter plugin, JSON config to enable).
  • Rich ecosystem (CSP templates, nosql, plugin, filter, ORM three dialects, complete examples), active community, thorough documentation.

Drogon costs (measured in drogon-master)

  • No HTTP/2 server implementation (lib/ 1.9.14: HttpServer.cc only outputs HTTP/1.1, no Http2Server/ALPN registration).
  • No Asio ecosystem compatibility: EventLoop self-built, not asio::io_context. All Asio third-party libraries (asio-grpc, boost::beast, async_mqtt, etc.) cannot directly connect.
  • No framework-level big family: MQTT broker, RPC, raw Socket server, JWT, OAuth, ACME/OCSP, webpay, document processing, resident outbound clients — none built-in, all require self-extension.
  • No framework-level self-protection: no deadlock detection, no watchdog thread exit terminate, no active stall-exit mechanism — process crashes/stalls can only rely on systemd WatchdogSec= / Docker health check passive timeout kill+restart.
  • No framework-level connection health check (ORM zombie cleanup relies on DB server wait_timeout).
  • Handlers default to running on the ioLoop thread; heavy business logic needs manual offload; ORM generation depends on live DB, offline/CI requires spinning up a DB.
