Paozhu (Firecracker) – Présentation du framework Web

Paozhu est un framework Web écrit en C++. Code source : https://github.com/hggq/paozhu. Ce qui frappe d'abord, c'est qu'un seul exécutable contient tout : HTTP/1.1, HTTP/2, WebSocket, TCP brut, un client MQTT, un client Redis, un ORM, les vues template et la diffusion de fichiers statiques vivent dans le même processus, et les éléments inutiles sont éliminés par des options de compilation.

Voici l'exemple le plus court : le gestionnaire renvoie une tâche coroutine, l'affectation à peer->output constitue le corps de la réponse, et la route est déclarée par le commentaire situé au-dessus de la fonction :

Une fois le serveur lancé, ouvrez http://localhost/hello dans un navigateur.

#include "httppeer.h"
#include "testhello.h"
namespace http
{
//@urlpath(null,hello)
asio::awaitable<std::string> testhello(std::shared_ptr<httppeer> peer)
{
    peer->output = "Hello, world!";
    co_return "";
}
 
}// namespace http

hello est une fonction d'annotation. testhello.h n'a pas besoin d'être créé manuellement : il est généré automatiquement lors de cmake make. co_return ""; est une utilisation avancée : renvoyer une valeur poursuit avec la fonction d'annotation suivante, tandis qu'un retour vide signifie la fin.

1. Ce que c'est

La structure des sources révèle plusieurs choix de conception nets.

La couche réseau repose sur Asio autonome. Le serveur détient un asio::io_context plutôt qu'une boucle d'événements maison, si bien que la plupart des usages de l'écosystème Asio peuvent être branchés tels quels.

Les E/S et la logique métier sont séparées. Les threads d'E/S ne font que accept, read et write ; les gestionnaires synchrones sont distribués à un pool de threads métier dédié, clientrunpool. Le code bloquant dans un gestionnaire occupe donc le pool métier, jamais les threads réseau.

Les boucles d'E/S ne sont pas fusionnées en une seule, mais regroupées selon le nombre de cœurs. Le processus possède plusieurs instances de io_context, chaque connexion est attribuée à l'une d'elles en round-robin, et chaque ioc exécute plusieurs threads. Le détail figure à la section 3.

Les coroutines sont le point d'entrée de la couche de routage. La correspondance et la distribution des routes commencent à router::co_resolve ; les pré-gestionnaires et les gestionnaires disposent de créneaux synchrones et coroutines, afin que le code métier choisisse le style souhaité.

HTTP/2 est implémenté en interne. L'analyse des trames, le codage Huffman utilisé par HPACK, l'anneau d'envoi par connexion, la file d'envoi globale et le contrôle de flux se trouvent tous dans ce dépôt, et non derrière un wrapper tiers.

Les routes sont déclarées dans des commentaires et compilées en registre. Une fonction métier porte un commentaire //@urlpath(...) ; à la compilation, paozhu_pre le analyse et génère le registre ainsi que les stubs de déclaration de fonction.

Les fonctionnalités sont livrées en un seul ensemble. L'ORM, le pool de connexions, RBAC, OAuth, les paiements, Excel/Word/PDF, les images, la compression, les graphiques, les SMS et le client Redis se trouvent tous sous vendor/ et libs/ dans le même dépôt. Ils sont désactivés par défaut ; les options CMake correspondantes dans CMakeLists.txt valent OFF.

Le dépôt se divise grossièrement en quatre couches. vendor/httpserver est le framework proprement dit. Les autres sous-répertoires de vendor/ et libs/ sont des fonctionnalités réutilisables. common/, orm/, models/ et viewsrc/ forment le lien entre le framework et le code métier. controller/, view/, www/ et module/ sont des exemples de code métier que l'on peut supprimer entièrement. mini_project.sh rend cette séparation concrète : il retire les répertoires de démonstration tels que controller/src/admin, github et oauth, pour ne laisser que le noyau du framework.

2. Le faire fonctionner

Dépendances et compilation

Les dépendances sont listées dans vcpkg.json : openssl, brotli, asio, zlib, sqlite3, ainsi que la fonctionnalité gd qui apporte pkgconf, libgd, freetype, libpng et libqrencode. Avec vcpkg, activez -DENABLE_VCPKG=ON et transmettez CMAKE_TOOLCHAIN_FILE ; le détail figure dans README_CN.md. Un xmake.lua est également fourni pour ceux qui préfèrent xmake.

Une compilation normale se fait en trois étapes :

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./bin/paozhu                 # you can also pass ./bin/paozhu /path/to/server.conf

bin/ contient actuellement trois artefacts : paozhu, paozhu_cli et paozhu_pre. Le code de benchmark nécessite -DENABLE_BENCHMARK=ON explicite.

La compilation produit quatre cibles CMake : le programme principal paozhu, l'outil base de données/modèles paozhu_cli, le générateur de routes par annotation paozhu_pre, et paozhu_codegen qui s'exécute à chaque build.

L'ensemble des sources du programme principal est assemblé à partir de plusieurs globs :

set(paozhu_srcs
  ${common_list} ${viewsrc_list} ${framework_cpps} ${orm_list}
  ${reflect_list} ${src_list} ${source_list} ${controller_list})

reflect_list récupère libs/*.cpp de façon récursive.

Points d'entrée

Une compilation Release utilise startup/main_daemon.cpp ; les autres configurations basculent automatiquement sur startup/main_dev.cpp. La version démon prend d'abord argv[1] comme chemin vers server.conf ou comme répertoire le contenant, puis effectue un fork dans init_daemon() : l'enfant exécute get_server_app(), http::rbac::install_route_guard() et httpmy.run(argv_str), tandis que le parent boucle sur wait et relance l'enfant sur SIGCHLD. La version au premier plan suit le même chemin run() sans fork.

Dans run(), la séquence est : lire la configuration, créer les iocs et les threads, démarrer l'acceptation, enregistrer les routes, entrer dans la boucle d'événements.

3. Comment une requête circule

La répartition des threads

Le processus comporte quatre classes de threads. Vue d'ensemble :

Classe de thread Nombre Responsabilité
threads accept 2 (un pour HTTP, un pour SSL) accept bloquant ; remise des nouvelles connexions à un ioc
threads d'E/S nombre d'ioc × threads run() par ioc exécutent io_context::run() ; E/S des connexions et analyse des protocoles
threads annexes un httpwatch, http2_send_loop_num émetteurs HTTP/2 (au moins 2), un websocket_loop, un ratelimiter inspection périodique, vidage de la file d'envoi HTTP/2, limitation de débit par connexion
pool métier hardware_concurrency() + 2 exécute les gestionnaires synchrones

Le nombre de threads d'E/S se calcule en deux étapes. Le nombre d'ioc vaut min(cothreadnum, hardware_concurrency()), porté à 4 s'il est plus faible ; chaque ioc lance ensuite per_ioc_thread_num threads run(). Le commentaire de conf/server.conf énonce directement la formule : cothreadnum * per_ioc_thread_num = threads.

io_contexts[0] a un second rôle : il est aussi le membre de compatibilité io_context, et la boucle de minuteur propre au framework, l'acquisition synchrone de connexion et client_context y restent.

La sérialisation n'a lieu qu'à l'intérieur d'une connexion. Une nouvelle connexion est attribuée à un ioc par session_ioc_cursor++ % io_contexts.size() et lie son propre asio::strand, ce qui maintient l'ordre du traitement du protocole pour cette connexion. Il n'existe pas d'ordre équivalent entre connexions distinctes.

Le pool httppeer n'est pas un thread ; il figure ici seulement parce qu'on le confond facilement avec l'un d'eux. acquire_peer() prend un objet réutilisable, et lorsque la dernière référence est libérée, l'objet revient via reset_for_reuse(). La limite est PEER_POOL_MAX = 512, soit 4096 dans une compilation BENCHMARK.

Une connexion traverse ces threads de son arrivée à son départ :

  1. Un thread accept la récupère et la transmet à un ioc.
  2. À partir de là, ses lectures, écritures et analyses de protocole s'exécutent sur les threads run() de cet ioc, le strand maintenant la sérialisation de la connexion.
  3. Lorsqu'un gestionnaire synchrone est atteint, le travail est distribué au pool métier ; un gestionnaire coroutine attend simplement sur place et continue sur le thread ioc.
  4. À la sortie, HTTP/1.1 est réécrit directement par le thread d'E/S, tandis que HTTP/2 passe par les threads fixes http2_send_queue_loop qui vident la file d'envoi.
  5. Les threads annexes ne font que l'inspection périodique, la limitation de débit et le vidage des files ; ils ne traitent jamais de logique métier.

Correspondance et distribution des routes

Le chemin principal, de accept à la réponse, ressemble à ceci :

accept (side thread)
  → pick an ioc by round-robin, bind the connection to a strand
  → parse: HTTP/1.1 via http_parse.cpp, HTTP/2 via http2_parse.cpp
  → take an httppeer (acquire_peer)
  → router::co_resolve
        ├─ exact lookup, then prefix fallback (up to 6 segments)
        ├─ write the matched mask_code into the peer
        ├─ annotation-level rate limiting
        ├─ RBAC hook, only when mask_code is non-zero
        └─ pre → handler (the synchronous path goes to the business pool; coroutines await in place)
  → write the response: HTTP/1.1 directly, HTTP/2 through the send queue

router.cpp contient deux implémentations parallèles : une pour la chaîne synchrone, une pour la chaîne coroutine dans co_resolve. Un commentaire de router.h exige explicitement que les branches pre/handler des deux chaînes se comportent de façon identique ; modifier l'une implique de modifier l'autre.

Sortie HTTP/1.1 et HTTP/2

L'analyse HTTP/1.1 est interne, centrée sur vendor/httpserver/src/http_parse.cpp et secondée par request.cpp et httppeer.cpp. Requêtes et réponses sont sérielles, sans pipelining.

HTTP/2 est une implémentation complète, dont tous les fichiers sont dans vendor/httpserver/src/ : http2_parse.cpp pour l'analyse des trames et la machine à états de connexion, http2_frame.cpp/http2_define.cpp pour la structure des trames et les constantes, http2_huffman.cpp pour le codec Huffman utilisé par HPACK, http2_ring_queue.cpp pour l'anneau d'envoi de taille fixe par connexion, http2_send_queue.cpp pour la file d'envoi globale, et http2_flow.h pour les définitions des fenêtres de contrôle de flux.

Quelques points de conception comptent :

  • Chaque connexion possède un anneau fixe de 32 emplacements, CONST_HTTP2_RING_QUEUE_CAPACITY = 32. Une vérification à la compilation exige une puissance de deux tenant dans un unsigned char ; head_ et tail_ sont des index atomiques, avec un compteur bytes distinct.
  • Les objets d'envoi ont une machine à états explicite : own_state indique si un objet est dans le pool, la file globale, un stockage privé au thread ou stationné, tandis que block_reason consigne la raison du blocage.
  • Les objets bloqués ne sont pas interrogés en boucle. Ils sont parqués dans parked_list et rattachés à nouveau par park() / detach_parked() / reattach_parked() sur trois types d'événements : changement de fenêtre, trame SETTINGS ou emplacement d'anneau libéré.
  • Un flux est réinitialisé après « 120 secondes sans progression », et non après un simple délai d'inactivité. La constante est CONST_HTTP2_SEND_NO_PROGRESS_TIMEOUT = 120, et le contrôle se trouve dans server.cpp.
  • L'interrupteur est http2_enable = 1 dans conf/server.conf.

4. Le rôle de chaque module

Noyau du framework : vendor/httpserver

Ce répertoire comporte include/ et src/, avec 85 fichiers .cpp sous src/. Les responsabilités se regroupent ainsi :

  • Serveur et cycle de vie : server.cpp, serverconfig.cpp, client_context.cpp, resident_stop.cpp — démarrage, configuration, orchestration des threads, arrêt propre.
  • Connexions et protocoles : http_parse.cpp, http_header.cpp, http_domain.cpp, rpc_parse.cpp, client_session.cpp — analyse HTTP/1.1, routage par hôte, analyse RPC.
  • HTTP/2 : le groupe de fichiers listé à la section 3.
  • Modèle de requête : httppeer.cpp, request.cpp, cookie.cpp, session_id.cpp.
  • Routage : router.cpp, viewmethold_reg.cpp.
  • ORM et connexions : orm_common.cpp, orm_conn_pool.cpp, orm_connect_mar.cpp, orm_query.cpp, mysql_conn.cpp, pg_conn.cpp, sqlite_conn.cpp.
  • Primitives de thread : threadpool.cpp, atomic_count.cpp, atomic_guard.cpp.
  • Fichiers statiques : file_get_content.cpp, gzip.cpp, https_brotli.cpp, mime.cpp, directory_fun.cpp.
  • Connexions de longue durée : ws_*.cpp, http_websocket_client.cpp, http_socket*.cpp, mqtt_*.cpp, sock_subpub_reg.cpp.
  • Sécurité et authentification : jwt.cpp, acme_*.cpp, ocsp_check.cpp, base64.cpp, md5.cpp.
  • Utilitaires : parse_ini.cpp, str_fun.cpp, urlcode.cpp, unicode.cpp, datetime.cpp, qrcode.cpp, send_email.cpp, fastcgi.cpp, loadmodule.cpp, loadviewso.cpp.

Deux en-têtes de include/ prêtent à confusion. request.h est en réalité un micro-objet JSON intégré, obj_val, et non une classe de requête HTTP ; le véritable support requête/réponse est httppeer.h. httphook.h forme avec common/httphook.cpp la couche de hooks à laquelle se rattachent routage, authentification et limitation de débit. En outre, orm_cache.hpp, mysqlorm.hpp, postgresqlorm.hpp et sqliteorm.hpp sont les façades template de l'ORM.

Les deux générateurs : vendor/httpcli

Ce répertoire construit deux exécutables aux tâches complètement différentes.

paozhu_pre est le générateur de routes par annotation. Ses sources sont vendor/httpcli/autopickmethod.cpp et vendor/httpserver/src/md5.cpp. Il analyse les annotations sous controller/src et écrit common/autocontrolmethod.hpp ainsi que controller/include/*.h.

paozhu_cli est l'outil base de données/modèles. Ses sources sont vendor/httpcli/http_cli.cpp et les sources de connexion et de modèles de l'ORM. Ses capacités comprennent dbcreate, dbconvert, dbschema_check, dbdump_*, templateparse* et struct_reflectfile, déclarées dans vendor/httpcli/*.hpp.

Les fichiers .hpp sous vendor/httpcli/ sont les templates et les implémentations d'analyse des générateurs : controllerparse.hpp, ccontrollfun.hpp, dbtypes.hpp, modelfun.hpp, templateparse.hpp, typestatement.hpp, utility.hpp.

La chaîne de génération est branchée sur la compilation :

add_custom_target(paozhu_codegen ALL)
    COMMAND paozhu_pre <source root>
add_dependencies(paozhu paozhu_codegen)

Ainsi paozhu_pre s'exécute à chaque build, mais il compare les hashes et les mtimes des fichiers et n'écrit rien s'il n'y a pas de changement.

Registres et couche métier : common, controller

common/ contient 14 fichiers, surtout des définitions globales et des registres écrits à la main ; un seul est généré. autocontrolmethod.hpp est le registre des routes par annotation écrit par paozhu_pre, dont le chemin de sortie est codé en dur dans vendor/httpcli/autopickmethod.cpp. autorestfulpaths.hpp enregistre les noms de paramètres des chemins RESTful ; server.cpp l'inclut et mini_project.sh le réécrit lors de la création d'un nouveau projet. cost_define.h contient les constantes globales, httphook.cpp implémente la couche de hooks, et json_reflect_headers.h regroupe les en-têtes de réflexion JSON. reghttpmethod.hpp et reghttpmethod_pre.hpp sont les anciens registres manuels (une liste de macros REG_SYNC_SYNC, incluse par server.cpp). Les fichiers restants — mqtt_client_regmethod.hpp, mqtt_method_reg.hpp, redis_regmethod.hpp, sock_client_regmethod.hpp, sockets_method_reg.hpp, websockets_method_reg.hpp, ws_client_regmethod.hpp — sont les registres des différents backends de connexions de longue durée.

L'ordre d'enregistrement mérite d'être retenu. server.cpp appelle _initauto_all_httputils(), _inithttpmethodregto() et _inithttpmethodregto_pre() dans cet ordre : table générée, table manuelle, table pre manuelle. reg_add conserve le premier enregistrement, si bien qu'une entrée manuelle pour le même chemin est masquée par la table générée. paozhu_pre le sait et signale ces collisions comme ROUTE-WARN pendant la génération.

Les 100 en-têtes sous controller/include/ sont des stubs de déclaration de fonction générés, et non du code écrit à la main. paozhu_pre ne les réécrit que lorsqu'une signature d'annotation change, en se basant sur md5 et mtime ; pendant configure, CMake se contente de file(TOUCH) sur les en-têtes manquants comme espaces réservés. Les véritables implémentations sont dans controller/src/, réparties par domaine métier : admin/, superadmin/ (dont superadmin/rbac/) et rbac/ pour le back-office et les permissions ; oauth/, oauth_client/ et github/ pour l'autorisation et la connexion ; saas.com/ pour un site de démonstration multi-locataire ; serverwatch.cpp pour les points de supervision ; les nombreux test_*.cpp et test*.cpp pour les démonstrations de capacités et les cas de régression (par exemple test_maskcode.cpp illustre la limitation de débit par annotation).

Couche de données : orm, models, schema

orm/orm.h est le point d'entrée. En dessous se trouvent trois domaines de modèles — cms/, pg/ et lite/ — correspondant à MySQL, PostgreSQL et SQLite. Les 64 fichiers *_base.h sous orm/cms/include/ sont générés par paozhu_cli ; leur en-tête indique This file is auto create from paozhu_cli. fk_child_opsql.cpp et fk_parent_opsql.cpp sont des requêtes de jointure écrites à la main. models/ contient le comportement des modèles : ces fichiers .cpp sont générés une seule fois par paozhu_cli puis jamais écrasés — l'en-tête précise qu'un fichier existant est conservé et qu'un fichier manquant est créé —, on peut donc y écrire de la logique métier en toute sécurité. schema/ contient le SQL de création des tables.

Le pool de connexions se trouve dans vendor/httpserver/src/orm_conn_pool.cpp et include/orm_conn_pool.h. Le pool est segmenté par ioc ; le max_pool global est réparti selon le nombre de segments, le reste allant aux segments les plus petits, et chaque segment reçoit au moins une place (slot_max_of / slot_min_of). Chaque segment a son propre verrou, si bien que les threads d'ioc différents ne se disputent jamais le même. Les clés de configuration sont orm_ioc_num et orm_thread_pool_num, et les paramètres de connexion figurent dans conf/orm.conf. L'ORM expose aussi une interface coroutine : les requêtes de orm_connect_mar.cpp et orm_query.cpp peuvent être attendues directement.

Bibliothèques de capacités réutilisables : libs

libs/ compte 11 sous-répertoires, tous écrits à la main. À la compilation, un glob récursif de CMakeLists.txt les intègre à la cible principale, et leurs répertoires d'en-têtes sont ajoutés récursivement au chemin d'inclusion.

libs/rbac est le noyau de la décision de permission. rbac.h fournit load_user_roles, load_role_perms, load_user_grants (six requêtes en une passe pour récupérer rôles, permissions, niveaux d'affectation et répertoires), user_has_url et user_has_permscode. route_guard.cpp est le hook de route : il renvoie 401 sans adminid, 403 sans companyid, et sinon s'en remet au cache. allow() dans route_cache.cpp met en cache par (adminid, companyid) avec 16 segments, 4096 entrées et un TTL de 60 secondes ; le chargement maintient le verrou du segment pour un comportement single-flight, et un échec de chargement est traité en fail-closed. route_cache.cpp possède aussi une fonction stats() sans appelant.

libs/oauth est la partie serveur d'OAuth, divisée en oauth_config (lit conf/oauth.conf), oauth_store (hachage des jetons, vérification PKCE, authentification client Basic) et oauth_audit (audit). audit_log() de oauth_audit écrit une ligne dans la file de logs d'erreur du framework, et httpwatch l'ajoute à log/error.log. Les points d'accès eux-mêmes sont dans controller/src/oauth/ : oauth_authorize.cpp, oauth_token.cpp, oauth_introspect.cpp, oauth_revoke.cpp, oauth_jwks.cpp, oauth_metadata.cpp, oauth_userinfo.cpp, oauth_bearerauth.cpp, oauth_client_add.cpp, oauth_purge.cpp.

libs/oauth_client est un client OAuth 2.x/2.1 générique, non lié à un serveur d'autorisation particulier : quatre URL d'endpoints suffisent pour dialoguer avec GitHub, Google ou un endpoint oauth auto-hébergé. Il prend en charge PKCE, trois grants (authorization code, refresh, client_credentials), ainsi que introspect et revoke. libs/github est la variante propre à GitHub : son state se compose de [adminid, client_id, rand32], revoke utilise DELETE + Basic, et le scope reçoit toujours read:user ajouté. Il inclut également github_api, github_config, github_crypto et github_store.

libs/webpay contient la logique de paiement côté application : machine à états des commandes (pending/paid/cancelled/refunded), génération des numéros de commande, recherche par wxorder, recherche asynchrone et décisions de règlement pour les réponses WeChat V3, ainsi que des fichiers pour les callbacks, la barrière de certificats, Alipay/WeChat V2/V3, les QR codes et les jetons.

markdown2html de libs/markdown traite les citations, le gras, les liens, les titres, les lignes horizontales, les tableaux, les images, les barrés sur une ligne, les blocs de code et les listes ordonnées/non ordonnées, et tient également une table des matières et une liste de références. libs/pinyin convertit les caractères han en pinyin à partir des données de pinyin-data et d'une recherche binaire. libs/ipdata lit ip.data (format ip2region) et associe une IP à un pays/province/ville par recherche binaire. libs/department est une structure d'arbre organisationnel avec parentid et children. upload_images de libs/img gère les envois d'images, de vidéos, de base64 et de fichiers de formulaire, et liste les fichiers déjà envoyés. libs/types contient des types d'exemple pour la réflexion JSON, avec objets imbriqués et tableaux, afin d'illustrer la génération de réflexion.

Modules de capacités optionnels : vendor/*

Ces modules suivent tous la structure include/ + src/ et sont désactivés par défaut. Leurs sources sont ajoutées à paozhu_srcs par des globs conditionnels dans CMakeLists.txt, et leurs interrupteurs y sont également centralisés. Ils sont classés ci-dessous du plus au moins susceptible d'être nécessaire dans une véritable application.

Documents et tableurs. Ce groupe couvre les exports de rapports back-office, les imports Excel, la génération de contrats ou d'avis, et l'enregistrement de pages en PDF. pzexcel gère la lecture et l'écriture xlsx, plusieurs feuilles et les styles de cellules. pzword gère la lecture et l'écriture docx, la conversion entre HTML et docx, et peut produire directement un flux d'octets en mémoire. webpdf est le moteur de rendu PDF ; son en-tête public expose HTMLRenderer, et le même répertoire contient quatre analyseurs pour HTML, CSS, SVG et TTF. Activez ENABLE_OFFICE dès que l'application importe ou exporte des documents Office, et ENABLE_PDF séparément pour HTML-vers-PDF.

Compression, images et graphiques. Utilisez pzzip pour les téléchargements groupés ou la décompression des envois ; il peut écrire un zip directement dans un tampon mémoire sans toucher à un fichier temporaire. Utilisez pzimage pour les captchas et le traitement d'image courant ; il embarque les codecs PNG/JPEG et sait dessiner des glyphes à partir des contours TrueType/OpenType. Utilisez pzcharts pour les graphiques intégrés aux pages de rapport ; il émet directement du SVG et couvre les graphiques en ligne, en ligne lissée, en barres, en nuage de points, en anneau, en radar, en jauge et en entonnoir. Les trois interrupteurs sont indépendants : n'activez que les capacités réellement utilisées.

Paiements et SMS. Utilisez vendor/webpay lorsqu'un flux transactionnel est nécessaire ; il enveloppe les SDK WeChat/Alipay et gère les détails de bas niveau tels que les certificats V3, les certificats de plateforme et les clés d'idempotence de remboursement. La logique côté application (machine à états des commandes, callbacks, barrière de certificats) se trouve dans libs/webpay, comme indiqué dans la section libs ci-dessus. Utilisez sms pour les codes de vérification ou les notifications ; il contient des clients Alibaba Cloud et Tencent Cloud. Ils correspondent respectivement à ENABLE_WEBPAY et ENABLE_SMS.

Cache et divers. pzredis est un client Redis. redis_client ne détient pas de connexion : chaque commande en emprunte une à une section de configuration et la restitue ensuite, avec des API synchrone et coroutine. Activez ENABLE_REDIS pour le cache, les verrous distribués ou le pub/sub. Le client Redis de longue durée au niveau framework a son propre interrupteur, ENABLE_REDIS_CLIENT, qui exige également ENABLE_REDIS ; sinon configure échoue immédiatement.

vendor/pzredis ENABLE_REDIS client Redis qui emprunte et restitue des connexions par section de configuration, avec API synchrone et coroutine

Une dépendance mérite d'être signalée : ENABLE_OFFICE active automatiquement ENABLE_ZIP, car pzword utilise pz::zip pour empaqueter les docx.

Connexions de longue durée

Le dépôt possède quatre répertoires indépendants — websockets/, sockets/, mqtt/ et redis/ — qui sont surtout des sites de démonstration et des exemples. Les véritables implémentations de protocole sont dans vendor/httpserver/src/ : WebSocket dans ws_conn.cpp, ws_handshake.cpp, ws_parser.cpp, ws_wire.cpp, websockets_callback.cpp ; TCP brut dans http_socket.cpp, http_socket_client.cpp, sock_subpub_reg.cpp ; MQTT dans mqtt_frame.cpp, mqtt_session.cpp, mqtt_reg.cpp, mqtt_subpub_reg.cpp, http_mqtt_client.cpp ; et la connexion Redis de longue durée dans http_rpcclient.cpp ainsi que le client de vendor/pzredis. Les interrupteurs sont ENABLE_WEBSOCKETS_CLIENT, ENABLE_SOCKETS_CLIENT, ENABLE_MQTT_CLIENT (actifs par défaut) et ENABLE_REDIS_CLIENT (désactivé par défaut et nécessitant ENABLE_REDIS). Les registres côté métier sont le groupe *_regmethod.hpp dans common/.

Vues, fichiers statiques et chargement à chaud de .so

view/ contient des modèles HTML écrits à la main, répartis par domaine métier en home/, admin/, cms/, login/, oauth/, superadmin/ et d'autres. viewsrc/include/viewsrc.h et viewsrc/include/regviewmethod.hpp sont les points d'entrée d'enregistrement manuels. viewsrc/view/**.cpp est du C++ généré par l'analyseur de modèles — les fichiers portent l'en-tête //This file create by paozhu (voir viewsrc/view/home/header.cpp) — et comprennent actuellement home/header.cpp, oauth/consent.cpp, oauth_client/page.cpp, superadmin/*.cpp et d'autres. L'analyseur se trouve dans vendor/httpcli/templateparse.hpp.

www/default/ est la racine du site statique, configurée par wwwpath = ./www/default.

module/ est le répertoire des bibliothèques partagées, avec module/controller/testviewso.so et module/view/{admin,cms,home,login}/*.so. Chaque interrupteur correspond à un côté : ENABLE_VIEWSO utilise viewsopath pour pointer vers module/view, tandis que ENABLE_MODELSO utilise controlsopath pour module/controller. La logique de chargement est dans loadmodule.cpp et loadviewso.cpp ; elle ouvre les fichiers .so avec pz::dll::library et conserve le handle de bibliothèque avec le pointeur de fonction mis en cache, afin que le pointeur ne devienne pas invalide après dlclose.

5. Configuration et extension

Où se trouvent les fichiers de configuration

conf/ est divisé par sous-système : server.conf, orm.conf, redis.conf, mqtt.conf, sockets.conf, websockets.conf, oauth.conf, webpay.conf, acme.conf, github.conf, test.conf, ainsi que les certificats et les clés. Les trois que l'on touche le plus souvent sont server.conf pour le processus et ses sites, orm.conf pour les connexions à la base de données et acme.conf pour l'émission automatique de certificats. Les autres ne comptent que lorsque le sous-système correspondant est activé.

Trois réglages de threads agissent ensemble. cothreadnum est la limite supérieure du nombre d'ioc ; le nombre réel vaut min(cothreadnum, nombre de cœurs), porté à 4 s'il est plus faible. per_ioc_thread_num est le nombre de threads run() par ioc, et leur produit donne le nombre total de threads d'E/S. orm_thread_pool_num est le nombre total de threads ORM ; 0 signifie hardware_concurrency(), plafonné à 512, réparti également sur orm_ioc_num iocs, le reste allant aux iocs d'index inférieur.

Certaines valeurs se lisent facilement à l'envers. upload_max_size est en octets ; la valeur du modèle 16777216 fait 16 MiB, la limite n'est appliquée que si elle dépasse 1024, et 0 ou vide signifie illimité, avec des redéfinitions par site. Pour usehtmlcache, vide ou une valeur commençant par 0 signifie désactivé, toute autre valeur non vide signifie activé ; usehtmlcachetime inférieur à 10 secondes est traité comme 10. rate_limit_second_num2 doit être strictement inférieur à rate_limit_second_num1, et rate_limit_accept_wait_num doit dépasser rate_limit_new_wait_num de plus de 100, sinon il est ramené au double de cette valeur. session_type vaut 0 fichier / 1 mémoire / 2 Redis / 3 Memcache / 4 réservé. acme_every_day accepte 2–23, et ocsp_intv_time inférieur à 3600 secondes est traité comme 3600.

Un autre groupe de clés n'a aucun site de lecture dans le code C++ de ce dépôt. Elles restent dans le fichier pour des raisons historiques ; ne supposez pas qu'elles doivent encore être configurées : threadmax, threadmin, bmcport, staticfile_cache_num, modelspath, viewpath, controlpath, libspath, pluginspath. Les commentaires décrivent bmcport comme un port d'administration et de supervision, et staticfile_cache_num comme un nombre d'entrées de cache, mais aucun n'a de lecteur à l'exécution.

maxpool et minpool sont répartis de façon asymétrique, ce qui prête à confusion. Le pool est segmenté par ioc, avec un nombre de places égal à orm_ioc_num. maxpool est un budget global partagé par toutes les places de ce rôle, et non un quota par place : on calcule maxpool / nombre de places, on distribue le reste une unité à la fois aux places d'index le plus bas, et on donne au moins 1 à chaque place — par exemple maxpool = 20 avec 4 places donne 5 par place, et maxpool = 10 avec 3 places donne 4/3/3. minpool n'est pas divisé : chaque place préconstruit minpool connexions, plafonné par son propre quota, si bien qu'avec maxpool = 5 et 4 places les quotas sont 2/1/1/1 et minpool = 5 ne donne toujours que 2/1/1/1.

Deux points supplémentaires. password ne peut contenir que de l'ASCII imprimable 0x21–0x7E ; un bloc contenant des espaces, des caractères de contrôle ou des caractères non ASCII est ignoré et signalé comme erreur. Pour SQLite, placez le chemin du fichier de base de données dans host et laissez port, dbname et les identifiants vides ; ssl, sslverify et sslhost ne s'appliquent qu'à MySQL et PostgreSQL.

L'émission ne se produit que si deux conditions sont réunies : le site a acme_auto = 1 dans server.conf, et email ici n'est pas vide. Sans e-mail, la tâche revient immédiatement et n'écrit qu'une ligne sous log/acme_log/. En outre, bien que cert_path soit réglé sur ./conf, le code actuel copie en réalité les certificats dans le répertoire contenant server.conf : cette valeur est lue mais n'influe pas sur la destination de copie.

Le flux d'émission est piloté chaque jour depuis httpwatch : acme_every_day choisit l'heure, l'heure précédente pose le drapeau du jour, et à l'heure dite un thread détaché exécute acme_task. La tâche parcourt les sites, vérifie acme_auto, construit le domaine principal et le domaine www, et lit la validité restante de acme_path/<primary_domain>/cert.pem ; si elle dépasse days_remain, le site est ignoré. Sinon, la tâche suit les étapes compte ACME, commande, validation HTTP-01, CSR et finalize, en écrivant privkey.pem, cert.pem et fullchain.pem sous acme_path/<primary_domain>/. En cas de succès, elle copie fullchain.pem vers conf/<primary_domain>.pem, privkey.pem vers conf/<primary_domain>.key et cert.pem vers conf/<primary_domain>.crt, puis écrit restart_ssl_config pour que la configuration SSL soit rechargée. Les entrées certificate_chain_file, private_key_file et chain_crt_file de server.conf utilisent exactement ces noms de fichiers, résolus par rapport au répertoire contenant server.conf.

Écrire des routes par annotation

Les routes sont déclarées dans le commentaire au-dessus d'une fonction métier, sous la forme //@urlpath(pre, urlpath), avec éventuellement un suffixe :mask pour distinguer les méthodes HTTP :

//@urlpath(superadmin_islogin,superadmin/rbac/perm)
std::string superadmin_rbac_perm_list(std::shared_ptr<httppeer> peer)

Cet exemple provient de controller/src/superadmin/rbac/rbacperm.cpp.

Après l'analyse, paozhu_pre génère des entrées de la forme reg_raw(site, path, pre_sync, co_pre, reg_sync, co_reg, mask_code), qui aboutissent dans common/autocontrolmethod.hpp. Un chemin contenant :param enregistre également ses noms de paramètres dans common/autorestfulpaths.hpp. Les annotations peuvent aussi porter des paramètres de limitation de débit avec //@urlpath(...):ratelimit(time,num) ; un exemple figure dans controller/src/test_maskcode.cpp, et les valeurs analysées alimentent rate_time et rate_num de l'entrée de route.

Si l'on ne souhaite pas d'annotations, common/reghttpmethod.hpp propose encore le style d'enregistrement purement manuel REG_SYNC_SYNC, avec un lambda intégré pour /helloworld. Ses enregistrements viennent toutefois après la table générée, si bien qu'un chemin de même nom est masqué par l'entrée générée. Cela convient à des essais temporaires, pas à des points d'accès de production.

Ajouter un point d'accès

La démarche normale est courte : choisir un fichier adapté sous controller/src/, écrire la fonction avec son annotation, puis compiler. Pendant la compilation, paozhu_codegen exécute paozhu_pre, qui met à jour les stubs de déclaration dans controller/include/ et les entrées de registre dans common/autocontrolmethod.hpp ; au démarrage du processus, la table générée est enregistrée et la requête peut être routée.

Si le point d'accès nécessite une limitation de débit, ajoutez ratelimit(time,num) après l'annotation. S'il nécessite RBAC, donnez à la route un mask_code non nul et ajoutez une ligne d'autorisation dans la table des permissions avec le même urlpath et le même maskcode — un commentaire de libs/rbac/rbac.h explique que la vérification exige que le maskcode de la route soit exactement égal à l'un des droits effectifs de l'utilisateur.

Charger un .so à l'exécution

Si ENABLE_VIEWSO ou ENABLE_MODELSO est activé à la compilation, les fichiers .so sous module/view et module/controller peuvent être chargés à l'exécution. Les points d'entrée côté vue sont loadview / loadviewso, et le point d'entrée côté contrôleur se trouve dans loadmodule.cpp. Dans la configuration, faites pointer viewsopath et controlsopath vers les répertoires correspondants. Les fichiers sous module/ sont des artefacts de compilation ou des bibliothèques partagées déployées manuellement, et non des sources.

6. Tests et auto-vérification

Les tests ne sont pas compilés par défaut ; ils ne sont inclus qu'avec -DENABLE_TESTS=ON. La convention de tests/CMakeLists.txt est de générer une cible exécutable de même nom pour chaque tests/*.cpp et tests/orm/*.cpp, avec pool_thread comme exception. Les cas existants comprennent test_framework_smoke.cpp (test de fumée du framework), test_http2_ring_queue.cpp et test_http2_headers_split.cpp (anneau d'envoi et séparation des en-têtes HTTP/2), test_router_hooks.cpp (hooks de route), test_jwt_smoke.cpp (JWT), test_filename_safety.cpp (sécurité des noms de fichiers), test_pzexcel_p2.cpp et test_pzzip.cpp (sous-modules optionnels). Il existe également des sous-répertoires pour l'analyse de protocoles : http1_consume/, multipart_boundary/, multipart_part_headers/, postform/, raw_post_fastpath/ et orm/.

Les points d'auto-vérification sont tous dans controller/src/serverwatch.cpp : /metrics émet du texte au format Prometheus, /paozhu_status est l'ancien tableau de bord personnalisé, et /frametasks_timeloop montre les tâches de minuteur du framework. Les points de connexion du back-office sont admin/login et admin/loginpost:ratelimit(60,5) avec limitation de débit, implémentés dans controller/src/admin/main.cpp ; l'entrée super-admin est superadmin/login, implémentée dans controller/src/superadmin/supermain.cpp.

7. Portée de la vérification

Les conclusions de ce document proviennent en grande partie de la lecture des sources et des répertoires : configuration de compilation, topologie des threads, chemin de routage, file d'envoi HTTP/2, cache RBAC, limitation de débit, artefacts générés, clés de server.conf et points d'auto-vérification, tout peut être retracé via les fichiers listés à la fin. Cette passe a également couvert les en-têtes publics des modules sous libs/ et vendor/ ; les descriptions de oauth, oauth_client, github, webpay, markdown, pinyin, ipdata, department, img, types, pzexcel, pzword, webpdf, pzimage, pzcharts, pzzip, pzredis et sms s'appuient sur les signatures de fonction ou les commentaires de ces en-têtes.

Six domaines n'ont pas été lus implémentation par implémentation. Ne considérez pas les descriptions hors de cette liste comme des faits vérifiés ligne par ligne :

  • Avec ENABLE_MODELSO, comment les noms de fonction dans module/controller/testviewso.so correspondent aux routes ; seul le lien entre l'interrupteur et le répertoire a été confirmé, pas toute la chaîne d'enregistrement après le chargement.
  • La couverture des champs et les règles de génération des trois domaines de modèles ORM (cms/pg/lite) ; seuls la source de génération, le découpage du pool et la règle « conserver les fichiers de modèles existants » ont été confirmés.
  • La syntaxe de génération et les déclencheurs de mise à jour qui transforment les modèles de view/ en viewsrc/view/*.cpp ; seuls le marqueur d'en-tête de fichier et l'emplacement de l'analyseur ont été confirmés.
  • Les assertions concrètes de chaque cas tests/*.cpp ; elles ne sont décrites que par le nom de fichier et les conventions de tests/CMakeLists.txt.
  • Si startup/main_dev.cpp et startup/main_daemon.cpp suivent exactement la même chaîne en dehors du fork ; les deux fichiers n'ont pas été comparés ligne à ligne.
  • La profondeur d'implémentation de pzexcel, pzword et webpdf ; seuls les en-têtes publics ont été lus, sans parcourir chaque flux de lecture/écriture.
