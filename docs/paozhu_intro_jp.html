Paozhu（爆竹）Web フレームワーク

Paozhu は C++ で書かれた Web フレームワークです。ソースコード: https://github.com/hggq/paozhu。まず目立つのは、1 つの実行ファイルにすべてが同梱されている点です。HTTP/1.1、HTTP/2、WebSocket、生の TCP、MQTT クライアント、Redis クライアント、ORM、テンプレートビュー、静的ファイル配信がすべて同じプロセス内にあり、コンパイル時のスイッチで不要な部分を削除できます。

最短の例から見てみましょう。ハンドラーはコルーチンのタスクを返し、peer->output に代入した値がレスポンス本文になります。ルートは関数の上のコメントで宣言します:

サーバーを起動したら、ブラウザで http://localhost/hello にアクセスできます。

#include "httppeer.h"
#include "testhello.h"
namespace http
{
//@urlpath(null,hello)
asio::awaitable<std::string> testhello(std::shared_ptr<httppeer> peer)
{
    peer->output = "Hello, world!";
    co_return "";
}
 
}// namespace http

hello はアノテーション関数です。testhello.h は手動で作成する必要はなく、cmake make 時に自動生成されます。co_return ""; は高度な使い方で、値を返すと次のアノテーション関数へ進み、空文字を返すと完了を意味します。

1. 概要

ソース構造を見るだけでも、明確な設計方針が読み取れます。

ネットワーク層は standalone Asio の上に構築されています。 サーバーは独自のイベントループではなく asio::io_context を保持するため、Asio エコシステムのほとんどの流儀をそのまま利用できます。

I/O とビジネスロジックは分離されています。 I/O スレッドは accept、read、write だけを行い、同期ハンドラーは専用のビジネススレッドプール clientrunpool にディスパッチされます。したがってハンドラー内のブロッキングコードはネットワークスレッドではなくビジネスプールを占有します。

I/O ループは 1 つに統合せず、コア数に応じてグループ化されています。 プロセスは複数の io_context インスタンスを持ち、各接続はラウンドロビンでそのうちの 1 つに割り当てられ、各 ioc は複数のスレッドを実行します。詳細は第 3 節で扱います。

コルーチンがルーティング層のエントリーポイントです。 ルートの照合とディスパッチは router::co_resolve から始まり、pre ハンドラーとハンドラーの両方に同期スロットとコルーチンスロットがあるため、ビジネスコードは好きな方式を選べます。

HTTP/2 は自前実装です。 フレーム解析、HPACK が使う Huffman コーディング、接続ごとの送信リング、グローバル送信キュー、フロー制御は、サードパーティのラッパーの背後ではなく、このリポジトリ内にあります。

ルートはコメントで宣言し、コンパイル時にレジストリにまとめます。 ビジネス関数に //@urlpath(...) コメントを付けると、ビルド時に paozhu_pre がそれを走査してレジストリと関数宣言のスタブを生成します。

機能はひとまとめで提供されます。 ORM、コネクションプール、RBAC、OAuth、決済、Excel/Word/PDF、画像、圧縮、チャート、SMS、Redis クライアントは、すべて同じリポジトリの vendor/ と libs/ の下にあります。既定では無効で、CMakeLists.txt の対応する CMake オプションの既定値は OFF です。

リポジトリはおおむね 4 つの層に分かれます。フレームワーク本体が vendor/httpserver です。その他の vendor/ サブディレクトリと libs/ は再利用可能な機能です。common/、orm/、models/、viewsrc/ はフレームワークとビジネスコードの間の接着層です。controller/、view/、www/、module/ は丸ごと削除できるサンプルビジネスコードです。mini_project.sh がこの分離を実際に行います。controller/src/admin、github、oauth などのデモディレクトリを削除し、フレームワークのコアだけを残します。

2. 起動まで

依存関係とビルド

依存関係は vcpkg.json に記載されています: openssl、brotli、asio、zlib、sqlite3 と、pkgconf、libgd、freetype、libpng、libqrencode を取り込む gd 機能です。vcpkg を使う場合は -DENABLE_VCPKG=ON を指定し、CMAKE_TOOLCHAIN_FILE を渡します。詳細は README_CN.md を参照してください。xmake を好む人のために xmake.lua も同梱されています。

通常のビルドは 3 ステップです:

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./bin/paozhu                 # you can also pass ./bin/paozhu /path/to/server.conf

bin/ には現在 3 つの成果物があります: paozhu、paozhu_cli、paozhu_pre。ベンチマーク関連のコードは -DENABLE_BENCHMARK=ON を明示しないと含まれません。

ビルドは 4 つの CMake ターゲットを生成します: メインプログラム paozhu、データベース/モデルツール paozhu_cli、アノテーションルートジェネレーター paozhu_pre、そしてビルドのたびに実行される paozhu_codegen です。

メインプログラムのソース集合は複数の glob で組み立てられます:

set(paozhu_srcs
  ${common_list} ${viewsrc_list} ${framework_cpps} ${orm_list}
  ${reflect_list} ${src_list} ${source_list} ${controller_list})

reflect_list は libs/*.cpp を再帰的に拾います。

エントリーポイント

Release ビルドは startup/main_daemon.cpp を使い、他のビルド構成は自動的に startup/main_dev.cpp に切り替わります。デーモン版はまず argv[1] を server.conf のパス、またはそれを含むディレクトリとして扱い、init_daemon() の中で fork します。子プロセスは get_server_app()、http::rbac::install_route_guard()、httpmy.run(argv_str) を実行し、親プロセスは wait を繰り返して SIGCHLD を受け取ると子を再生成します。フォアグラウンド版は fork なしで同じ run() の道をたどります。

run() 内の順序は次のとおりです: 設定を読み、ioc とスレッドを作り、accept を開始し、ルートを登録し、イベントループに入ります。

3. リクエストの流れ

スレッドの分け方

プロセスには 4 種類のスレッドがあります。概要は次のとおりです。

スレッドの種類 数 担当
accept スレッド 2 つ (HTTP 用と SSL 用に 1 つずつ) ブロッキング accept。新しい接続を ioc に渡す
I/O スレッド ioc 数 × ioc あたりの run() スレッド数 io_context::run() を実行。接続の I/O とプロトコル解析
補助スレッド httpwatch 1 つ、HTTP/2 送信 http2_send_loop_num 個(最小 2)、websocket_loop 1 つ、ratelimiter 1 つ 定期検査、HTTP/2 送信キューの排出、接続単位のレート制限
ビジネスプール hardware_concurrency() + 2 同期ハンドラーを実行

I/O スレッド数は 2 段階で計算されます。ioc 数は min(cothreadnum, hardware_concurrency()) で、4 未満なら 4 に引き上げられます。次に各 ioc が per_ioc_thread_num 個の run() スレッドを起動します。conf/server.conf のコメントが式をそのまま示しています: cothreadnum * per_ioc_thread_num = threads。

io_contexts[0] には第 2 の役割があります。互換用メンバー io_context でもあり、フレームワーク自身のタイマーループ、同期接続取得、client_context はすべてこの上にあります。

直列化は接続内だけで行われます。新しい接続は session_ioc_cursor++ % io_contexts.size() で ioc に割り当てられ、接続は自身の asio::strand をバインドして、その接続のプロトコル処理の順序を保ちます。異なる接続同士にはそのような順序保証はありません。

httppeer プールはスレッドではありませんが、混同されやすいためここに挙げます。acquire_peer() が再利用可能なオブジェクトを取り出し、最後の参照が解放されると reset_for_reuse() を経て戻ります。上限は PEER_POOL_MAX = 512 で、BENCHMARK ビルドでは 4096 です。

接続は到着から離脱まで次のスレッドを通ります:

  1. accept スレッドが接続を受け取り、ioc に渡します。
  2. 以降、読み書きとプロトコル解析はその ioc の run() スレッドで動作し、strand が接続の処理を直列化します。
  3. 同期ハンドラーに達すると処理はビジネスプールにディスパッチされ、コルーチンハンドラーはその場で await して ioc スレッド上で進み続けます。
  4. 出力では、HTTP/1.1 は I/O スレッドが直接書き戻し、HTTP/2 は送信キューを排出する固定の http2_send_queue_loop スレッドへ渡ります。
  5. 補助スレッドは定期検査、レート制限、キューの排出だけを行い、ビジネスロジックは扱いません。

ルートの照合とディスパッチ

accept からレスポンスまでの主要な経路は次のとおりです:

accept (side thread)
  → pick an ioc by round-robin, bind the connection to a strand
  → parse: HTTP/1.1 via http_parse.cpp, HTTP/2 via http2_parse.cpp
  → take an httppeer (acquire_peer)
  → router::co_resolve
        ├─ exact lookup, then prefix fallback (up to 6 segments)
        ├─ write the matched mask_code into the peer
        ├─ annotation-level rate limiting
        ├─ RBAC hook, only when mask_code is non-zero
        └─ pre → handler (the synchronous path goes to the business pool; coroutines await in place)
  → write the response: HTTP/1.1 directly, HTTP/2 through the send queue

router.cpp には 2 つの並列実装があります。1 つは同期チェーン、もう 1 つは co_resolve 内のコルーチンチェーンです。router.h のコメントは、両チェーンの pre/handler 分岐が同じように振る舞うことを明示的に要求しています。片方を変更したらもう片方も変更する必要があります。

HTTP/1.1 と HTTP/2 の出力

HTTP/1.1 の解析は自前実装で、vendor/httpserver/src/http_parse.cpp を中心に request.cpp と httppeer.cpp が支えます。リクエストとレスポンスは直列で、パイプライン処理はありません。

HTTP/2 は完全な実装で、関連ファイルはすべて vendor/httpserver/src/ にあります。http2_parse.cpp はフレーム解析と接続ステートマシン、http2_frame.cpp/http2_define.cpp はフレーム構造と定数、http2_huffman.cpp は HPACK が使う Huffman コーデック、http2_ring_queue.cpp は接続ごとの固定サイズ送信リング、http2_send_queue.cpp はグローバル送信キュー、http2_flow.h はフロー制御ウィンドウの定義です。

重要な設計ポイントがいくつかあります:

  • 接続ごとに 32 スロットの固定リングがあります。CONST_HTTP2_RING_QUEUE_CAPACITY = 32 で、2 のべき乗であり unsigned char に収まることをコンパイル時に検査します。head_ と tail_ はアトミックなインデックスで、別に bytes の滞留カウンターがあります。
  • 送信オブジェクトは明示的なステートマシンを持ちます。own_state がプール、グローバルキュー、スレッド専用領域、待機状態のどこにあるかを示し、block_reason がブロックされた理由を記録します。
  • ブロックされたオブジェクトを繰り返しポーリングしません。parked_list に待機させ、ウィンドウの変化、SETTINGS フレーム、リングスロットの空きという 3 種類のイベントで park() / detach_parked() / reattach_parked() により再接続します。
  • ストリームは通常のアイドルタイムアウトではなく「120 秒間進展がないこと」でリセットされます。定数は CONST_HTTP2_SEND_NO_PROGRESS_TIMEOUT = 120 で、検査は server.cpp にあります。
  • スイッチは conf/server.conf の http2_enable = 1 です。

4. 各モジュールの役割

フレームワークコア: vendor/httpserver

このディレクトリは include/ と src/ に分かれ、src/ の下に 85 個の .cpp ファイルがあります。役割は次のように分類できます:

  • サーバーとライフサイクル: server.cpp, serverconfig.cpp, client_context.cpp, resident_stop.cpp — 起動、設定、スレッドの調整、正常シャットダウン。
  • 接続とプロトコル: http_parse.cpp, http_header.cpp, http_domain.cpp, rpc_parse.cpp, client_session.cpp — HTTP/1.1 解析、ホストルーティング、RPC 解析。
  • HTTP/2: 第 3 節に挙げたファイル群。
  • リクエストモデル: httppeer.cpp, request.cpp, cookie.cpp, session_id.cpp。
  • ルーティング: router.cpp, viewmethold_reg.cpp。
  • ORM と接続: orm_common.cpp, orm_conn_pool.cpp, orm_connect_mar.cpp, orm_query.cpp, mysql_conn.cpp, pg_conn.cpp, sqlite_conn.cpp。
  • スレッドプリミティブ: threadpool.cpp, atomic_count.cpp, atomic_guard.cpp。
  • 静的ファイル: file_get_content.cpp, gzip.cpp, https_brotli.cpp, mime.cpp, directory_fun.cpp。
  • 長期接続: ws_*.cpp, http_websocket_client.cpp, http_socket*.cpp, mqtt_*.cpp, sock_subpub_reg.cpp。
  • セキュリティと認証: jwt.cpp, acme_*.cpp, ocsp_check.cpp, base64.cpp, md5.cpp。
  • ユーティリティ: parse_ini.cpp, str_fun.cpp, urlcode.cpp, unicode.cpp, datetime.cpp, qrcode.cpp, send_email.cpp, fastcgi.cpp, loadmodule.cpp, loadviewso.cpp。

include/ の 2 つのヘッダーは誤解されやすいです。request.h は実際には HTTP リクエストクラスではなく組み込み JSON マイクロオブジェクト obj_val で、本当のリクエスト/レスポンスの担い手は httppeer.h です。httphook.h は common/httphook.cpp とともに、ルーティング、認証、レート制限が接続されるフック層を形成します。また orm_cache.hpp、mysqlorm.hpp、postgresqlorm.hpp、sqliteorm.hpp は ORM のテンプレートファサードです。

2 つのジェネレーター: vendor/httpcli

このディレクトリは役割がまったく異なる 2 つの実行ファイルを生成します。

paozhu_pre はアノテーションルートジェネレーターです。ソースは vendor/httpcli/autopickmethod.cpp と vendor/httpserver/src/md5.cpp です。controller/src 配下のアノテーションを走査し、common/autocontrolmethod.hpp と controller/include/*.h に書き出します。

paozhu_cli はデータベース/モデルツールです。ソースは vendor/httpcli/http_cli.cpp と ORM の接続・モデルソースです。dbcreate、dbconvert、dbschema_check、dbdump_*、templateparse*、struct_reflectfile などの機能を持ち、vendor/httpcli/*.hpp に宣言されています。

vendor/httpcli/ 配下の .hpp ファイルはジェネレーターのテンプレートと解析実装です: controllerparse.hpp、ccontrollfun.hpp、dbtypes.hpp、modelfun.hpp、templateparse.hpp、typestatement.hpp、utility.hpp。

生成チェーンはビルドに組み込まれています:

add_custom_target(paozhu_codegen ALL)
    COMMAND paozhu_pre <source root>
add_dependencies(paozhu paozhu_codegen)

したがってビルドのたびに paozhu_pre が実行されますが、ファイルのハッシュと mtime を比較し、変化がなければ何も書き込みません。

レジストリとビジネス層: common, controller

common/ には 14 個のファイルがあり、その多くは手書きのグローバル定義とレジストリで、生成物は 1 つだけです。autocontrolmethod.hpp は paozhu_pre が書き出すアノテーションルートのレジストリで、出力先は vendor/httpcli/autopickmethod.cpp にハードコードされています。autorestfulpaths.hpp は RESTful パスのパラメーター名を記録し、server.cpp がインクルードし、mini_project.sh が新しいプロジェクトを作るときに書き換えます。cost_define.h はグローバル定数、httphook.cpp はフック層の実装、json_reflect_headers.h は JSON リフレクションヘッダーを集約します。reghttpmethod.hpp と reghttpmethod_pre.hpp は初期の手書きレジストリです(REG_SYNC_SYNC マクロのリストで、server.cpp がインクルード)。残りのファイル — mqtt_client_regmethod.hpp, mqtt_method_reg.hpp, redis_regmethod.hpp, sock_client_regmethod.hpp, sockets_method_reg.hpp, websockets_method_reg.hpp, ws_client_regmethod.hpp — はさまざまな長期接続バックエンド用のレジストリです。

登録順序は覚えておく価値があります。server.cpp は _initauto_all_httputils()、_inithttpmethodregto()、_inithttpmethodregto_pre() をこの順で呼びます。生成テーブル、手書きテーブル、手書き pre テーブルの順です。reg_add は最初の登録を保持するため、同じパスの手書きエントリは生成テーブルに隠されます。paozhu_pre はこれを知っており、生成時にそのような衝突を ROUTE-WARN として報告します。

controller/include/ 配下の 100 個のヘッダーは手書きコードではなく生成された関数宣言スタブです。paozhu_pre はアノテーションのシグネチャが変わったときだけ md5 と mtime で判断して書き換えます。configure 段階では CMake が足りないヘッダーを file(TOUCH) でプレースホルダーとして作るだけです。実際の実装は controller/src/ にあり、ビジネスドメインごとに分かれています: 管理画面と権限用の admin/、superadmin/(superadmin/rbac/ を含む)、rbac/; 認可とログイン用の oauth/、oauth_client/、github/; マルチテナントのデモサイト saas.com/; 監視エンドポイント用の serverwatch.cpp; 機能デモと回帰ケース用の多数の test_*.cpp、test*.cpp(たとえば test_maskcode.cpp はアノテーションによるレート制限を示します)。

データ層: orm, models, schema

orm/orm.h がエントリーポイントです。その下に MySQL、PostgreSQL、SQLite に対応する 3 つのモデルドメイン cms/、pg/、lite/ があります。orm/cms/include/ 配下の 64 個の *_base.h は paozhu_cli が生成し、ヘッダーに This file is auto create from paozhu_cli とあります。fk_child_opsql.cpp と fk_parent_opsql.cpp は手書きの結合クエリです。models/ はモデルの振る舞いを保持します。これらの .cpp は paozhu_cli が一度だけ生成し、以降は上書きしません。ファイルヘッダーに既存ファイルは保持し、欠けているファイルを生成すると明記されているため、ここにビジネスロジックを安全に書けます。schema/ にはテーブル作成 SQL があります。

コネクションプールは vendor/httpserver/src/orm_conn_pool.cpp と include/orm_conn_pool.h にあります。プールは ioc ごとにシャーディングされます。グローバルな max_pool をシャード数で割り、余りは小さいシャードに順に割り当て、各シャードに最低 1 スロットを与えます(slot_max_of / slot_min_of)。シャードごとに専用のロックがあるため、異なる ioc のスレッドが同じロックで競合することはありません。設定キーは orm_ioc_num と orm_thread_pool_num で、接続パラメーターは conf/orm.conf にあります。ORM はコルーチンインターフェースも公開しており、orm_connect_mar.cpp と orm_query.cpp のクエリはそのまま await できます。

再利用可能な機能ライブラリ: libs

libs/ には 11 個のサブディレクトリがあり、すべて手書きです。ビルド時に CMakeLists.txt の再帰 glob でメインターゲットに取り込まれ、ヘッダーディレクトリも再帰的にインクルードパスに追加されます。

libs/rbac は権限判定の核です。rbac.h は load_user_roles、load_role_perms、load_user_grants(1 回のパスで 6 つのクエリを実行し、ロール、権限、割り当て階層、ディレクトリを取得)、user_has_url、user_has_permscode を提供します。route_guard.cpp はルートフックで、adminid がなければ 401、companyid がなければ 403 を返し、それ以外はキャッシュに委譲します。route_cache.cpp の allow() は (adminid, companyid) をキーに 16 シャード、4096 エントリ、60 秒 TTL でキャッシュします。読み込み時にシャードロックを保持して single-flight を実現し、読み込み失敗は fail-closed として扱います。route_cache.cpp には呼び出し元のない stats() 関数もあります。

libs/oauth は OAuth のサーバー側で、conf/oauth.conf を読む oauth_config、トークンのハッシュ化、PKCE 検証、Basic クライアント認証を担う oauth_store、監査を担う oauth_audit に分かれます。oauth_audit の audit_log() はフレームワークのエラーログキューに 1 行を書き込み、httpwatch がそれを log/error.log に追記します。エンドポイント自体は controller/src/oauth/ にあります: oauth_authorize.cpp、oauth_token.cpp、oauth_introspect.cpp、oauth_revoke.cpp、oauth_jwks.cpp、oauth_metadata.cpp、oauth_userinfo.cpp、oauth_bearerauth.cpp、oauth_client_add.cpp、oauth_purge.cpp。

libs/oauth_client は特定の認可サーバーに結びつかない汎用 OAuth 2.x/2.1 クライアントです。4 つのエンドポイント URL を埋めれば GitHub、Google、セルフホストの oauth エンドポイントと通信できます。PKCE、3 種類の grant(authorization code、refresh、client_credentials)、introspect と revoke をサポートします。libs/github は GitHub 専用の亜種で、state は [adminid, client_id, rand32] の 3 要素、revoke は DELETE + Basic、scope には常に read:user が付きます。github_api、github_config、github_crypto、github_store も含まれます。

libs/webpay はアプリケーション側の決済ロジックです。注文のステートマシン(pending/paid/cancelled/refunded)、注文番号の生成、wxorder による照会、非同期照会、WeChat V3 の照会レスポンスに対する精算判定と、コールバック、証明書ゲート、Alipay/WeChat V2/V3、QR コード、トークン関連のファイルがあります。

libs/markdown の markdown2html は引用、太字、リンク、見出し、水平線、表、画像、1 行の打ち消し線、コードブロック、順序付き/順序なしリストを処理し、目次と参照一覧も管理します。libs/pinyin は pinyin-data のデータと二分探索で漢字をピンインに変換します。libs/ipdata は ip.data(ip2region 形式)を読み、IP を国/省/都市に対応させます。libs/department は parentid と children を持つ組織ツリー構造です。libs/img の upload_images は画像、動画、base64、フォームファイルのアップロードを扱い、アップロード済みファイルを一覧します。libs/types には入れ子オブジェクトと配列を含む JSON リフレクション用のサンプル型があり、リフレクション生成を実演します。

オプション機能モジュール: vendor/*

これらのモジュールはすべて include/ + src/ の構成で、既定では無効です。ソースは CMakeLists.txt の条件付き glob で paozhu_srcs に追加され、スイッチも同じ場所に集約されています。実際のアプリケーションで必要になる可能性が高い順に並べました。

ドキュメントとスプレッドシート。 管理画面のレポート出力、Excel の取り込み、契約書や通知の生成、ページの PDF 保存が対象です。pzexcel は xlsx の読み書き、複数シート、セルのスタイルを扱います。pzword は docx の読み書き、HTML と docx の相互変換を行い、メモリ上のバイトストリームに直接出力できます。webpdf は PDF レンダラーで、公開ヘッダーが HTMLRenderer を公開し、同じディレクトリに HTML、CSS、SVG、TTF 用の 4 つのパーサーがあります。アプリケーションが Office 文書を取り込む/出力する場合は ENABLEOFFICE を、HTML から PDF には別途 ENABLE_PDF をON にしてください。

圧縮、画像、チャート。 パッケージのダウンロードやアップロードの展開には pzzip を使ってください。一時ファイルを使わずにメモリバッファに直接 zip を書けます。キャプチャや一般的な画像処理には pzimage を使ってください。PNG/JPEG コーデックを内包し、TrueType/OpenType のアウトラインからグリフを描けます。レポートページに埋め込むチャートには pzcharts を使ってください。SVG を直接生成し、折れ線、平滑折れ線、棒、散布、ドーナツ、レーダー、ゲージ、ファネルをカバーします。3 つのスイッチは独立しているので、実際に使う機能だけを有効にしてください。

決済と SMS。 取引フローが必要なら vendor/webpay を使ってください。WeChat/Alipay SDK をラップし、V3 証明書、プラットフォーム証明書、返金の冪等キーなどの低レベルな詳細を処理します。アプリケーション側のロジック(注文ステートマシン、コールバック、証明書ゲート)は前述の libs の節で説明したとおり libs/webpay にあります。認証番号や通知には sms を使ってください。Alibaba Cloud と Tencent Cloud のクライアントが含まれます。それぞれ ENABLE_WEBPAY と ENABLE_SMS に対応します。

キャッシュなど。 pzredis は Redis クライアントです。redis_client は接続を保持しません。各コマンドが設定セクションから接続を借りて使い、終わったら返します。同期 API とコルーチン API の両方を備えます。キャッシュ、分散ロック、pub/sub には ENABLE_REDIS を有効にしてください。フレームワーク水準の Redis 長期接続クライアントは別のスイッチ ENABLE_REDIS_CLIENT で、ENABLE_REDIS もON である必要があります。そうでない場合 configure は即座に失敗します。

長期接続

リポジトリには主にデモサイトとサンプルである 4 つの独立ディレクトリ — websockets/、sockets/、mqtt/、redis/ — があります。実際のプロトコル実装は vendor/httpserver/src/ にあります。WebSocket は ws_conn.cpp、ws_handshake.cpp、ws_parser.cpp、ws_wire.cpp、websockets_callback.cpp; 生 TCP は http_socket.cpp、http_socket_client.cpp、sock_subpub_reg.cpp; MQTT は mqtt_frame.cpp、mqtt_session.cpp、mqtt_reg.cpp、mqtt_subpub_reg.cpp、http_mqtt_client.cpp; Redis 長期接続は http_rpcclient.cpp と vendor/pzredis のクライアントです。スイッチは ENABLE_WEBSOCKETS_CLIENT、ENABLE_SOCKETS_CLIENT、ENABLE_MQTT_CLIENT(既定でON)、ENABLE_REDIS_CLIENT(既定でOFF、ENABLE_REDIS が必要)です。ビジネス側のレジストリは common/ の *_regmethod.hpp 群です。

ビュー、静的ファイル、.so ホットロード

view/ には手書きの HTML テンプレートがあり、ビジネスドメインごとに home/、admin/、cms/、login/、oauth/、superadmin/ などに分かれています。viewsrc/include/viewsrc.h と viewsrc/include/regviewmethod.hpp は手書きの登録エントリーポイントです。viewsrc/view/**.cpp はテンプレートパーサーが生成した C++ で、ファイル先頭に //This file create by paozhu が付きます(viewsrc/view/home/header.cpp を参照)。現在 home/header.cpp、oauth/consent.cpp、oauth_client/page.cpp、superadmin/*.cpp などが含まれます。パーサーは vendor/httpcli/templateparse.hpp にあります。

www/default/ は静的サイトのルートで、wwwpath = ./www/default で設定します。

module/ は共有ライブラリのディレクトリで、module/controller/testviewso.so と module/view/{admin,cms,home,login}/*.so が入っています。スイッチがそれぞれの側を担当します。ENABLE_VIEWSO は viewsopath で module/view を指し、ENABLE_MODELSO は controlsopath で module/controller を指します。ロード処理は loadmodule.cpp と loadviewso.cpp にあり、pz::dll::library で .so を開き、ライブラリハンドルをキャッシュ済み関数ポインターと一緒に保持して dlclose 後にポインターが無効にならないようにします。

5. 設定と拡張

設定ファイルの場所

3 つのスレッド設定は連動します。cothreadnum は ioc 数の上限で、実際の数は min(cothreadnum, コア数) であり、4 未満なら 4 に引き上げます。per_ioc_thread_num は ioc あたりの run() スレッド数で、2 つの積が I/O スレッド総数です。orm_thread_pool_num は ORM の全スレッド数で、0 は hardware_concurrency() を意味します。上限は 512 で、orm_ioc_num 個の ioc に均等に分け、余りはインデックスの小さい ioc に割り当てます。

いくつかの値は逆に読まれやすいです。upload_max_size の単位はバイトで、テンプレート値 16777216 は 16 MiB です。1024 より大きいときだけ制限が適用され、0 または空は無制限を意味し、サイトごとの上書きが可能です。usehtmlcache は空または 0 で始まる値ならOFF、それ以外の非空の値ならON です。 usehtmlcachetime が 10 秒未満なら 10 秒として扱います。rate_limit_second_num2 は rate_limit_second_num1 より厳密に小さく、rate_limit_accept_wait_num は rate_limit_new_wait_num より 100 以上大きくなければなりません。そうでない場合は 2 倍の値に再設定されます。session_type は 0 ファイル / 1 メモリ / 2 Redis / 3 Memcache / 4 予約です。acme_every_day は 2〜23 を受け付け、ocsp_intv_time が 3600 秒未満なら 3600 として扱います。

もう一団のキーは、このリポジトリの C++ コードのどこからも読み込まれていません。歴史的な理由でファイルに残っているだけなので、まだ設定が必要だと思わないでください: threadmax、threadmin、bmcport、staticfile_cache_num、modelspath、viewpath、controlpath、libspath、pluginspath。コメントは bmcport を管理・監視ポート、staticfile_cache_num をキャッシュエントリ数と説明していますが、どちらも実行時の読み取り側がありません。

maxpool と minpool は非対称に分割されるため誤読しやすいです。プールは ioc ごとにシャーディングされ、スロット数は orm_ioc_num に等しいです。maxpool はその役割の全スロットが共有するグローバル予算であり、スロットごとの割り当てではありません。maxpool / スロット数 を計算し、余りをインデックスの低いスロットに 1 つずつ渡し、各スロットに最低 1 を与えます。たとえば maxpool = 20 でスロット 4 つなら各 5、maxpool = 10 でスロット 3 つなら 4/3/3 です。minpool は分割しません。各スロットが minpool 個の接続をあらかじめ作りますが、そのスロット自身の割り当てが上限になるため、maxpool = 5 でスロット 4 つなら割り当てが 2/1/1/1 となり、minpool = 5 でも結果は 2/1/1/1 です。

もう 2 点あります。password に使えるのは印字可能な ASCII 0x21〜0x7E だけで、空白、制御文字、非 ASCII を含むブロックはスキップされ、エラーとして記録されます。SQLite ではデータベースファイルのパスを host に置き、port、dbname、資格情報を空にしてください。ssl、sslverify、sslhost は MySQL と PostgreSQL にだけ適用されます。

発行は 2 つの条件がともに成り立つときだけ実行されます。サイトの server.conf に acme_auto = 1 があり、ここの email が空でないことです。メールがなければタスクは即座に戻り、log/acme_log/ 配下に 1 行書くだけです。また cert_path が ./conf であっても、現在のコードは実際には server.conf のあるディレクトリに証明書をコピーするため、この値は読み込まれますがコピー先には影響しません。

発行の流れは httpwatch が毎日動かします。acme_every_day が時刻を決め、その 1 時間前に当日のフラグを立て、時刻になると分離スレッドが acme_task を実行します。タスクはサイトを順に見て acme_auto を確認し、プライマリドメインと www ドメインを組み立て、acme_path/<primary_domain>/cert.pem の残存有効期間を読みます。days_remain を超えていればそのサイトを飛ばします。そうでなければ ACME のアカウント、注文、HTTP-01 検証、CSR、finalize の各ステップを進め、acme_path/<primary_domain>/ 配下に privkey.pem、cert.pem、fullchain.pem を書き出します。成功すると fullchain.pem を conf/<primary_domain>.pem に、privkey.pem を conf/<primary_domain>.key に、cert.pem を conf/<primary_domain>.crt にコピーし、restart_ssl_config を書いて SSL 設定を再読み込みさせます。server.conf の certificate_chain_file、private_key_file、chain_crt_file はまさにこのファイル名を使い、server.conf のあるディレクトリを基準に解決されます。

アノテーションルートの書き方

ルートはビジネス関数の上のコメントで宣言します。形式は //@urlpath(pre, urlpath) で、HTTP メソッドを区別するには :mask 接尾辞を付けられます:

//@urlpath(superadmin_islogin,superadmin/rbac/perm)
std::string superadmin_rbac_perm_list(std::shared_ptr<httppeer> peer)

この例は controller/src/superadmin/rbac/rbacperm.cpp から取っています。

走査の後、paozhu_pre は reg_raw(site, path, pre_sync, co_pre, reg_sync, co_reg, mask_code) の形のエントリを生成し、common/autocontrolmethod.hpp に置きます。:param を含むパスはパラメーター名も common/autorestfulpaths.hpp に登録します。アノテーションには //@urlpath(...):ratelimit(time,num) の形でレート制限パラメーターを載せることもできます。例は controller/src/test_maskcode.cpp にあり、解析された値はルートエントリの rate_time と rate_num に入ります。

アノテーションを使いたくない場合は、common/reghttpmethod.hpp に純粋な手書き登録方式 REG_SYNC_SYNC があり、/helloworld 用のインラインラムダも入っています。ただしこの登録は生成テーブルの後に来るため、同じ名前のパスは生成エントリに隠されます。一時的な実験には向いていますが、本番のエンドポイントには向きません。

エンドポイントの追加

普通の手順は短いです。controller/src/ の下で適当なファイルを選び、アノテーションを付けて関数を書き、ビルドします。ビルド中に paozhu_codegen が paozhu_pre を実行し、controller/include/ の宣言スタブと common/autocontrolmethod.hpp のレジストリエントリを更新します。プロセスが起動すると生成テーブルを登録し、リクエストがそのルートへ振り向けられます。

エンドポイントにレート制限が必要なら、アノテーションの後に ratelimit(time,num) を追加してください。RBAC が必要なら、ルートに 0 以外の mask_code を与え、権限テーブルに同じ urlpath と maskcode の授権行を追加してください。libs/rbac/rbac.h のコメントは、判定には「ルートの maskcode がユーザーの有効な権限のいずれかと厳密に一致すること」が必要だと説明しています。

実行時の .so ロード

コンパイル時に ENABLE_VIEWSO または ENABLE_MODELSO が有効なら、module/view と module/controller 配下の .so ファイルを実行時にロードできます。ビュー側のエントリーポイントは loadview / loadviewso で、コントローラー側は loadmodule.cpp にあります。設定で viewsopath と controlsopath をそれぞれのディレクトリに向けてください。module/ 配下のファイルはビルド成果物または手動配置の共有ライブラリであり、ソースではありません。

6. テストと自己診断

テストは既定ではビルドされず、-DENABLE_TESTS=ON のときだけ含まれます。tests/CMakeLists.txt の規則では tests/*.cpp と tests/orm/*.cpp のそれぞれに同名の実行ターゲットを作り、pool_thread だけが例外です。既存のケースには test_framework_smoke.cpp(フレームワークのスモークテスト)、test_http2_ring_queue.cpp と test_http2_headers_split.cpp(HTTP/2 送信リングとヘッダー分割)、test_router_hooks.cpp(ルートフック)、test_jwt_smoke.cpp(JWT)、test_filename_safety.cpp(ファイル名の安全性)、test_pzexcel_p2.cpp と test_pzzip.cpp(オプションのサブモジュール)があります。プロトコル解析用のサブディレクトリとして http1_consume/、multipart_boundary/、multipart_part_headers/、postform/、raw_post_fastpath/、orm/ もあります。

自己診断エンドポイントはすべて controller/src/serverwatch.cpp にあります。/metrics は Prometheus テキスト形式を出力し、/paozhu_status は古い独自ダッシュボード、/frametasks_timeloop はフレームワークのタイマータスクを示します。管理画面のログインエンドポイントは admin/login とレート制限付きの admin/loginpost:ratelimit(60,5) で、controller/src/admin/main.cpp に実装されています。スーパー管理者の入口は superadmin/login で、controller/src/superadmin/supermain.cpp にあります。

7. 検証の範囲

このドキュメントの結論は、ほぼソースとディレクトリの内容を読んで得たものです。ビルド設定、スレッド構成、ルーティング経路、HTTP/2 送信キュー、RBAC キャッシュ、レート制限、生成物、server.conf のキー、自己診断エンドポイントは、すべて最後に挙げたファイルで辿れます。今回は libs/ と vendor/ 配下モジュールの公開ヘッダーも読みました。oauth、oauth_client、github、webpay、markdown、pinyin、ipdata、department、img、types、pzexcel、pzword、webpdf、pzimage、pzcharts、pzzip、pzredis、sms の説明は、それぞれのヘッダーの関数シグネチャやコメントに基づいています。

次の 6 つの領域は実装を 1 つずつ読みませんでした。この一覧の外の記述を、1 行ごとに検証済みの事実として扱わないでください:

  • ENABLE_MODELSO を有効にしたとき、module/controller/testviewso.so 内の関数名がルートにどう対応するか。スイッチとディレクトリの対応関係だけを確認し、ロード後の登録チェーン全体は確認していません。
  • 3 つの ORM モデルドメイン(cms/pg/lite)のフィールド範囲と生成規則。生成元、プールのシャーディング、「既存のモデルファイルは保持する」方針だけを確認しました。
  • view/ のテンプレートを viewsrc/view/*.cpp にする生成構文と更新トリガー。ファイル先頭の目印とパーサーの場所だけを確認しました。
  • 各 tests/*.cpp ケースの具体的なアサーション。ファイル名と tests/CMakeLists.txt の規則だけで説明しています。
  • startup/main_dev.cpp と startup/main_daemon.cpp が fork 以外にまったく同じチェーンをたどるかどうか。両ファイルを 1 行ずつ比較していません。
  • pzexcel、pzword、webpdf の実装の深さ。公開ヘッダーだけを読み、各読み書きの流れは辿っていません。
