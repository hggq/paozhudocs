Paozhu（炮竹）Web 框架介绍

Paozhu 是一个用 C++ 写的 Web 框架，源码地址：https://github.com/hggq/paozhu。它最直观的特点是"一个可执行文件什么都带"：HTTP/1.1、HTTP/2、WebSocket、裸 TCP、MQTT 客户端、Redis 客户端、ORM、模板视图和静态文件服务都在同一个进程里，编译时再按开关把用不到的部分裁掉。

先看一个最短的例子：业务函数返回协程任务，给 peer->output 赋值就是响应体，路由由函数上方的注解声明：

服务启动后，可在浏览器访问 http://localhost/hello。

#include "httppeer.h"
#include "testhello.h"
namespace http
{
//@urlpath(null,hello)
asio::awaitable<std::string> testhello(std::shared_ptr<httppeer> peer)
{
    peer->output = "Hello, world!";
    co_return "";
}
 
}// namespace http

hello 是注解函数，testhello.h 无需手动创建，cmake make 时会自动生成。co_return ""; 是高级使用方式：返回值会继续执行下一个注解函数，为空表示完成。

一、它是什么

从源码结构看，Paozhu 有几个很明确的取向。

网络层直接建在 standalone Asio 上。 服务器持有的就是 asio::io_context，没有另造一套事件循环，所以 Asio 生态里的用法基本都能接进来。

I/O 和业务是分开的。 I/O 线程只做 accept、read、write，同步业务 handler 会被投递到独立的业务线程池 clientrunpool。这意味着在 handler 里写阻塞代码，堵住的是业务池，不会把网络线程一起拖死。

I/O 循环按核数分组，而不是单 loop。 进程里有一组 io_context，连接按轮询分到其中某一个，每个 ioc 再跑若干线程，后面第三节会展开。

协程是路由层的入口。 路由匹配和派发的主入口是 router::co_resolve，pre 和 handler 都同时准备了同步、协程两套槽位，业务可以按需要选。

HTTP/2 是自己实现的。 帧解析、HPACK 用的 Huffman、每连接的发送环、全局发送队列和流控都在仓库里，不是包一层第三方库。

路由声明写在注释里，构建时生成注册表。 业务函数的注释里写 //@urlpath(...)，构建时由 paozhu_pre 扫描出来，生成注册表和函数声明桩。

能力是打包交付的。 ORM、连接池、RBAC、OAuth、支付、Excel/Word/PDF、图片、压缩、图表、短信、Redis 客户端都在同一个仓库的 vendor/ 和 libs/ 下，默认关闭，按 CMake 开关启用，这些 option 在 CMakeLists.txt 里的默认值都是 OFF。

仓库大致分成四层：vendor/httpserver 是框架本体；vendor/ 下其余子目录和 libs/ 是可复用能力；common/、orm/、models/、viewsrc/ 这些是框架和业务之间的胶水层；controller/、view/、www/、module/ 则是可以直接删掉的示例业务。这个分层在 mini_project.sh 里体现得很直接：它会移除 controller/src/admin、github、oauth 等演示目录，只留框架核心。

二、把项目跑起来

依赖和构建

依赖列在 vcpkg.json：openssl、brotli、asio、zlib、sqlite3，另有一个 gd feature 带 pkgconf、libgd、freetype、libpng、libqrencode。用 vcpkg 时打开 -DENABLE_VCPKG=ON 并把 CMAKE_TOOLCHAIN_FILE 传进去，README_CN.md 里有对应说明。仓库也带了一份 xmake.lua，喜欢 xmake 的可以走另一条路。

常规构建就是三步：

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./bin/paozhu                 # 也可以传 ./bin/paozhu /path/to/server.conf

bin/ 下现在有 paozhu、paozhu_cli、paozhu_pre 三个产物。压测相关的东西要显式打开 -DENABLE_BENCHMARK=ON。

构建会产出四个 CMake 目标：主程序 paozhu、数据库/模型工具 paozhu_cli、注解路由生成器 paozhu_pre，以及每次构建都会跑一遍的 paozhu_codegen。

主程序的源码集合是几个 glob 拼起来的：

set(paozhu_srcs
  ${common_list} ${viewsrc_list} ${framework_cpps} ${orm_list}
  ${reflect_list} ${src_list} ${source_list} ${controller_list})

其中 reflect_list 会把 libs/*.cpp 递归收进来。

启动入口

Release 构建用 startup/main_daemon.cpp，其它构建配置自动换成 startup/main_dev.cpp。守护版先把 argv[1] 当作 server.conf 的路径或目录解析，然后 init_daemon() 里 fork：子进程执行 get_server_app()、http::rbac::install_route_guard()、httpmy.run(argv_str)；父进程循环 wait，收到 SIGCHLD 时重启子进程。前台版走同一条 run()，只是不 fork。

run() 内部依次做：读配置、建 ioc 和线程、起 accept、注册路由、进事件循环。

三、一次请求怎么走

线程是怎么分的

进程里的线程可以归成四类，先看全貌：

线程类别 数量 负责什么
accept 线程 2（HTTP 一个、SSL 一个） 阻塞 accept，把新连接交给 ioc
I/O 线程 ioc 组数 × 每组的 run() 线程数 跑 io_context::run()，做连接读写和协议解析
旁路线程 httpwatch 1 条、HTTP/2 发送 http2_send_loop_num 条（下限 2）、websocket_loop 1 条、ratelimiter 1 条 定时巡检、消费 HTTP/2 发送队列、连接级限流
业务线程池 hardware_concurrency() + 2 跑同步 handler

I/O 线程的数量分两层算。组数是 min(cothreadnum, hardware_concurrency())，低于 4 时抬到 4；每组再起 per_ioc_thread_num 个 run() 线程。conf/server.conf 的注释直接给了算式 cothreadnum * per_ioc_thread_num = threads。

io_contexts[0] 还有额外身份：它同时就是兼容成员 io_context，框架自己的定时循环、同步取连接和 client_context 都留在它上面。

串行只发生在连接内部。新连接按 session_ioc_cursor++ % io_contexts.size() 轮询落到某个 ioc，连接自己再绑一个 asio::strand，保证同一条连接上的协议处理按序执行。不同连接之间没有这层顺序。

httppeer 池不是线程，放在这里只是因为容易和线程混在一起：acquire_peer() 拿可复用对象，最后一个引用释放时走 reset_for_reuse() 回池；上限 PEER_POOL_MAX = 512，BENCHMARK 构建下是 4096。

一条连接从进来到出去，会依次碰到这些线程：

  1. accept 线程接住连接，交给某个 ioc。
  2. 之后该连接的读写和协议解析都在这个 ioc 的 run() 线程上，由 strand 保证同连接串行。
  3. 命中同步 handler 时，工作被投递到业务线程池；协程 handler 则就地 co_await，仍在该 ioc 线程上推进。
  4. 输出阶段，HTTP/1.1 由 I/O 线程直接写回，HTTP/2 交给固定的 http2_send_queue_loop 线程消费发送队列。
  5. 旁路线程只做周期性的巡检、限流和队列消费，不参与具体业务处理。

路由匹配与派发

请求从 accept 到输出，主干是这样的：

accept（旁路线程）
  → 轮询选 ioc，连接绑 strand
  → 协议解析：HTTP/1.1 走 http_parse.cpp，HTTP/2 走 http2_parse.cpp
  → 取 httppeer（acquire_peer）
  → router::co_resolve
        ├─ 精确查找，未命中再做前缀回退（最多 6 段）
        ├─ 把命中的 mask_code 写进 peer
        ├─ 注解级限流
        ├─ RBAC 钩子，mask_code 非 0 才进
        └─ pre → handler（同步步进业务池，协程就地 co_await）
  → 输出写回：HTTP/1.1 直接写，HTTP/2 进发送队列

同步链和协程链在 router.cpp 里是两段平行实现：同步侧一条，协程侧在 co_resolve 里一条。router.h 的注释明确要求两条链的 pre/handler 分支行为保持一致，改一边就得同步改另一边。

HTTP/1.1 与 HTTP/2 的输出

HTTP/1.1 是自研解析，主体在 vendor/httpserver/src/http_parse.cpp，配合 request.cpp、httppeer.cpp。请求-响应串行，没有 pipeline。

HTTP/2 是一套完整实现，相关文件都在 vendor/httpserver/src/：http2_parse.cpp 管帧解析和连接状态机，http2_frame.cpp/http2_define.cpp 管帧结构与常量，http2_huffman.cpp 是 HPACK 用的 Huffman 编解码，http2_ring_queue.cpp 是每连接的定长发送环，http2_send_queue.cpp 是全局发送队列，http2_flow.h 放流控窗口定义。

几个关键设计点：

  • 每连接一个 32 槽定长环，常量 CONST_HTTP2_RING_QUEUE_CAPACITY = 32。编译期要求它是 2 的幂并且能塞进 unsigned char；head_/tail_ 是原子下标，另有一个 bytes 积压计数。
  • 发送对象有明确的状态机：own_state 表示它在池里、全局队列里、线程私有还是挂起，block_reason 记录为什么被挡住。
  • 被挡住的对象不会反复轮询复查，而是 park 进 parked_list，由 park() / detach_parked() / reattach_parked() 在窗口变化、收到 SETTINGS、环腾出槽位这三类事件上回灌。
  • 撤流条件是"连续 120 秒没有任何推进"，不是普通的空闲超时。CONST_HTTP2_SEND_NO_PROGRESS_TIMEOUT = 120，判定逻辑在 server.cpp。
  • 开关是 conf/server.conf 里的 http2_enable = 1。

四、各模块各自管什么

框架核心 vendor/httpserver

include/ 加 src/，src/ 下有 85 个 .cpp。按职责可以分成这么几组：

  • 服务器与生命周期：server.cpp、serverconfig.cpp、client_context.cpp、resident_stop.cpp，负责启动、配置、线程编排和优雅退出。
  • 连接与协议：http_parse.cpp、http_header.cpp、http_domain.cpp、rpc_parse.cpp、client_session.cpp，负责 HTTP/1.1 解析、域名路由和 RPC 解析。
  • HTTP/2：前面第三节列过的那组文件。
  • 请求模型：httppeer.cpp、request.cpp、cookie.cpp、session_id.cpp。
  • 路由：router.cpp、viewmethold_reg.cpp。
  • ORM 与连接：orm_common.cpp、orm_conn_pool.cpp、orm_connect_mar.cpp、orm_query.cpp、mysql_conn.cpp、pg_conn.cpp、sqlite_conn.cpp。
  • 线程原语：threadpool.cpp、atomic_count.cpp、atomic_guard.cpp。
  • 静态文件：file_get_content.cpp、gzip.cpp、https_brotli.cpp、mime.cpp、directory_fun.cpp。
  • 长连接：ws_*.cpp、http_websocket_client.cpp、http_socket*.cpp、mqtt_*.cpp、sock_subpub_reg.cpp。
  • 安全与鉴权：jwt.cpp、acme_*.cpp、ocsp_check.cpp、base64.cpp、md5.cpp。
  • 工具：parse_ini.cpp、str_fun.cpp、urlcode.cpp、unicode.cpp、datetime.cpp、qrcode.cpp、send_email.cpp、fastcgi.cpp、loadmodule.cpp、loadviewso.cpp。

include/ 里有两个容易看错的头。request.h 其实是内置的 JSON 微对象 obj_val，不是 HTTP 请求类；真正的请求/响应载体是 httppeer.h。httphook.h 配合 common/httphook.cpp 构成钩子层，路由、认证、限流都挂在上面。另外 orm_cache.hpp、mysqlorm.hpp、postgresqlorm.hpp、sqliteorm.hpp 是 ORM 的模板门面。

两个生成器 vendor/httpcli

这个目录编出两个可执行文件，用途完全不同。

paozhu_pre 是注解路由生成器，源码是 vendor/httpcli/autopickmethod.cpp 加 vendor/httpserver/src/md5.cpp。它扫描 controller/src 里的注解，写出 common/autocontrolmethod.hpp 和 controller/include/*.h。

paozhu_cli 是数据库/模型工具，源码是 vendor/httpcli/http_cli.cpp 加 ORM 连接和模型相关源。能力包括 dbcreate、dbconvert、dbschema_check、dbdump_*、templateparse*、struct_reflectfile 等，声明在 vendor/httpcli/*.hpp 里。

vendor/httpcli/ 下那批 .hpp 是生成器的模板和解析实现：controllerparse.hpp、ccontrollfun.hpp、dbtypes.hpp、modelfun.hpp、templateparse.hpp、typestatement.hpp、utility.hpp。

生成链挂在构建里：

add_custom_target(paozhu_codegen ALL)
    COMMAND paozhu_pre <源码根>
add_dependencies(paozhu paozhu_codegen)

所以每次构建都会跑一遍 paozhu_pre，但它用文件 hash 加 mtime 判断，没变化就不落盘。

注册表与业务层 common、controller

common/ 下有 14 个文件，大部分是手写的全局定义和注册表，只有一个文件是生成物。autocontrolmethod.hpp 就是 paozhu_pre 写出的注解路由注册表，输出路径写死在 vendor/httpcli/autopickmethod.cpp。autorestfulpaths.hpp 登记 RESTful 路径里的参数名，server.cpp 引入它，mini_project.sh 会在建新项目时重写。cost_define.h 放全局常量，httphook.cpp 是钩子层实现，json_reflect_headers.h 聚合 JSON 反射头。reghttpmethod.hpp 和 reghttpmethod_pre.hpp 是早期的手写注册表（REG_SYNC_SYNC 宏列表，server.cpp 引入）。剩下 mqtt_client_regmethod.hpp、mqtt_method_reg.hpp、redis_regmethod.hpp、sock_client_regmethod.hpp、sockets_method_reg.hpp、websockets_method_reg.hpp、ws_client_regmethod.hpp 分别是各长连接后端的注册表。

注册顺序值得记一下：server.cpp 里依次调用 _initauto_all_httputils()、_inithttpmethodregto()、_inithttpmethodregto_pre()，也就是"生成表 → 手写表 → 手写 pre 表"。reg_add 保留首次注册，所以同一个路径上手写项会被生成表挡住。paozhu_pre 知道这一点，生成时会把撞名打成 ROUTE-WARN。

controller/include/ 下的 100 个头都是生成出来的函数声明桩，不是手写代码。paozhu_pre 只在注解签名变化时重写它们，内部靠 md5 和 mtime 判断；CMake 在 configure 阶段对缺失的头只做 file(TOUCH) 占位。真正的实现在 controller/src/，按业务域分目录：admin/、superadmin/（含 superadmin/rbac/）、rbac/ 是后台与权限，oauth/、oauth_client/、github/ 是授权登录，saas.com/ 是多租户演示站，serverwatch.cpp 放监控端点，test_*.cpp 和 test*.cpp 是一批能力演示和回归用例（比如 test_maskcode.cpp 演示注解限流）。

数据层 orm、models、schema

orm/orm.h 是总入口，下面有 cms/、pg/、lite/ 三套模型域，分别对应 MySQL、PostgreSQL、SQLite。orm/cms/include/ 里的 64 个 *_base.h 是 paozhu_cli 生成的，文件头注释写着 This file is auto create from paozhu_cli。fk_child_opsql.cpp 和 fk_parent_opsql.cpp 是手写的联表查询。models/ 放模型行为实现，这批 .cpp 由 paozhu_cli 首次生成，之后不再覆盖——文件头写着"如果此文件存在不会自动覆盖，没有则会自动生成"，所以可以放心在里面写业务。schema/ 是建表 SQL。

连接池在 vendor/httpserver/src/orm_conn_pool.cpp 和 include/orm_conn_pool.h。池按 ioc 分槽，全局 max_pool 按槽数切分、余数给小槽、每槽保底 1（slot_max_of / slot_min_of），每槽一把独立的锁，不同 ioc 的线程不会抢同一把锁。配置项是 orm_ioc_num 和 orm_thread_pool_num，连接参数在 conf/orm.conf。ORM 也提供协程接口，orm_connect_mar.cpp、orm_query.cpp 里的查询可以直接 co_await。

可复用能力库 libs

libs/ 下 11 个子目录，全是手写源码。编译期由 CMakeLists.txt 里的递归 glob 收进主目标，头文件目录也递归加入 include 路径。

libs/rbac 是权限判定内核。rbac.h 提供 load_user_roles、load_role_perms、load_user_grants（一次六条查询把角色、权限、分配层、目录取完）、user_has_url、user_has_permscode 等；route_guard.cpp 是路由钩子，先看 adminid 判 401，再看 companyid 判 403，最后交给缓存；route_cache.cpp 的 allow() 按 (adminid, companyid) 做缓存，16 分片、4096 条、60 秒 TTL，装载时持分片锁做 singleflight，加载失败按 fail-closed 处理。route_cache.cpp 里还有个 stats()，目前没有调用点。

libs/oauth 是 OAuth 服务端侧，拆成 oauth_config（读 conf/oauth.conf）、oauth_store（令牌哈希、PKCE 验算、Basic 客户端认证）、oauth_audit（审计）。oauth_audit 的 audit_log() 把一行写进框架的错误日志队列，由 httpwatch 追加到 log/error.log。具体端点在 controller/src/oauth/：oauth_authorize.cpp、oauth_token.cpp、oauth_introspect.cpp、oauth_revoke.cpp、oauth_jwks.cpp、oauth_metadata.cpp、oauth_userinfo.cpp、oauth_bearerauth.cpp、oauth_client_add.cpp、oauth_purge.cpp。

libs/oauth_client 是通用 OAuth 2.x/2.1 客户端，不绑定具体授权服务器：填四个端点 URL 就能对 GitHub、Google 或自搭的 oauth 端点。它提供 PKCE、授权码/refresh/client_credentials 三种 grant，以及 introspect 和 revoke。libs/github 则是 GitHub 专用版，state 是 [adminid, client_id, rand32] 三段式，revoke 走 DELETE + Basic，scope 会强制追加 read:user，另外还有 github_api、github_config、github_crypto、github_store。

libs/webpay 是应用侧的支付逻辑：订单状态机（pending/paid/cancelled/refunded）、单号生成、按 wxorder 查单、异步查单、微信 V3 查单应答的落账判定，以及回调、证书闸门、支付宝/微信 V2/V3、二维码、token 这些文件。

libs/markdown 的 markdown2html 逐项处理块引用、粗体、链接、标题、分隔线、表格、图片、单行删除线、代码块、有序/无序列表，还维护目录和引用列表。libs/pinyin 做汉字转拼音，数据取自 pinyin-data，用二分查找。libs/ipdata 读 ip.data（ip2region 格式），用二分查找把 IP 落到国家/省/市。libs/department 是带 parentid 和 children 的组织树结构。libs/img 的 upload_images 处理图片、视频、base64 和表单文件上传，并列出已上传文件。libs/types 是 JSON 反射的样例类型，里面有嵌套对象和数组，用来演示反射生成。

可选能力模块 vendor/*

这些模块都是 include/ + src/ 的结构，默认关闭，源码通过 CMakeLists.txt 里的条件 glob 加入 paozhu_srcs，开关也集中在 CMakeLists.txt。下面按业务里用到的可能性从高到低分组。

文档与表格。 后台导出报表、导入 Excel、生成合同或通知、把页面存成 PDF，这类需求都在这一组。pzexcel 负责 xlsx 读写，支持多 sheet 和单元格样式；pzword 负责 docx 读写，能在 HTML 和 docx 之间互转，也能直接输出内存字节流；webpdf 是 PDF 渲染，公开头里能看到 HTMLRenderer，同目录还配了 HTML、CSS、SVG、TTF 四个解析器。业务只要涉及 Office 文档的导入导出，就开 ENABLE_OFFICE；需要 HTML 转 PDF 再单独开 ENABLE_PDF。

压缩、图片与图表。 打包下载或上传解包用 pzzip，它支持把 zip 直接写进内存 buffer，不必落临时文件；验证码和常规图片处理用 pzimage，它自带 PNG/JPEG 编解码，也能读 TrueType/OpenType 字形轮廓来画字；报表页要内嵌图形用 pzcharts，它直接输出 SVG，覆盖折线、平滑折线、柱状、散点、环形、雷达、仪表盘和漏斗。三个开关彼此独立，按实际用到的能力单独打开即可。

支付与短信。 需要走交易闭环时用 vendor/webpay，它是微信/支付宝的 SDK 封装，处理 V3 证书、平台证书和退款幂等键这些底层细节；订单状态机、回调、证书闸门这些应用侧逻辑在 libs/webpay，前面 libs 一节已经讲过。需要短信验证码或通知时用 sms，里面是阿里云和腾讯云两个客户端。两者分别对应 ENABLE_WEBPAY 和 ENABLE_SMS。

缓存与其它。 pzredis 是 Redis 客户端，redis_client 不持有连接，每条命令向配置段借一条、用完归还，同步和协程各有一套方法。做缓存、分布式锁或 pub/sub 时开 ENABLE_REDIS；框架层的 Redis 长连接客户端是另一个开关 ENABLE_REDIS_CLIENT，它要求 ENABLE_REDIS 同时打开，否则 configure 直接报错。

配置文件放在哪

线程相关的键是三组联动：cothreadnum 是 ioc 组数上限，实际组数取 min(cothreadnum, 核数)，低于 4 抬到 4；per_ioc_thread_num 是每组 run() 线程数，两者相乘就是总 I/O 线程数；orm_thread_pool_num 是 ORM 线程总数，配 0 表示用 hardware_concurrency()，上限 512，线程按 orm_ioc_num 均分，余数给下标小的 ioc。

几个容易看反的取值：upload_max_size 单位是字节，模板值 16777216 即 16 MiB，只有大于 1024 才真正启用限制，配 0 或留空表示不限，站点段可以覆盖；usehtmlcache 空或 0 打头算关、其它非空值算开，usehtmlcachetime 低于 10 秒按 10 秒算；rate_limit_second_num2 必须严格小于 rate_limit_second_num1，rate_limit_accept_wait_num 要比 rate_limit_new_wait_num 高 100 以上，否则会被改成后者的 2 倍；session_type 依次是 0 文件 / 1 内存 / 2 Redis / 3 Memcache / 4 预留；acme_every_day 允许 2–23，ocsp_intv_time 低于 3600 秒按 3600 算。

还有一组键在当前仓库的 C++ 代码里找不到读取点，配置文件里留着只是历史遗留，不要以为还要配：threadmax、threadmin、bmcport、staticfile_cache_num、modelspath、viewpath、controlpath、libspath、pluginspath。其中 bmcport 注释写着管理和监控端口，staticfile_cache_num 注释写着缓存条数，但两者都没有对应的运行时读取。

maxpool 和 minpool 的分法不对称，容易看错。连接池按 ioc 分槽，槽数等于 orm_ioc_num；maxpool 是该角色所有槽共享的全局预算，不是每槽额度，先算 maxpool / 槽数，余数逐个加给下标小的槽，每个槽至少 1，比如 maxpool = 20、4 个槽是每槽 5，maxpool = 10、3 个槽是 4/3/3；minpool 不参与切分，每个槽都独立预建 minpool 条，只受本槽配额限制，所以 maxpool = 5、4 个槽时配额是 2/1/1/1，minpool = 5 也只能各建 2/1/1/1 条。

另外两点：password 只允许可打印 ASCII 0x21–0x7E，含空格、控制字符或非 ASCII 的配置会被跳过并打错误日志；SQLite 的 host 填数据库文件路径，port、dbname、账号密码留空即可，ssl、sslverify、sslhost 只在 MySQL/PostgreSQL 上用。

只有同时满足两个条件才会真正触发：server.conf 里对应站点的 acme_auto = 1，且这里的 email 非空。缺邮箱时任务会直接返回，只在 log/acme_log/ 里记一行。另外 cert_path 虽然写着 ./conf，当前代码实际把证书复制到 server.conf 所在目录，这一项读了但没有参与复制路径。

签发流程在 httpwatch 里按天触发：acme_every_day 指定小时，前一小时先把当天标记置上，到点起一个 detached 线程跑 acme_task。任务逐个站点看 acme_auto，拼出主域名和 www 域名，先检查 acme_path/<主域名>/cert.pem 的剩余天数，超过 days_remain 就跳过。需要申请时走完 ACME 的账户、订单、HTTP-01 验证、CSR 和 finalize，产物写到 acme_path/<主域名>/ 下的 privkey.pem、cert.pem、fullchain.pem。成功后把 fullchain.pem 复制成 conf/<主域名>.pem、privkey.pem 复制成 conf/<主域名>.key、cert.pem 复制成 conf/<主域名>.crt，并写 restart_ssl_config 让 SSL 配置重载。server.conf 里的 certificate_chain_file、private_key_file、chain_crt_file 就是按这些文件名填的，路径相对于 server.conf 所在目录。

注解路由怎么写

路由声明写在业务函数上方的注释里，格式是 //@urlpath(pre, urlpath)，可以带 :mask 后缀区分 HTTP method：

//@urlpath(superadmin_islogin,superadmin/rbac/perm)
std::string superadmin_rbac_perm_list(std::shared_ptr<httppeer> peer)

这个例子来自 controller/src/superadmin/rbac/rbacperm.cpp。

paozhu_pre 扫描后会生成 reg_raw(site, path, pre_sync, co_pre, reg_sync, co_reg, mask_code) 形式的表项（落在 common/autocontrolmethod.hpp）。带 :param 的路径同时把参数名登记到 common/autorestfulpaths.hpp。注解还能带限流参数，写法是 //@urlpath(...):ratelimit(time,num)，示例在 controller/src/test_maskcode.cpp，解析结果进路由项的 rate_time 和 rate_num。

如果不想用注解，common/reghttpmethod.hpp 还留了纯手写的 REG_SYNC_SYNC 注册方式，里面有一个 /helloworld 的内联 lambda。但它的注册顺序在生成表之后，同名路径会被生成表覆盖，适合临时验证，不适合正式接口。

新增一个接口要动哪些地方

正常路径很短：在 controller/src/ 找个合适的文件写函数，函数上写注解，然后构建。构建时 paozhu_codegen 会跑 paozhu_pre，它更新 controller/include/ 里的声明桩和 common/autocontrolmethod.hpp 里的注册项；进程启动时把生成表注册进去，请求就能命中。

如果接口需要限流，在注解后面加 ratelimit(time,num)；如果接口要进 RBAC，给路由一个非 0 的 mask_code，并在权限表里配一条同 urlpath、同 maskcode 的授权行——libs/rbac/rbac.h 的注释说明了判定是"路由的 maskcode 必须与用户生效授权里某一条精确相等"。

运行期加载 .so

如果编译时打开了 ENABLE_VIEWSO 或 ENABLE_MODELSO，module/view 和 module/controller 下的 .so 可以在运行期被加载。视图侧入口是 loadview / loadviewso，控制器侧入口在 loadmodule.cpp 里。配置里把 viewsopath、controlsopath 指到对应目录即可。module/ 下的文件是构建产物或手工部署的动态库，不是源码。

六、测试与自检

测试默认不构建，打开 -DENABLE_TESTS=ON 才进 tests/。tests/CMakeLists.txt 的约定是：为 tests/*.cpp 和 tests/orm/*.cpp 自动生成同名可执行目标，pool_thread 是例外。现有用例包括 test_framework_smoke.cpp（框架冒烟）、test_http2_ring_queue.cpp 和 test_http2_headers_split.cpp（HTTP/2 发送环与头拆分）、test_router_hooks.cpp（路由钩子）、test_jwt_smoke.cpp（JWT）、test_filename_safety.cpp（文件名安全）、test_pzexcel_p2.cpp 和 test_pzzip.cpp（可选子模块）。另有 http1_consume/、multipart_boundary/、multipart_part_headers/、postform/、raw_post_fastpath/、orm/ 这些针对协议解析的子目录。

自检端点都在 controller/src/serverwatch.cpp：/metrics 输出 Prometheus 文本格式；/paozhu_status 是旧版自定义仪表盘；/frametasks_timeloop 看框架定时任务。后台登录入口是 admin/login 和带限流的 admin/loginpost:ratelimit(60,5)，实现在 controller/src/admin/main.cpp；超管入口是 superadmin/login，实现在 controller/src/superadmin/supermain.cpp。

七、关于这份文档的核验范围

正文里的结论基本都是读源码或读目录得到的：构建配置、线程拓扑、路由链路、HTTP/2 发送队列、RBAC 缓存、限流、生成物来源、server.conf 各项、自检端点，都能按文末列出的文件回查。libs/ 和 vendor/ 下各模块的职责这一轮也补读了公开头文件，oauth、oauth_client、github、webpay、markdown、pinyin、ipdata、department、img、types、pzexcel、pzword、webpdf、pzimage、pzcharts、pzzip、pzredis、sms 的描述都有头文件里的函数签名或注释支撑。

还没逐行读实现的部分有六处，看的时候别把这段之外的相关描述当成逐行核实过的事实：

  • ENABLE_MODELSO 打开后，module/controller/testviewso.so 里的函数名怎样映射到路由，只确认了开关和目录的对应关系，没有把加载后的注册链走完。

  • view/ 模板到 viewsrc/view/*.cpp 的生成语法和更新触发条件，只确认了文件头标记和解析器位置。
  • tests/*.cpp 各用例的具体断言，只按文件名和 tests/CMakeLists.txt 的约定描述。
  • startup/main_dev.cpp 与 startup/main_daemon.cpp 除 fork 之外是否完全同链，没有逐行对比。
  • pzexcel、pzword、webpdf 的内部实现深度，只读了公开头文件，没有逐个走读写流程。
