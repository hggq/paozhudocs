Paozhu (Firecracker) Web Framework

Paozhu is a web framework written in C++. Source code: https://github.com/hggq/paozhu. What stands out first is that one executable ships with everything: HTTP/1.1, HTTP/2, WebSocket, raw TCP, an MQTT client, a Redis client, an ORM, template views, and static file serving all live in the same process, and compile-time switches trim whatever you do not need.

Here is the shortest example: the handler returns a coroutine task, writing to peer->output produces the response body, and the route is declared by the annotation above the function:

Once the server is running, open http://localhost/hello in a browser.

#include "httppeer.h"
#include "testhello.h"
namespace http
{
//@urlpath(null,hello)
asio::awaitable<std::string> testhello(std::shared_ptr<httppeer> peer)
{
    peer->output = "Hello, world!";
    co_return "";
}
 
}// namespace http

hello is an annotation function. testhello.h does not need to be created manually — it is generated automatically during cmake make. co_return ""; is an advanced feature: returning a value continues to the next annotation function, while returning an empty string means completion.

1. What It Is

Several design choices are visible directly in the source layout.

The network layer is built on standalone Asio. The server holds an asio::io_context rather than a home-grown event loop, so most of the Asio ecosystem can be plugged in as-is.

I/O and business logic are separated. I/O threads do only accept, read, and write; synchronous handlers are dispatched to a dedicated business thread pool, clientrunpool. Blocking code in a handler therefore ties up the business pool, never the network threads.

I/O loops are grouped by core count rather than collapsed into one loop. The process owns a set of io_context instances, each connection is assigned to one of them by round-robin, and each ioc runs several threads. Section 3 covers the details.

Coroutines are the entry point of the routing layer. Route matching and dispatch start at router::co_resolve, and both pre-handlers and handlers have synchronous and coroutine slots, so business code can choose either style.

HTTP/2 is implemented in-house. Frame parsing, the Huffman coding used by HPACK, the per-connection send ring, the global send queue, and flow control all live in this repository rather than behind a third-party wrapper.

Routes are declared in comments and compiled into a registry. A business function carries a //@urlpath(...) comment; at build time paozhu_pre scans it and generates the registry plus function declaration stubs.

Capabilities are delivered as one bundle. The ORM, connection pool, RBAC, OAuth, payments, Excel/Word/PDF, images, compression, charts, SMS, and the Redis client all live under vendor/ and libs/ in the same repository. They are off by default; their CMake options default to OFF in CMakeLists.txt.

The repository roughly splits into four layers. vendor/httpserver is the framework proper. The other vendor/ subdirectories and libs/ are reusable capabilities. common/, orm/, models/, and viewsrc/ form the glue between framework and business code. controller/, view/, www/, and module/ are sample business code that can be deleted outright. mini_project.sh makes this split concrete: it removes demo directories such as controller/src/admin, github, and oauth, leaving only the framework core.

2. Getting It Running

Dependencies and Build

Dependencies are listed in vcpkg.json: openssl, brotli, asio, zlib, and sqlite3, plus a gd feature that pulls in pkgconf, libgd, freetype, libpng, and libqrencode. With vcpkg, enable -DENABLE_VCPKG=ON and pass CMAKE_TOOLCHAIN_FILE; README_CN.md covers the details. The repository also ships an xmake.lua for those who prefer xmake.

A normal build takes three steps:

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./bin/paozhu                 # you can also pass ./bin/paozhu /path/to/server.conf

bin/ currently contains three artifacts: paozhu, paozhu_cli, and paozhu_pre. Benchmark-related code requires an explicit -DENABLE_BENCHMARK=ON.

The build produces four CMake targets: the main program paozhu, the database/model tool paozhu_cli, the annotation-route generator paozhu_pre, and paozhu_codegen, which runs on every build.

The main program's source set is assembled from several globs:

set(paozhu_srcs
  ${common_list} ${viewsrc_list} ${framework_cpps} ${orm_list}
  ${reflect_list} ${src_list} ${source_list} ${controller_list})

reflect_list picks up libs/*.cpp recursively.

Entry Points

A Release build uses startup/main_daemon.cpp; other build configurations switch automatically to startup/main_dev.cpp. The daemon version first treats argv[1] as the path to, or directory containing, server.conf, then forks inside init_daemon(): the child runs get_server_app(), http::rbac::install_route_guard(), and httpmy.run(argv_str), while the parent loops on wait and respawns the child on SIGCHLD. The foreground version follows the same run() path without forking.

Inside run(), the sequence is: read configuration, create iocs and threads, start accepting, register routes, enter the event loop.

3. How a Request Travels Through It

How the Threads Are Split

The process has four classes of threads. Here is the overview:

Thread class Count Responsibility
accept threads 2 (one HTTP, one SSL) blocking accept; hand new connections to an ioc
I/O threads ioc count × run() threads per ioc run io_context::run(); connection I/O and protocol parsing
side threads one httpwatch, http2_send_loop_num HTTP/2 senders (minimum 2), one websocket_loop, one ratelimiter periodic inspection, draining the HTTP/2 send queue, connection-level rate limiting
business pool hardware_concurrency() + 2 runs synchronous handlers

The number of I/O threads is computed in two layers. The ioc count is min(cothreadnum, hardware_concurrency()), raised to 4 if it comes out lower; each ioc then starts per_ioc_thread_num run() threads. The comment in conf/server.conf states the formula directly: cothreadnum * per_ioc_thread_num = threads.

io_contexts[0] has a second role: it is also the compatibility member io_context, and the framework's own timer loop, synchronous connection acquisition, and client_context all stay on it.

Serialization happens only within a connection. A new connection is assigned to an ioc by session_ioc_cursor++ % io_contexts.size(), and the connection binds its own asio::strand, which keeps protocol handling on that one connection in order. There is no such ordering between different connections.

The httppeer pool is not a thread; it appears here only because it is easy to confuse with one. acquire_peer() takes a reusable object, and when the last reference is released the object goes back through reset_for_reuse(). The cap is PEER_POOL_MAX = 512, or 4096 in a BENCHMARK build.

A connection passes through these threads from arrival to departure:

  1. An accept thread picks it up and hands it to an ioc.
  2. From then on, its reads, writes, and protocol parsing run on that ioc's run() threads, with the strand keeping the connection serialized.
  3. When a synchronous handler is hit, the work is dispatched to the business pool; a coroutine handler simply awaits in place and keeps advancing on the ioc thread.
  4. On output, HTTP/1.1 is written back directly by the I/O thread, while HTTP/2 goes to the fixed http2_send_queue_loop threads that drain the send queue.
  5. Side threads only perform periodic inspection, rate limiting, and queue draining; they never process business logic.

Route Matching and Dispatch

From accept to response, the main path looks like this:

accept (side thread)
  → pick an ioc by round-robin, bind the connection to a strand
  → parse: HTTP/1.1 via http_parse.cpp, HTTP/2 via http2_parse.cpp
  → take an httppeer (acquire_peer)
  → router::co_resolve
        ├─ exact lookup, then prefix fallback (up to 6 segments)
        ├─ write the matched mask_code into the peer
        ├─ annotation-level rate limiting
        ├─ RBAC hook, only when mask_code is non-zero
        └─ pre → handler (the synchronous path goes to the business pool; coroutines await in place)
  → write the response: HTTP/1.1 directly, HTTP/2 through the send queue

router.cpp holds two parallel implementations: one for the synchronous chain, one for the coroutine chain inside co_resolve. A comment in router.h explicitly requires the pre/handler branches of the two chains to behave identically; changing one means changing the other.

HTTP/1.1 and HTTP/2 Output

HTTP/1.1 parsing is in-house, centered on vendor/httpserver/src/http_parse.cpp and supported by request.cpp and httppeer.cpp. Requests and responses are serial, with no pipelining.

HTTP/2 is a complete implementation, and its files all sit in vendor/httpserver/src/: http2_parse.cpp handles frame parsing and the connection state machine, http2_frame.cpp/http2_define.cpp define frame structure and constants, http2_huffman.cpp is the Huffman codec used by HPACK, http2_ring_queue.cpp is the fixed-size per-connection send ring, http2_send_queue.cpp is the global send queue, and http2_flow.h holds the flow-control window definitions.

A few design points matter:

  • Each connection has a 32-slot fixed ring, CONST_HTTP2_RING_QUEUE_CAPACITY = 32. A compile-time check requires it to be a power of two and to fit in an unsigned char; head_ and tail_ are atomic indices, with a separate bytes backlog counter.
  • Send objects have an explicit state machine: own_state says whether an object is in the pool, the global queue, thread-private storage, or parked, while block_reason records why it was blocked.
  • Blocked objects are not polled repeatedly. They are parked in parked_list and reattached by park() / detach_parked() / reattach_parked() on three kinds of events: a window change, a SETTINGS frame, or a ring slot becoming free.
  • A stream is reset after "120 seconds with no progress", not after an ordinary idle timeout. The constant is CONST_HTTP2_SEND_NO_PROGRESS_TIMEOUT = 120, and the check lives in server.cpp.
  • The switch is http2_enable = 1 in conf/server.conf.

4. What Each Module Does

Framework Core: vendor/httpserver

This directory has include/ and src/, with 85 .cpp files under src/. Responsibilities group as follows:

  • Server and lifecycle: server.cpp, serverconfig.cpp, client_context.cpp, resident_stop.cpp — startup, configuration, thread orchestration, and graceful shutdown.
  • Connections and protocols: http_parse.cpp, http_header.cpp, http_domain.cpp, rpc_parse.cpp, client_session.cpp — HTTP/1.1 parsing, host routing, and RPC parsing.
  • HTTP/2: the file group listed in Section 3.
  • Request model: httppeer.cpp, request.cpp, cookie.cpp, session_id.cpp.
  • Routing: router.cpp, viewmethold_reg.cpp.
  • ORM and connections: orm_common.cpp, orm_conn_pool.cpp, orm_connect_mar.cpp, orm_query.cpp, mysql_conn.cpp, pg_conn.cpp, sqlite_conn.cpp.
  • Thread primitives: threadpool.cpp, atomic_count.cpp, atomic_guard.cpp.
  • Static files: file_get_content.cpp, gzip.cpp, https_brotli.cpp, mime.cpp, directory_fun.cpp.
  • Long-lived connections: ws_*.cpp, http_websocket_client.cpp, http_socket*.cpp, mqtt_*.cpp, sock_subpub_reg.cpp.
  • Security and authentication: jwt.cpp, acme_*.cpp, ocsp_check.cpp, base64.cpp, md5.cpp.
  • Utilities: parse_ini.cpp, str_fun.cpp, urlcode.cpp, unicode.cpp, datetime.cpp, qrcode.cpp, send_email.cpp, fastcgi.cpp, loadmodule.cpp, loadviewso.cpp.

Two headers in include/ are easy to misread. request.h is actually an embedded JSON micro-object, obj_val, not an HTTP request class; the real request/response carrier is httppeer.h. httphook.h, together with common/httphook.cpp, forms the hook layer where routing, authentication, and rate limiting attach. In addition, orm_cache.hpp, mysqlorm.hpp, postgresqlorm.hpp, and sqliteorm.hpp are the ORM's template facades.

The Two Generators: vendor/httpcli

This directory builds two executables with completely different jobs.

paozhu_pre is the annotation-route generator. Its sources are vendor/httpcli/autopickmethod.cpp plus vendor/httpserver/src/md5.cpp. It scans annotations under controller/src and writes common/autocontrolmethod.hpp and controller/include/*.h.

paozhu_cli is the database/model tool. Its sources are vendor/httpcli/http_cli.cpp plus the ORM connection and model sources. Its capabilities include dbcreate, dbconvert, dbschema_check, dbdump_*, templateparse*, and struct_reflectfile, declared in vendor/httpcli/*.hpp.

The .hpp files under vendor/httpcli/ are the generators' templates and parsing implementations: controllerparse.hpp, ccontrollfun.hpp, dbtypes.hpp, modelfun.hpp, templateparse.hpp, typestatement.hpp, and utility.hpp.

The generation chain is wired into the build:

add_custom_target(paozhu_codegen ALL)
    COMMAND paozhu_pre <source root>
add_dependencies(paozhu paozhu_codegen)

Every build therefore runs paozhu_pre, but it compares file hashes and mtimes and writes nothing when there are no changes.

Registries and the Business Layer: common, controller

common/ holds 14 files, mostly hand-written global definitions and registries; only one file is generated. autocontrolmethod.hpp is the annotation-route registry written by paozhu_pre, and its output path is hard-coded in vendor/httpcli/autopickmethod.cpp. autorestfulpaths.hpp records parameter names for RESTful paths; server.cpp includes it, and mini_project.sh rewrites it when creating a new project. cost_define.h holds global constants, httphook.cpp implements the hook layer, and json_reflect_headers.h aggregates the JSON reflection headers. reghttpmethod.hpp and reghttpmethod_pre.hpp are the early hand-written registries (a REG_SYNC_SYNC macro list, included by server.cpp). The remaining files — mqtt_client_regmethod.hpp, mqtt_method_reg.hpp, redis_regmethod.hpp, sock_client_regmethod.hpp, sockets_method_reg.hpp, websockets_method_reg.hpp, and ws_client_regmethod.hpp — are registries for the various long-lived-connection backends.

Registration order is worth remembering. server.cpp calls _initauto_all_httputils(), _inithttpmethodregto(), and _inithttpmethodregto_pre() in that order — generated table, then hand-written table, then hand-written pre table. reg_add keeps the first registration, so a hand-written entry for the same path is shadowed by the generated table. paozhu_pre knows this and reports such collisions as ROUTE-WARN during generation.

The 100 headers under controller/include/ are generated function declaration stubs, not hand-written code. paozhu_pre rewrites them only when an annotation signature changes, using md5 and mtime to decide; during configure, CMake merely file(TOUCH)es any missing header as a placeholder. The real implementations live in controller/src/, split by business domain: admin/, superadmin/ (including superadmin/rbac/), and rbac/ for back-office and permissions; oauth/, oauth_client/, and github/ for authorization and login; saas.com/ for a multi-tenant demo site; serverwatch.cpp for monitoring endpoints; and the many test_*.cpp and test*.cpp files for capability demos and regression cases (for example, test_maskcode.cpp demonstrates annotation rate limiting).

Data Layer: orm, models, schema

orm/orm.h is the entry point. Below it are three model domains — cms/, pg/, and lite/ — corresponding to MySQL, PostgreSQL, and SQLite. The 64 *_base.h files under orm/cms/include/ are generated by paozhu_cli; their headers say This file is auto create from paozhu_cli. fk_child_opsql.cpp and fk_parent_opsql.cpp are hand-written join queries. models/ holds model behavior: these .cpp files are generated by paozhu_cli once and never overwritten afterwards — the file header states that an existing file is kept and a missing one is generated — so it is safe to write business logic there. schema/ contains the table-creation SQL.

The connection pool lives in vendor/httpserver/src/orm_conn_pool.cpp and include/orm_conn_pool.h. The pool is sharded by ioc; the global max_pool is split by shard count, the remainder goes to smaller shards, and every shard gets at least one slot (slot_max_of / slot_min_of). Each shard has its own lock, so threads on different iocs never contend for the same one. The configuration keys are orm_ioc_num and orm_thread_pool_num, and connection parameters live in conf/orm.conf. The ORM also exposes a coroutine interface: queries in orm_connect_mar.cpp and orm_query.cpp can be awaited directly.

Reusable Capability Libraries: libs

libs/ has 11 subdirectories, all hand-written. At build time they are pulled into the main target by a recursive glob in CMakeLists.txt, and their header directories are added recursively to the include path.

libs/rbac is the permission-decision core. rbac.h provides load_user_roles, load_role_perms, load_user_grants (six queries in one pass to fetch roles, permissions, assignment layers, and directories), user_has_url, and user_has_permscode. route_guard.cpp is the route hook: it returns 401 when adminid is missing, 403 when companyid is missing, and otherwise defers to the cache. The allow() function in route_cache.cpp caches by (adminid, companyid) with 16 shards, 4096 entries, and a 60-second TTL; loading holds the shard lock for single-flight behavior, and a load failure is treated as fail-closed. route_cache.cpp also has a stats() function that currently has no callers.

libs/oauth is the server side of OAuth, split into oauth_config (reads conf/oauth.conf), oauth_store (token hashing, PKCE verification, Basic client authentication), and oauth_audit (auditing). oauth_audit's audit_log() writes a line into the framework's error-log queue, and httpwatch appends it to log/error.log. The endpoints themselves live in controller/src/oauth/: oauth_authorize.cpp, oauth_token.cpp, oauth_introspect.cpp, oauth_revoke.cpp, oauth_jwks.cpp, oauth_metadata.cpp, oauth_userinfo.cpp, oauth_bearerauth.cpp, oauth_client_add.cpp, and oauth_purge.cpp.

libs/oauth_client is a generic OAuth 2.x/2.1 client that is not tied to a particular authorization server: fill in four endpoint URLs and it can talk to GitHub, Google, or a self-hosted oauth endpoint. It supports PKCE, three grants (authorization code, refresh, and client_credentials), and introspect and revoke. libs/github is the GitHub-specific variant: its state is the three-part [adminid, client_id, rand32], revoke uses DELETE + Basic, and the scope always has read:user appended. It also includes github_api, github_config, github_crypto, and github_store.

libs/webpay is the application-side payment logic: the order state machine (pending/paid/cancelled/refunded), order-number generation, lookup by wxorder, asynchronous lookup, and settlement decisions for WeChat V3 lookup responses, along with files for callbacks, the certificate gate, Alipay/WeChat V2/V3, QR codes, and tokens.

libs/markdown's markdown2html handles block quotes, bold, links, headings, horizontal rules, tables, images, single-line strikethrough, code blocks, and ordered/unordered lists, and also maintains a table of contents and a reference list. libs/pinyin converts Han characters to pinyin using data from pinyin-data and binary search. libs/ipdata reads ip.data (ip2region format) and maps an IP to country/province/city by binary search. libs/department is an organization-tree structure with parentid and children. libs/img's upload_images handles image, video, base64, and form-file uploads and lists already uploaded files. libs/types contains sample types for JSON reflection, including nested objects and arrays, to demonstrate reflection generation.

Optional Capability Modules: vendor/*

These modules all follow the include/ + src/ layout and are off by default. Their sources are added to paozhu_srcs by conditional globs in CMakeLists.txt, and their switches are also centralized there. They are grouped below from most to least likely to be needed in a real application.

Documents and spreadsheets. This group covers back-office report exports, Excel imports, generated contracts or notices, and saving pages as PDF. pzexcel handles xlsx reading and writing, multiple sheets, and cell styles. pzword handles docx reading and writing, converts between HTML and docx, and can output an in-memory byte stream directly. webpdf is the PDF renderer; its public header exposes HTMLRenderer, and the same directory includes four parsers for HTML, CSS, SVG, and TTF. Turn on ENABLE_OFFICE whenever the application imports or exports Office documents, and enable ENABLE_PDF separately for HTML-to-PDF.

Compression, images, and charts. Use pzzip for packaged downloads or unpacking uploads; it can write a zip straight into an in-memory buffer without touching a temporary file. Use pzimage for captchas and ordinary image processing; it bundles PNG/JPEG codecs and can draw glyphs from TrueType/OpenType outlines. Use pzcharts for charts embedded in report pages; it emits SVG directly and covers line, smoothed line, bar, scatter, donut, radar, gauge, and funnel charts. The three switches are independent, so enable only the capabilities you actually use.

Payments and SMS. Use vendor/webpay when a transaction flow is needed; it wraps the WeChat/Alipay SDKs and handles low-level details such as V3 certificates, platform certificates, and refund idempotency keys. The application-side logic — order state machine, callbacks, certificate gate — lives in libs/webpay, as covered in the libs section above. Use sms for verification codes or notifications; it contains Alibaba Cloud and Tencent Cloud clients. They correspond to ENABLE_WEBPAY and ENABLE_SMS respectively.

Caching and other. pzredis is a Redis client. redis_client does not hold a connection: each command borrows one from a configuration section and returns it when done, with both synchronous and coroutine APIs. Enable ENABLE_REDIS for caching, distributed locks, or pub/sub. The framework-level Redis long-connection client is a separate switch, ENABLE_REDIS_CLIENT, which requires ENABLE_REDIS to be on as well; otherwise configure fails immediately.

Long-Lived Connections

The repository has four standalone directories — websockets/, sockets/, mqtt/, and redis/ — that are mainly demo sites and examples. The real protocol implementations live in vendor/httpserver/src/: WebSocket in ws_conn.cpp, ws_handshake.cpp, ws_parser.cpp, ws_wire.cpp, and websockets_callback.cpp; raw TCP in http_socket.cpp, http_socket_client.cpp, and sock_subpub_reg.cpp; MQTT in mqtt_frame.cpp, mqtt_session.cpp, mqtt_reg.cpp, mqtt_subpub_reg.cpp, and http_mqtt_client.cpp; and the Redis long connection in http_rpcclient.cpp plus the client in vendor/pzredis. The switches are ENABLE_WEBSOCKETS_CLIENT, ENABLE_SOCKETS_CLIENT, and ENABLE_MQTT_CLIENT (on by default), and ENABLE_REDIS_CLIENT (off by default, and requiring ENABLE_REDIS). The business-side registries are the *_regmethod.hpp group in common/.

Views, Static Files, and .so Hot Loading

view/ contains hand-written HTML templates, split by business domain into home/, admin/, cms/, login/, oauth/, superadmin/, and others. viewsrc/include/viewsrc.h and viewsrc/include/regviewmethod.hpp are the hand-written registration entry points. viewsrc/view/**.cpp is C++ generated by the template parser — its files carry the header //This file create by paozhu (see viewsrc/view/home/header.cpp) — and currently includes home/header.cpp, oauth/consent.cpp, oauth_client/page.cpp, superadmin/*.cpp, and others. The parser lives in vendor/httpcli/templateparse.hpp.

www/default/ is the static-site root, configured by wwwpath = ./www/default.

module/ is the shared-library directory, containing module/controller/testviewso.so and module/view/{admin,cms,home,login}/*.so. Each switch owns one side: ENABLE_VIEWSO uses viewsopath to point at module/view, while ENABLE_MODELSO uses controlsopath to point at module/controller. The loading logic is in loadmodule.cpp and loadviewso.cpp; it opens .so files with pz::dll::library and keeps the library handle alongside the cached function pointer so the pointer does not become invalid after dlclose.

5. Configuration and Extension

Where the Config Files Live

conf/ is split by subsystem: server.conf, orm.conf, redis.conf, mqtt.conf, sockets.conf, websockets.conf, oauth.conf, webpay.conf, acme.conf, github.conf, and test.conf, plus certificate and key files. The three you will touch most are server.conf for the process and its sites, orm.conf for database connections, and acme.conf for automatic certificate issuance. The rest matter only when the corresponding subsystem is enabled.

server.conf

This is the main configuration, read once at startup. It consists of a [default] global section plus any number of site sections named after a host (the file uses [www.hggq.com]). A site section can override wwwpath, http2_enable, acme_auto, upload_max_size, cors_domain, static_pre, fastcgi_host, fastcgi_port, siteid, and groupid. Three thread settings work together. cothreadnum is the upper bound on the ioc count; the actual count is min(cothreadnum, core count), raised to 4 if lower. per_ioc_thread_num is the number of run() threads per ioc, and the product of the two is the total I/O thread count. orm_thread_pool_num is the total ORM thread count; 0 means hardware_concurrency(), capped at 512, split evenly across orm_ioc_num iocs with the remainder going to lower-index iocs.

A few values are easy to read backwards. upload_max_size is in bytes; the template value 16777216 is 16 MiB, the limit is enforced only when it is greater than 1024, and 0 or empty means unlimited, with per-site overrides. For usehtmlcache, empty or a value starting with 0 means off and any other non-empty value means on; usehtmlcachetime below 10 seconds is treated as 10. rate_limit_second_num2 must be strictly less than rate_limit_second_num1, and rate_limit_accept_wait_num must exceed rate_limit_new_wait_num by more than 100, otherwise it is reset to twice that value. session_type is 0 file / 1 memory / 2 Redis / 3 Memcache / 4 reserved. acme_every_day accepts 2–23, and ocsp_intv_time below 3600 seconds is treated as 3600.

Another group of keys has no read site anywhere in this repository's C++ code. They remain in the file for historical reasons, so do not assume they still need configuring: threadmax, threadmin, bmcport, staticfile_cache_num, modelspath, viewpath, controlpath, libspath, and pluginspath. The comments describe bmcport as a management and monitoring port and staticfile_cache_num as a cache-entry count, but neither has a runtime reader.

maxpool and minpool are split asymmetrically, which is easy to misread. The pool is sharded by ioc, with the slot count equal to orm_ioc_num. maxpool is a global budget shared by all slots for that role, not a per-slot quota: compute maxpool / slot count, hand the remainder one by one to the lowest-index slots, and give every slot at least 1 — for example, maxpool = 20 with 4 slots gives 5 per slot, and maxpool = 10 with 3 slots gives 4/3/3. minpool is not divided: every slot pre-builds minpool connections, capped by that slot's own quota, so with maxpool = 5 and 4 slots the quotas are 2/1/1/1 and minpool = 5 still yields only 2/1/1/1.

Two more points. password may contain only printable ASCII 0x21–0x7E; a block containing spaces, control characters, or non-ASCII is skipped and logged as an error. For SQLite, put the database file path in host and leave port, dbname, and the credentials empty; ssl, sslverify, and sslhost apply only to MySQL and PostgreSQL.

acme.conf

This file controls automatic certificate issuance. It targets ZeroSSL's ACME endpoints by default and uses HTTP-01 validation. The file follows verbatim:

[zerossl]

email      =

Issuance only runs when both conditions hold: the site has acme_auto = 1 in server.conf, and email here is non-empty. Without an email the task returns immediately and only writes a line under log/acme_log/. Also, although cert_path is set to ./conf, the current code actually copies certificates into the directory containing server.conf, so this value is read but does not affect the copy target.

The issuance flow is driven daily from httpwatch: acme_every_day picks the hour, the preceding hour sets the day's flag, and a detached thread runs acme_task when the hour arrives. The task walks the sites, checks acme_auto, builds the primary and www domains, and reads the remaining validity of acme_path/<primary_domain>/cert.pem; if it exceeds days_remain, the site is skipped. Otherwise the task goes through the ACME account, order, HTTP-01 validation, CSR, and finalize steps, writing privkey.pem, cert.pem, and fullchain.pem under acme_path/<primary_domain>/. On success it copies fullchain.pem to conf/<primary_domain>.pem, privkey.pem to conf/<primary_domain>.key, and cert.pem to conf/<primary_domain>.crt, then writes restart_ssl_config so the SSL configuration reloads. The certificate_chain_file, private_key_file, and chain_crt_file entries in server.conf use exactly these file names, resolved relative to the directory containing server.conf.

Writing Annotation Routes

Routes are declared in the comment above a business function, in the form //@urlpath(pre, urlpath), optionally with a :mask suffix to distinguish HTTP methods:

//@urlpath(superadmin_islogin,superadmin/rbac/perm)
std::string superadmin_rbac_perm_list(std::shared_ptr<httppeer> peer)

This example comes from controller/src/superadmin/rbac/rbacperm.cpp.

After scanning, paozhu_pre generates entries of the form reg_raw(site, path, pre_sync, co_pre, reg_sync, co_reg, mask_code), which land in common/autocontrolmethod.hpp. A path containing :param also registers its parameter names in common/autorestfulpaths.hpp. Annotations can also carry rate-limit parameters with //@urlpath(...):ratelimit(time,num); an example is in controller/src/test_maskcode.cpp, and the parsed values go into the route entry's rate_time and rate_num.

If annotations are not desired, common/reghttpmethod.hpp still offers the purely hand-written REG_SYNC_SYNC registration style, including an inline lambda for /helloworld. Its registrations come after the generated table, however, so a path with the same name is shadowed by the generated entry. It is suitable for temporary experiments, not for production endpoints.

Adding an Endpoint

The normal path is short: pick a suitable file under controller/src/, write the function with an annotation, and build. During the build, paozhu_codegen runs paozhu_pre, which updates the declaration stubs in controller/include/ and the registry entries in common/autocontrolmethod.hpp; when the process starts, it registers the generated table and the request can be routed.

If the endpoint needs rate limiting, add ratelimit(time,num) after the annotation. If it needs RBAC, give the route a non-zero mask_code and add an authorization row in the permission table with the same urlpath and maskcode — a comment in libs/rbac/rbac.h explains that the check requires the route's maskcode to exactly equal one of the user's effective grants.

Loading .so at Runtime

If ENABLE_VIEWSO or ENABLE_MODELSO is enabled at compile time, the .so files under module/view and module/controller can be loaded at runtime. The view-side entry points are loadview / loadviewso, and the controller-side entry point is in loadmodule.cpp. Point viewsopath and controlsopath at the corresponding directories in the configuration. Files under module/ are build artifacts or manually deployed shared libraries, not source.

6. Tests and Self-Checks

Tests are not built by default; they are included only with -DENABLE_TESTS=ON. The convention in tests/CMakeLists.txt is to generate an executable target with the same name for each tests/*.cpp and tests/orm/*.cpp, with pool_thread as the exception. Existing cases include test_framework_smoke.cpp (framework smoke test), test_http2_ring_queue.cpp and test_http2_headers_split.cpp (HTTP/2 send ring and header splitting), test_router_hooks.cpp (route hooks), test_jwt_smoke.cpp (JWT), test_filename_safety.cpp (filename safety), and test_pzexcel_p2.cpp and test_pzzip.cpp (optional submodules). There are also subdirectories for protocol parsing: http1_consume/, multipart_boundary/, multipart_part_headers/, postform/, raw_post_fastpath/, and orm/.

The self-check endpoints are all in controller/src/serverwatch.cpp: /metrics emits Prometheus text format, /paozhu_status is the older custom dashboard, and /frametasks_timeloop shows framework timer tasks. The back-office login endpoints are admin/login and the rate-limited admin/loginpost:ratelimit(60,5), implemented in controller/src/admin/main.cpp; the super-admin entry is superadmin/login, implemented in controller/src/superadmin/supermain.cpp.

7. Scope of Verification

The conclusions in this document were largely obtained by reading source and directory contents: build configuration, thread topology, the routing path, the HTTP/2 send queue, the RBAC cache, rate limiting, generated artifacts, the server.conf keys, and the self-check endpoints can all be traced through the files listed at the end. This round also covered the public headers of the modules under libs/ and vendor/; the descriptions of oauth, oauth_client, github, webpay, markdown, pinyin, ipdata, department, img, types, pzexcel, pzword, webpdf, pzimage, pzcharts, pzzip, pzredis, and sms are backed by function signatures or comments in those headers.

Six areas were not read implementation-by-implementation. Do not treat descriptions outside this list as line-by-line verified facts:

  • With ENABLE_MODELSO, how function names inside module/controller/testviewso.so map to routes; only the switch-to-directory relationship was confirmed, not the full registration chain after loading.
  • The field coverage and generation rules of the three ORM model domains (cms/pg/lite); only the generation source, pool sharding, and the "keep existing model files" policy were confirmed.
  • The generation syntax and update triggers that turn view/ templates into viewsrc/view/*.cpp; only the file-header marker and the parser location were confirmed.
  • The concrete assertions in each tests/*.cpp case; these are described only by filename and by the conventions in tests/CMakeLists.txt.
  • Whether startup/main_dev.cpp and startup/main_daemon.cpp follow exactly the same chain apart from forking; the two were not compared line by line.
  • The implementation depth of pzexcel, pzword, and webpdf; only the public headers were read, without walking through each read/write flow.
